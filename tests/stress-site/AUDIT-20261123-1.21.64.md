# Audit — 1.21.64 (PHP install source and build flags)

Date: 2026-11-23
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe,
Ubuntu 26.04.1, kernel 7.0.0-43), verified against its pristine manifest
(696 packages) before the install and restored afterwards.  CPU mitigations
were **off** for every number below (operator request; a test-host-only GRUB
drop-in, removed at restore; `/sys/.../vulnerabilities/*` read
"Vulnerable").  Pair: `server-configs-nginx` 1.6.56.  Applications:
WordPress 7.1.4, XenForo 2.3.13 (200 threads / 2,600 posts / 60 users),
Chevereto 4.5.9-pro, deployed with `deploy-three-apps.sh`.

Primary focus: **is the PHP install source or its build flags worth anything
on this stack?**  Three sources were measured: the Sury packages every
host runs today, the Ubuntu 26.04 archive (no third-party key), and PHP
8.5.13 built from source with CentminMod's Intel flags and with a plain
distribution-style flag set.

## 1. Why the build was the last unmeasured lever

The 1.21.63 profile put 92 % of a logged-in XenForo thread page in PHP-FPM
(36.9 of 40 ms per request) and every uncached tier saturates all 12
threads.  On a CPU-bound stack one per cent of PHP CPU is one per cent of
throughput, so the compiler and the module set are the only server-owned
variables left.  The repository had always installed Sury and had never
measured an alternative:

* `lib/services.sh:31` — `configure_php_repo` writes one repository, Sury.
* `README.md:204` — "Repository: Sury, with an embedded keyring".
* Ubuntu 26.04 publishes PHP 8.5.4 in `universe`, with every extension the
  applications need (`php8.5-{fpm,mysql,gd,curl,xml,zip,mbstring,gmp,xsl}`),
  so an official-archive arm needed no third-party key.
* Sury's PHP 8.5.13 is built by Debian's rules with `optimize=-lto`
  (`debian/rules:22`), i.e. `-O2` generic plus hardening, no LTO, no PGO.
  That is the build every host has today, and the reference point.

## 2. The four arms

| Arm | What it is | Version | Flags |
|---|---|---|---|
| **sury** | installed by `setup.sh` (Debian packaging) | 8.5.13-3+debsuryorg | `-O2`, generic, hardening, no LTO/PGO |
| **ubuntu** | Ubuntu 26.04 archive packages, extracted (not installed) | 8.5.4-0ubuntu1.6 | `-O2`, generic, hardening |
| **src-gen** | source tarball, minimal XenForo module set | 8.5.13 | `-O2 -march=x86-64 -pipe` |
| **src-cm** | same source and module set | 8.5.13 | `-O3 -m64 -march=native -pipe` |

`src-cm` is CentminMod's default Intel path: `MARCH_TARGETNATIVE=y` with
`GCC_FALIGN_FUNCTION=n`, `PHP_LTO=n` and `PHP_PGO=n` in `centmin.sh`, which
resolves to `CFLAGS="-O3 -m64 -march=${CPU_MARCH} -pipe"`; on this Coffee
Lake Xeon `gcc -march=native` reports `skylake`, the same string CentminMod
uses.  The builds differ as intended: 26,148 AVX2 (`ymm`) instructions in
`php-fpm` for `src-cm` against 171 for the two distribution binaries.

The source builds load exactly the XenForo module set (mysqli, gd, curl,
mbstring, xml, zip, gmp, OPcache, JIT).  PECL redis 6.2.0 does not compile
against PHP 8.5 (`common.h` includes `ext/standard/php_smart_string.h`,
removed in 8.5) and PECL imagick 3.8.0 predates it; the distributions carry
patches, so **redis, igbinary and imagick come from the distribution for
every arm**. That also makes the extension code identical across arms: only
the PHP binary changes.

All four arms read the same managed `php.ini`, pool and scan directory:
12 static workers, OPcache 512 MB, tracing JIT 64 MB, huge code pages on,
`opcache.max_accelerated_files=130987` (Chevereto's vendor tree).  Each arm
was checked with `opcache_get_status()` before its run (`jit.on = 1`).

`tests/bench-php-matrix/` contains the tools: `build-php-source.sh`,
`extract-php-debs.sh`, `switch-php-arm.sh`, `bench-php-sources.sh`,
`bench-php-probe.sh` and `php-build-probe.php`.

## 3. Method

* Clock pinned at 3.6 GHz (`set-clock.sh 3600`): turbo on this host is
  power-limited (PL2 112 W then PL1 80 W, 4.5 to 4.1 GHz) and PHP CPU per
  request follows the clock 1:1 (1.21.63 §3.1).
* 3 rounds, arms rotated forward then backward inside each round, all 12
  guest/member tiers of `loopback-tiers.sh` run once for the baseline and
  the five PHP-bound tiers for the matrix (c=100, 10 s, loopback `wrk`).
* The guest cache is emptied before every arm; each URL is warmed for 2 s.
* Median of 3 with min-max spread; a change inside the spread or under
  ~3 % is noise.

|---|---:|---:|---:|---:|
| WP member home | 141 (128-142) | 142 (130-143) | 141 (140-142) | 141 (130-142) |
| WP member post | 133 (126-133) | 133 (122-133) | 132 (125-133) | 133 (123-134) |
| XF member home | 446 (443-449) | 430 (413-447) | 447 (417-451) | 453 (416-454) |
| XF member thread | 248 (248-250) | 250 (231-250) | 244 (231-251) | 252 (234-253) |
| Chev guest home (uncached) | 1448 (1439-1489) | 1461 (1368-1478) | 1320 (1317-1415) | 1447 (1292-1460) |

Against Sury: WordPress is flat for every arm; XenForo member home/thread
spans −3.8 % to +1.6 % with spreads that overlap the baseline; the one
larger number, the generic build on Chevereto's uncached home (−8.8 %), is
on a tier that uses 1.35 cores (not PHP-bound) and the same build is
neutral on every PHP-bound tier, so it is an outlier, not a build effect.
No arm clears the ~3 % bar.

The clean machine-code comparison agrees.  `php-build-probe.php` run from
the CLI (15 runs, minimum and median of each section; no FPM scheduler
noise):

| Section | sury | ubuntu | src-gen | src-cm |
|---|---:|---:|---:|---:|
| C builtins (json/preg/str/hash/sort), ms | 3.018 / 3.090 | 3.013 / 3.114 | 3.184 / 3.272 | 3.076 / 3.166 |
| Objects and methods, ms | 0.519 / 0.533 | 0.530 / 0.540 | 0.519 / 0.533 | 0.527 / 0.534 |
| Userland loops (JIT), ms | 0.218 / 0.222 | 0.215 / 0.216 | 0.218 / 0.224 | 0.218 / 0.219 |

`-O3 -march=native` is 1.9 % *slower* than Sury's `-O2` on the C-builtin
section and identical on the JIT section; the generic source build is
5.5 % slower than Sury.  The same probe served through FPM at 50
connections was too contended to resolve anything (the same arm's section
median varied 2x between rounds), so it is not used for the verdict.

### 4.1 Why the flags do nothing here

With `opcache.jit=tracing` the hot PHP code is emitted by the JIT as
machine code at run time; that code is identical whichever C compiler
built the interpreter, which is why the loop section is 0.218 ms for every
arm.  The flags only reach the interpreter's own C helpers and the
extensions, and the 1.21.63 profile showed those are a small share of a
real page once zlib moved to Angie.  A faster C compiler cannot help a
workload whose hot path is already generated code plus MariaDB I/O.

## 5. Verdict

* **Keep Sury.** It is as fast as anything measured, it is 9 patch
  releases ahead of the Ubuntu archive (8.5.13 vs 8.5.4), and it carries
  the extension set the applications use.
* **No `--php repo=ubuntu`.** It is not slower (inside the noise) but it
  is older and adds a second packaging path to test for no gain.
* **No source build.** `-O3 -march=native` with the minimal module set
  buys nothing on this stack, and a compiled PHP would put a toolchain and
  manual security updates on every host.  The tooling stays in
  `tests/bench-php-matrix/` so the measurement can be repeated when the
  JIT, the compiler or the workload changes.

|---|---|---|---|

| Chevereto 4.5.9-pro | 0 fatal | 0 fatal | **8.6** |

The XenForo vendor failures are
`src/vendor/braintree/.../Digest.php` (`${var}` interpolation) and

XenForo's debug mode turns the deprecations into a 500, which is why the
repository warns and keeps 8.5 for a forum.

## 8. Restore

`restore-baseline.sh` (run from `/tmp`, outside `/root/work`) with
`--purge all`, after deleting the audit-only trees outside the package
delta (`/opt/php-gen`, `/opt/php-cm`, `/opt/php-ubuntu`, `/etc/php-src`,
`/etc/php-ubuntu`, their units and logs, the PHP build and PECL trees).
Then `/root/audit`, `/root/work`, `/root/.debug` and the upload directory
under `/home/ubuntu` were deleted, the audit GRUB drop-in went with
`--purge`, and the host was rebooted.  A fresh `host-manifest.sh` against
the pre-install baseline:

* **696 -> 696 packages**, none added, removed or version-changed.
* **0 `/etc` files added, removed or changed.**  The one manual step was
  byte-level: the audit's `# audit` line in `/etc/hosts` was appended to a
  file without a trailing newline, and removing the line with `sed` left
  one, so the last byte was truncated to make the digest match the
  baseline exactly.
* Enabled units identical.  Active services identical except
  `fwupd.service`, which the baseline captured active and the reboot left
  inactive (same enabled unit list; a provider service, not the stack).
* sysctl: only `kernel.random.boot_id`, `net.core.netdev_rss_key` and
  `net.ipv4.tcp_fastopen_key`, which change on every boot.
* Mitigations back on (`/proc/cmdline` has no `mitigations=off`), hostname,
  timezone (UTC), swap (the two provider partitions, no `/swapfile`) and
  the disabled firewall as recorded.  `/root` and `/home/ubuntu` hold only
  their baseline entries; `/var/www`, `/var/lib/setup.sh`, `/etc/angie` and
  `/etc/php` are gone.

## 9. Follow-up (same day): every optimisation enabled

The first four arms left the obvious question open: what if LTO, PGO,
function alignment and the interposition/PLT switches are all on, and every
module is compiled from source too?  Measured on the same host, same apps,
same method:

| Arm | Flags | XF thread | XF home | WP home | WP post |
|---|---|---:|---:|---:|---:|
| Sury 8.5.13 | Debian `-O2` | 246 (244-247) | 419 (408-422) | 141 (129-142) | 138 (127-139) |
| + LTO | adds `-flto` `-falign-functions=32` `-fno-semantic-interposition` | 236 (219-246) | 393 (365-421) | 140 (137-140) | 138 (128-139) |
| + LTO + PGO | two-stage, trained on real XF/WP traffic | **213 (211-221)** | **359 (359-385)** | 131 (130-131) | 131 (121-131) |
| + PGO only | same, no LTO | **230 (213-231)** | **398 (368-399)** | 133 (133-133) | 131 (121-131) |

LTO alone is a wash (-0.7 % to +0.0 %).  PGO costs **5-10 %** on the
application tiers, with or without LTO.  The CLI probe (15 runs, minimum)
agrees and removes any scheduler doubt: C builtins 3.014 ms for Sury
against 3.589 ms (+19 %) for LTO+PGO with the JIT on, and 2.537 against
3.160 ms (+25 %) with the JIT off; userland loops 0.216 vs 0.226 ms.
Even without the JIT, where PGO is supposed to shine, the binary is
slower.

PGO training used an instrumented build behind the same vhosts: 144
req/s on the XenForo thread, 258 on the home page, 94/93 on WordPress,
1,053 on the probe, 779 `.gcda` files, and a `-fprofile-use` rebuild with
zero missing profiles.  Extension modules came from source: redis 6.3.0
and imagick 3.8.1 built with the new tree's phpize.  igbinary 3.2.16 does
not compile on 8.5 (`php_smart_string.h` again); redis builds without it
and XenForo's core provider does not need it.

Build traps worth recording: `-fno-plt` with LTO does not link (undefined
`.L1`-style local labels from bfd), `-flto-partition=max` was removed with
it, and a PGO rebuild fails configure with `-Werror=coverage-mismatch`
from the reused `conftest.c` profile unless those files are deleted.

Verdict unchanged and stronger: **keep the distribution package; do not
enable PGO on this stack**.  Tools added: `build-php-max.sh`,
`train-php-pgo.sh` (see section 10).
