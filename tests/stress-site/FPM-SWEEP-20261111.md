# PHP-FPM worker sweep - 2026-11-11

Authenticated XenForo thread page (no FastCGI cache; every request renders in
PHP), 100 connections, 8 s per count after a 3 s warm-up, `oha` from the macOS
workstation.  Host: 16 logical CPUs / 27 812 MiB / NVMe bare metal, PHP 8.5.12,
tracing JIT 64 MB.  `pm = static`; only `pm.max_children` changes.

| Workers | req/s | p50 ms | p99 ms | PHP ms/req |
|---:|---:|---:|---:|---:|
| 8 | 412 | 246.5 | 291.1 | 18.87 |
| 12 | 511 | 199.0 | 221.9 | 21.54 |
| **16** | **572** | **171.0** | **321.0** | **23.83** |
| **20** | **574** | **173.9** | **209.4** | **24.63** |
| 24 | 548 | 181.2 | 309.8 | 25.73 |

Eight workers leave half the host idle and lose 28% of the throughput; beyond
16 the same CPU is shared by more processes, per-request CPU rises and
throughput flattens (20) then falls (24).  The shipped 1.0 worker per logical
CPU (`php_workers_per_cpu_tenths`) therefore remains the right target on this
host class.  Absolute rate drifts ±8% between sweeps with link/CPU state; the
shape (a broad 16-20 plateau) repeated in every run.

## CPU saturation without `fastcgi_cache`

During the 16-worker run PHP-FPM used ~1 100% of one core (11 of 16 logical
CPUs at 100% of a core each), MariaDB ~135% and Angie ~14%.  The remaining
cores are not idle work: each static worker waits on MariaDB and the socket
between requests, so `pm.max_children` is not the limiter — per-request PHP
execution is.  That is why the JIT and application-level changes (widgets,
templates, plugins) move this tier and extra workers do not.
