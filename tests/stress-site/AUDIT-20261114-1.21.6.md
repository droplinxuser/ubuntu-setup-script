## 1. What changed

This cycle re-validated the 1.21 line end to end on a freshly restored
baseline.  The production modules needed no correction; the only defects
found were in the benchmarking harness, where they had already produced a
silently invalid measurement during this audit.

| Area | Change | Verification |
|---|---|---|
| Remote stress harness | A run throttled by Angie's per-IP limiter reported the 429 rate as requests/s. `run-stress-remote.sh` now tracks the 429 share per scenario and fails with exit 3, a stderr error and a `WARNING` report section when 5% or more of a scenario's answers are 429. | Without an exemption `xf-guest` answered 41 204 of 41 614 requests with 429 and the run exited 3; with `SETUP_LIMIT_REQ_EXEMPT=192.168.1.111/32` it exited 0 |
| FPM metrics | `collect-metrics.sh` queried `cgi-fcgi` and then a `/fpm-status.php` that does not exist, so every sample recorded an empty PHP-FPM field.  Without `cgi-fcgi` it now counts the pool from the process table. | idle `workers=16 busy~=0`; under load `workers=16 busy~=16` |

No `setup.sh` or Angie configuration change was required.  The audit
therefore also serves as a regression check on the 1.21.5 tree.

## 3. Application compatibility

The deprecation scan (`compat-php.sh`, forced `E_ALL`) and a side-by-side
PHP 8.6 CLI (installed only for the scan, then purged) give the ceiling for
each application.  "Functional" means the production error level
(`E_ALL & ~E_DEPRECATED`), which is what the applications ship with.

| Application | 8.4 | 8.5 | 8.6 RC5 | Newest fully compatible |
|---|---|---|---|---|
| WordPress 7.1.4 | clean | clean | clean bootstrap (`wp-load.php`, 19 compile deprecations, 0 fatals) | **8.6** (extensions permitting) |
| XenForo 2.3.13 | clean | clean | blocked: `php8.6-redis`/`igbinary`/`imagick` unpublished; 2 unused vendor files (`laminas-mail`, `braintree`) fail to compile | **8.5** |
| Chevereto 4.5.9 | clean (with `?ImageManager` vendor fix) | clean (same fix) | blocked: `php8.6-redis`/`imagick` unpublished | **8.4** |

Notes:

- Chevereto 4.5.9 bundles Intervention Image 2.x, whose implicit-nullable
  constructor is a fatal deprecation under the application's shutdown
  handler on 8.4+.  The one-line upstream fix (`?ImageManager $manager =
  null` in `ImageManagerStatic.php`) makes it clean on 8.4 and 8.5.  This is
  an application defect, not a server setting.
- Under forced `E_ALL` plus XenForo `debug=true`, the reply/search POSTs
  answer 500 because the debug handler turns core/vendor deprecations into
  exceptions (`src/XF/App.php` "Using null as an array offset").  Under the
  production error level the same requests answer 200.  `compat-php.sh` is
  therefore a deprecation finder, not a pass/fail gate; the functional suite
  is the gate.
- The shipped `--upgrade-php` preflight refuses 8.6 for this host because
  Chevereto and Redis-backed XenForo would lose `redis`; nothing is changed
  before the refusal.

## 4. Performance

Workstation `oha` 1.16.0 over the LAN (`--connect-to`, TLS, HTTP/1.1),
8 s per tier, 200 connections for guests and 100 for member/uncached tiers.
The load-generator address is exempted from the rate limiter
(`SETUP_LIMIT_REQ_EXEMPT=192.168.1.111/32`, persisted in
`/etc/default/setup-tuning`); every response in the tables below is 200.

| Layer | Setting | Source |
|---|---|---|
| Kernel | `somaxconn=65536`, `tcp_max_syn_backlog=65536`, `netdev_max_backlog=32768`, rmem/wmem 32 MB, `fs.file-max=10485760`, `swappiness=1`, dirty 1.11 GB / 278 MB, `tcp_congestion_control=bbr`, `fq` | `--basic` hardware profile |
| Angie | 16 workers, 32 768 connections/worker, `worker_rlimit_nofile=131072` | 1 worker/CPU |
| PHP-FPM | `pm=static`, 16 children, `max_requests=16384`, `process_control_timeout=10s` | 1 worker/CPU, worker recycling |
| OPcache | 512 MB, 93 238 files, 64 MB interned strings, tracing JIT 64 MB | RAM/16 clamp, vhost file count |
| MariaDB | buffer pool 1 738 MB (live data +20 %), redo 434 MB, `max_connections=200`, table cache 4 000, `io_capacity` 10000, `pool-of-threads` | data-set sized, NVMe class |

| Elasticsearch | 4 GB heap | explicit `ram=4g` |

MariaDB's pool is intentionally data-set sized (≈1.45 GB of seed data plus
20 %), not a fixed RAM fraction; the remaining RAM feeds Elasticsearch,
Valkey and the PHP workers.  Raising it further showed no throughput gain
on this workload.

## 6. Security checks

All three vhosts answered **403** for `.env`, `.git/config`, `.htaccess`,
`.DS_Store`, `composer.json/lock`, `wp-config.php` (+ `.bak/.save/.swp`) and
archives (`.zip/.tar.gz/.sql/.sql.gz/.zst/.bz2`); **404** for `/logs/`,
`/mysql_database/`, `/phpinfo.php`, `/index.php/foo` and `/%2e%2e/...`;
**400** for `/..%2f...`; **405** for TRACE/PUT/DELETE/OPTIONS.  A forged
`Host` closes the connection.  A PHP file written into `wp-content/uploads`
is **403**.  `/foo/../index.php` is normalised with a 301 to the canonical
path; Chevereto's `/logs/` canonicalises to a 404.  TLS 1.0 and 1.1 are
refused; HSTS (2 years, preload), X-Frame-Options, X-Content-Type-Options
and Referrer-Policy are present on every vhost.  Guest responses carry no
`Set-Cookie`; a forged session bypasses rather than poisons the cache.
