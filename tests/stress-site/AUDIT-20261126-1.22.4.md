# Audit — 1.22.4 (first AMD host: EPYC 4245P, Ubuntu 24.04 and 26.04)

Date: 2026-11-26
Host: AMD EPYC 4245P (Zen 5, family 26 model 68, 6C/12T, 32 GB, NVMe,
bare metal at a cloud provider whose cloud-init manages `/etc/hosts`).
Ubuntu 24.04.5 (kernel 6.8) first, then an in-place `do-release-upgrade`
to 26.04.1 (kernel 7.0).  Mitigations at the kernel default (on).  The
CPU boosts to 4.9-5.4 GHz under these loads; no clock was pinned.
Pair: `server-configs-nginx` (branch `main`, unchanged this cycle).

## 1. Scope

Question asked: does the current code (1.22.3) work on AMD as it does on
the Intel test host, and is there anything to optimise there?  Every
earlier 1.22 test ran on the Xeon E-2236.

## 2. Method

* Baseline manifest of each OS before anything ran (24.04: 827 packages;
  26.04 after the upgrade: 852).
* A read-only code review of the build and tuning code for AMD-specific
  risks (perf/BOLT, `-march=native`, the CPU fingerprint, the governor),
  each finding checked against the code by a second reviewer.
* On each OS: the 1.21.71 installer (Angie package, Sury PHP 8.5, the
  distribution's valkey-server package, Elasticsearch, WordPress, XenForo,
  Chevereto), a reboot, the before benchmark (12 loopback tiers, `wrk
  -c100`, 10 s, 5 rounds, medians), `setup.sh --optimize` (the one-time
  migration), the functional walk, the security probe, the guest-cache
  cookie suite, a second `--optimize` under traffic (BOLT), a reboot, the
  after benchmark.
* AMD tuning sweeps on 24.04 (variant order rotated each round): JIT mode
  and buffer, PHP workers, nginx workers, BOLT `-hugify`.
* Between the two OSes the host was restored to the 24.04 baseline, then
  upgraded.

## 3. AMD-specific results

* clang 23 (apt.llvm.org) resolves `-march=native` to `znver5`.
* BOLT works with AMD's branch records (LbrExtV2, 16 entries deep, against
  32 on the Xeon): nginx 991, PHP 2,515 and Valkey 398 profiled functions,
  in line with the Xeon; the thresholds (150/300/100) are met with margin.
* Sweeps (24.04, member/uncached tiers unless noted), req/s medians:

  | Sweep | Result |
  |---|---|
  | JIT: tracing 64 MB / off / function / tracing 128 MB | WP member home 344 / 313 / 323 / 342; XF thread 584 / 590 / 615 / 578: tracing stays (function helps XF thread, costs WP) |
  | PHP workers 6 / 9 / 12 / 18 / 24 | WP member home 234 / 303 / **342** / 329 / 320; XF thread 403 / 515 / **585** / 576 / 574: one per thread stays |
  | nginx workers 6 / 8 / 10 / 12 (cached tiers) | XF thread 487,946 / **517,773** / 483,499 / 476,682, p99 0.3 ms at 8 vs ~3 ms at 10-12: two thirds stays |
  | BOLT layout: current / `-hugify` | ties on every tier (XF thread 587 / 587) |

  No AMD-specific constant was needed.  Huge code pages after BOLT cover
  the original `.text` (16 MB) and not BOLT's new hot segment; `-hugify`
  (BOLT's own remap of the hot code) measured no difference, and
  `-use-old-text` is refused by BOLT for this binary (a hand-written
  OpenSSL function cannot be skipped in that mode).

## 4. Findings fixed

### 4.1 Chevereto: session GC inside requests (high)

1.22.0 added a `[PATH=]` section with `session.gc_probability = 1` for
Chevereto roots, because nothing else removed Chevereto's file sessions
(`/tmp`, one per guest visit).  PHP's files GC lists and stats the whole
directory, inside a request, after that request took its session lock.
Evidence on 24.04: one worker made 356,332 `newfstatat` calls in 5 s; the
member tier (one session for all connections) waited in `flock` on the
session file for ~256 ms at a time; throughput fell and p99 grew as `/tmp`
grew (242k -> 750k files during the day).  A/B on the same host:

| Tier | GC in requests | GC off |
|---|---|---|
| Chev member explore | 1,032-1,171 req/s, p99 457-753 ms | 2,211-2,220 req/s, p99 48 ms |
| Chev guest home (uncached) | 3,253-3,517 req/s, p99 300-420 ms | 4,324-4,328 req/s, p99 37 ms |

This is also the member-explore p99 regression 1.22.3 recorded on the Xeon.
Fixed: GC off for those roots, `setup-php-sessionclean.timer` (10 min, idle
priority) deletes expired files, keeping the save path's depth and the
longest `session.gc_maxlifetime` any FPM configuration sets.  With sessions
in Valkey (`CHEVERETO_SESSION_SAVE_HANDLER=redis`, now suggested by the
report) member explore measured 9,466 req/s (p99 11.7 ms) and uncached
guests 4,418 req/s, with no files.

### 4.2 CPU fingerprint and the Zen 5 RDSEED workaround (medium)

RDSEED/RDRAND were hashed.  Linux clears RDSEED on Zen 5 parts with the
RDSEED erratum (microcode gives it back); such an update would have looked
like a CPU change and kept every compiled service down until the native
rebuild.  Neither flag is hashed now; the gates accept the four 1.22.0-
1.22.3 variants, so updating rebuilds nothing (unit tests build both
forms).  On this host RDSEED is present on both kernels (microcode
0xb404035).

### 4.3 `--purge` refused on Ubuntu 24.04 (high for 24.04 hosts)

The purge hit the fresh-install check (26.04 or newer), so a host
`--optimize` had migrated on 24.04 could not be purged.  It now uses the
`--optimize` gate (22.04-26.04).

### 4.4 Hostname reverted by cloud-init (medium)

The provider's vendor-data sets `manage_etc_hosts`; cloud-init rewrote the
127.0.1.1 line with its own name at every boot and `hostname -f` failed.
`--basic` writes a `cloud.cfg.d` drop-in, `--optimize` repairs hosts
renamed earlier, `--purge basic` removes it.  Verified across reboots.

### 4.5 BOLT passes that collide (medium)

The migration queues a delayed BOLT unit; an `--optimize` started within
its delay found the build lock held (PHP skipped) or reloaded PHP during
its sample (136 functions, skipped), and the queued pass re-ran a Valkey
BOLT that had just restarted Valkey (perf lost the process).  Now:
`--optimize` cancels a queued pass that is still waiting (and waits for one
already working), and the daily refresh retries a missing PHP BOLT (as it
did for nginx).  Both verified live (refresh: 2,511 functions).

### 4.6 Smaller

* `apt-mark hold` lost to `apt-daily` (dpkg lock): retried while locked.
* perf errors quoted verbatim instead of "no LBR on this CPU or VM?".
* The original `energy_performance_preference` is recorded and restored.
* Tool install order: `build-common.sh` before each tool.
* Harness: `wrk` required, `set-fpm.sh` uses the active version,
  `restore-baseline.sh` stops when the purge fails and keeps an active UFW
  (it had disabled the provider's firewall on this host; re-enabled with
  the baseline rules within minutes).

## 6. Validation

* Unit suites on the host: tuning 2,944 (0 failed, 1 skipped), migration
  478 (1 environmental skip), PHP build 317; ShellCheck 0.11.0 clean at CI
  severity; `check-public-ips.sh` clean.
* Both OSes: functional walk 0 unexpected, security 78/78, cookie 109/109,
  0 segfaults, every service back after each reboot, a repeated
  `--optimize` changed nothing (8 s).
* An independent review of the diff found six more issues (install order,
  save-path depth, session lifetime source, commented env.php lines, EPP
  on already-switched hosts, an FQDN-first hosts line); all are fixed and
  tested.

## 7. Open items

* XenForo member thread on AMD: no gain from the migration (Intel +2.7 %).
* Chevereto file sessions still cost a file per guest visit; the report
  now suggests Valkey sessions.
* Valkey's deferred BOLT re-runs for a build that is already BOLTed when
  it waited for the lock (harmless; `--optimize` now cancels it first).
