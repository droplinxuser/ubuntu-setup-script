# Audit — 1.21.67 (XenForo server shootout: Angie + PHP-FPM vs OpenLiteSpeed + LSCache)

Date: 2026-11-23/24
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe, Ubuntu
26.04.1, kernel 7.0.0-43), checked against its pristine state before the
install (696 packages, clean `/root` and `/home/ubuntu`) and restored
afterwards.  CPU mitigations were **off** for every number below (operator
request; `--basic mitigations=off`, removed at restore).  Pair:
`server-configs-nginx` 1.6.58.  Applications: WordPress 7.1.4, XenForo 2.3.13,
Chevereto 4.5.9-pro, deployed with `deploy-three-apps.sh`; for the shootout
the forum was then grown with the Hampel Seeder to **20,060 users, 10,200
threads and 103,002 posts** (`bench-php-matrix/seed-xf.sh`).

## 1. What this cycle chose and why

**Primary question (operator):** which server serves a large XenForo forum
fastest on this hardware: the shipped Angie + Sury PHP-FPM with
`fastcgi_cache`, Angie + a clang `-O3 -march=native` PHP-FPM, or
OpenLiteSpeed + LSAPI with LSCache through the official XenForo add-on
(`xenforo_addon_LiteSpeedCache-2.3.0.zip`)?  OpenLiteSpeed had never been
measured here: 1.21.60/61 excluded it because it has no generic page cache,
and the add-on closes that gap.

**Audit:** two rounds, each finding checked by independent refuters before
anything changed (round 1: 3 lenses per finding; round 2: 2).  Round 1 (setup
parity/tuning/robustness and Angie security) gave 8 findings: 7 confirmed, 1
refuted (container huge pages).  Round 2 (a review of this cycle's own diff
plus PHP tuning and purge/restore) gave 16: 10 confirmed and fixed, 6
refuted or 1/2 and left (listed in §6).  Round 2 caught a regression in this
cycle's own HUP handling before it shipped.

## 2. Arms

All four arms run PHP **8.5.13**, the same managed `php.ini` and settings
files (OPcache 512 MB, tracing JIT 64 MB), **12** PHP processes sharing one
OPcache, the same TLS certificate, HTTP/1.1 over TLS from loopback `wrk`,
access logs off, and the same XenForo code (the LSCache add-on is installed
for every arm).

| Arm | Server | PHP | Guest page cache |
|---|---|---|---|
| **sury** | Angie (shipped tree) | Sury `php8.5-fpm`, FastCGI | `fastcgi_cache`, 5 min |
| **src-clang** | Angie | clang `-O3 -march=native -falign-functions=32 -fno-semantic-interposition`, FPM | `fastcgi_cache`, 5 min |
| **ols-lsphp** | OpenLiteSpeed 1.9.4 | LiteSpeed `lsphp85` 8.5.13, LSAPI | LSCache + XenForo add-on, 300 s |
| **ols-src-clang** | OpenLiteSpeed 1.9.4 | the clang build's `lsphp` (`--enable-litespeed`), LSAPI | LSCache + add-on |

Every arm was checked before measuring: SAPI (`fpm-fcgi` / `litespeed`), JIT
on, extension set (redis, igbinary, imagick, mysqli, gd, zip, zlib, sodium
...), a guest page served from the cache, a member page served by PHP with
`data-logged-in="true"`.

### 2.1 OpenLiteSpeed: three configuration traps found on the way

1. **suEXEC floor.**  lsphp runs as `www-data` (uid 33, the owner of the
   roots); OpenLiteSpeed's `CGIRLimit` refuses uids below 100 by default and
   every request was a 503 ("cgidSuEXEC failed").  `minUID 11 / minGID 10`.
2. **Keep-alive.**  `maxKeepAliveReq 65536` (Angie's value) is out of range
   and silently becomes **100**, a TLS handshake every 100 requests.  The
   maximum, 32767, is never reached in a run.
3. **Members got the cached guest page.**  With the add-on's documented
   rule set, `CacheLookup on` serves the public entry to every request.  The
   add-on's `xf_lscxf_logged_in` marker only exists for logins made after it
   was installed, so a member with `xf_user`/`xf_session` (remember-me, or
   logged in before the add-on) got `x-litespeed-cache: hit` and a
   logged-out page.  No member data leaks (the add-on never lets a logged-in
   page be stored), but members are shown as guests.  Fix in the harness:
   `RewriteRule .* - [E="cache-vary:xf_session,xf_user,xf_lscxf_logged_in,xf_session_admin"]`
   before `CacheLookup on`; a no-cache rule placed before or after the lookup
   did not help.  **Anyone running the add-on in production needs this line.**

## 3. Method

* Clock pinned at 3.6 GHz (`set-clock.sh 3600`).
* `bench-php-sources.sh`: arms rotated forward then backward each round, the
  guest cache (Angie and LSCache) emptied before each arm, each URL warmed
  for 2 s, loopback `wrk -t4`, CPU per request from the systemd cgroups
  (`sample-cpu.sh` now separates OpenLiteSpeed and lsphp).
* Median with min-max spread; under ~3 % or inside the spread is noise.

### 3.1 Harness defects found and fixed this cycle

* **The summary's "p99" was the median.**  `bench-php-sources.sh` read column
  5 (p50) as p99 since 1.21.64.  Fixed; `RAW=` keeps every row with non-2xx
  and CPU.  Earlier tier tables came from `loopback-tiers.sh` directly and
  are not affected.
* **lsphp outlived OpenLiteSpeed.**  After a switch away from an OLS arm,
  LSAPI children kept burning CPU for seconds; an Angie arm measured right
  after lost ~10 % (199 vs 222 req/s, lsphp still in its CPU samples).
  `switch-php-arm.sh` now waits until every lsphp has exited.  The 5-round
  matrix (§4.2) never measured an Angie arm directly after an OLS arm; the
  encoding run (§4.4) did, and its contaminated rounds are excluded.
* **wrk's latency hides starvation.**  It records latency only for completed
  requests, so a server that serves some connections and parks others shows
  a short tail.  The per-visitor latency probe (§4.3) measures what a new
  visitor sees.

### 4.3 What a visitor waits under member saturation

`wrk -c100` on the member thread page for 70 s; meanwhile 150 sequential
requests from a separate client, each timed end to end (`curl
--max-time 30`).  Two rounds, arms rotated:

| Arm | p50 | p90 | p99 | max | timeouts (30 s) | wrk req/s alongside |
|---|---:|---:|---:|---:|---:|---:|
| sury | 0.461 / 0.443 s | 0.473 / 0.451 s | 0.480 / 0.456 s | 7.35 / 0.46 s | 0 / 0 | 218 / 228 |
| src-clang | 0.439 / 0.435 s | 0.449 / 0.445 s | 0.457 / 0.454 s | 8.27 / 8.59 s | 0 / 0 | 227 / 229 |
| ols-lsphp | 0.038 / 0.038 s | 0.210 / 0.045 s | 1.95 / 3.72 s | **30.0 s** | **2 / 2** | 234 / 232 |
| ols-src-clang | 0.037 / 0.036 s | 0.057 / 0.041 s | 2.92 / 4.85 s | **30.0 s** | **2 / 2** | 242 / 243 |

Angie + PHP-FPM serves in arrival order: once the box is saturated every
visitor waits about the same 0.45 s.  OpenLiteSpeed keeps about 12
connections moving and parks the rest: most requests are fast, but a parked
visitor waits seconds, and 4 of 300 probe requests were still waiting after
30 s.  wrk cannot show this (it records latency only for requests that
finish), which is why its OpenLiteSpeed p99 looked better than Angie's.
The occasional 7-8 s maximum on the Angie arms is the first probe request
after the switch (OPcache warm-up behind 100 queued requests).


### 4.4 Member pages with matched encoding

The member gap in §4.2 was larger than the CPU figures explain, so the
member tiers were measured again with the §3.1 fixes: every lsphp gone and
a 5 s pause after each switch, arms alternated, 5 rounds, 12 s, c=100.
Angie was measured twice, with the client's `gzip, br` (brotli, as in every
tier) and with `gzip` only, because OpenLiteSpeed compresses dynamic pages
with gzip only:

| Member tier | Angie, `gzip, br` | Angie, `gzip` | OpenLiteSpeed | OLS vs Angie (br) |
|---|---:|---:|---:|---:|
| thread | 221 (220-221) | 222 (221-222) | 223 (223-224) | **+0.9 %** |
| home | 248 (248-249) | 251 (251-253) | 257 (257-261) | **+3.6 %** |

CPU per member thread page: Angie 3.1 + PHP-FPM 44.5 = **47.6 ms**;
OpenLiteSpeed 0.4 + lsphp 47.5 = **47.9 ms**.  Home: 2.5 + 37.7 = 40.2 ms
against 38.0-39.6 ms.  The two stacks spend the same CPU on a member page;
compression is not the difference either (Angie's gzip costs what its
brotli costs here).  Thread is a tie; home is at the 3 % bar.


### 4.5 Verdict

**Keep Angie + Sury PHP-FPM + `fastcgi_cache`.  OpenLiteSpeed is not
adopted; neither is a compiled PHP.**

* **Guests, which are most of a large forum's traffic (and all of its bot
  traffic): Angie is 16-23 % faster** (125.0k vs 96.7k req/s on the forum
  index, 99.4k vs 83.3k on a thread), and the gap holds at c=400.  An LSCache hit costs 14-22 % more CPU than
  an Angie hit, and OpenLiteSpeed stops short of using all 12 threads.
* **Members: a tie.**  Controlled, the thread page is +0.9 % and the index
  +3.6 % for OpenLiteSpeed, at equal CPU per request.  The +6-9 % of the
  bigger matrix came partly from harness defects found during this cycle.
* **Under saturation Angie + FPM is fair, OpenLiteSpeed is not:** p99 0.46 s
  for every visitor against seconds-long waits and 30 s timeouts for parked
  connections.
* **OpenLiteSpeed needs care to be correct:** with the add-on's documented
  rules it shows members the cached guest page; the suEXEC floor and the
  keep-alive limit have to be changed by hand.  It would also mean a second
  web-server stack in `setup.sh` with its own security model, while the
  Angie tree carries every guest-cache safety rule and regression probe this
  project has built.
* **clang PHP:** +3.1 to +3.4 % on member pages again (it was +3 % in
  1.21.66), 0 on cached pages, the same on OpenLiteSpeed.  It stays a
  measured option, not a default: a toolchain and a manual rebuild per PHP
  security release cost more than 3 % on one tier buys.
* **lsphp built with clang** adds nothing measurable over LiteSpeed's own
  lsphp85 (within 1 % on every tier).


## 5. Fixes (all with regression tests)

### 5.1 Security (server-configs-nginx 1.6.58)

| Finding | Evidence | Fix | Test |
|---|---|---|---|
| A Cookie with `\v`/`\f` before a name passed the guest-cache default-deny: PHP strips those bytes, the allowlist and `$cookie_*` did not | `http.d/fastcgi_cache.conf:84`; on the host `_ga=1;\vsso_token=abc` gave `MISS MISS HIT` and the next plain guest got that copy (PHP saw `sso_token`, `xf_language_id`) | first map regex: any C0 control character but TAB, or DEL, is unlisted | 3 tree checks (Perl on the shipped regex), 12 HTTP probes over the three apps (cookie suite 86 → 98); old tree fails them |
| XenForo front-proxy cache stored an origin 403/429 for every guest for 5 s | `h5bp/xf_proxy_pass.conf:68-73` (`any 5s`) | `proxy_cache_valid 403 429 0s` before `any` | tree check |
| Login limiter keyed on the full IPv6 address: one /64 = 2^64 buckets | `http.d/limit_req.conf:35-38` | `map $binary_remote_addr` keeps the first 8 bytes of an IPv6 address (`(?s)`, `\z`) | live probe: 40 addresses of one /64, all 200 on the old key, 429 at attempt 12 on the new (security 73 → 74); tree check |

The WooCommerce half of the limiter finding was refuted (WooCommerce handles
its login POST on every URL, so adding `my-account` to the route list does
nothing).  Cost of the cookie rule: XF guest home with a neutral `_ga`
cookie, 3 rotated rounds per tree: median 105.3k (old) vs 105.1k req/s (new),
inside the spread.  Requests without a Cookie header never reach the regex.

## 6. Refuted or left

* Container huge pages (`configure_sysctl` in a privileged LXC): refuted
  0/3, intended and documented.
* WooCommerce `my-account` in the login limiter: the proposed fix would not
  work (see 5.1).
* `restore-baseline.sh` resetting UFW without reading the baseline: 1/2, the
  harness's documented scope (the audit host's baseline has UFW inactive).
* `--upgrade-php` not migrating `phpenmod` fragments: 1/2, documented design.
* Keeping only this run's keys under `OPT_KEEP_EXPLICIT`: refuted, a
  domain-only run never takes the keep path.
