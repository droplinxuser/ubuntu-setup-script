# Anubis behind Cloudflare — 720p.site-b.example (2026-11-18)

Host: `origin-host` / 203.0.113.25 (Ubuntu 24.04.5, 8 vCPU,
32 GB).  Sites: `720p.site-b.example`, `site-e.example`, `site-f.example`.
Public DNS for all three resolves to Cloudflare (`172.67.68.227`,
`104.26.14.120`, `104.26.15.120`); the origin sees the CDN/proxy address
`203.0.113.23` as its peer.

Command under test:

```
bash setup.sh --optimize --reset-overrides anubis=yes
```

## Symptom

The public site loops between Cloudflare's "Just a moment..." and the Anubis
challenge, and the Anubis page sometimes stops at "Calculating... 0 kH/s".

## Origin defects found and fixed (1.21.31)

### 1. Thai challenge page panics → 502

Anubis 1.28.2 localises its own pages from `Accept-Language` with go-i18n
`MustLocalize`.  The bundled `th` catalogue has no `simplified_explanation`,
so a Thai browser makes the handler panic and Angie answers **502**
(reproduced deterministically with `Accept-Language: th`; en/ja/de/fr/zh/ru/
ar/hi/id/vi/tr/ko/pt/es/it/pl were fine).

Fix: the managed `anubis.env` pins `FORCED_LANGUAGE=en` (English is the only
catalogue complete in every shipped release).  `SETUP_ANUBIS_LANGUAGE` can
select another locale once upstream completes it.  The application still
receives the visitor's own `Accept-Language`.

### 2. CDN-perimeter guards answer 444 → 502 for every request

`site-e.example` and `site-f.example` carried:

```
set_real_ip_from 203.0.113.23;
real_ip_recursive on;
if ($realip_remote_addr != "203.0.113.23") { return 444; }
```

`$realip_remote_addr` is the **direct peer** (before `real_ip`).  Behind
Anubis the peer is the local Unix socket (`unix:`), so the guard never passed:
every page and every static-shadow request answered 444, which the filter
reports as 502.  `720p.site-b.example` has no such guard and was unaffected.
This is why two of the three sites failed while one worked.

Fix: `anubis_disable_realip_guards()` comments the guard (single- or
multi-line) in the moved vhost, logs it in the `--optimize` report, and also
runs for vhosts integrated by an older release.  The socket (0660 in a 0750
runtime dir, no public listener left on the vhost) is the perimeter; disabling
Anubis restores the original vhost and guard.

## Origin verification (all three vhosts, direct)

Solved the real proof-of-work with a script (parse challenge → SHA-256 brute
force → GET `/api/pass-challenge` → cookie → fetch `/`):

| Host | Challenge | Pass-challenge | Authenticated page |
|---|---|---|---|
| 720p.site-b.example | 200 (Thai UA, English UI) | 302 + auth cookie | **200, 56,954 B — "Video Optimizer v9.18"** |
| site-e.example | 200 | 302 + cookie | **200, 69,769 B — "site-e"** |
| site-f.example | 200 | 302 + cookie | **200, 242,890 B — "Media \| site-f"** |

Static assets through the shadow: site-e image 200 (87,881 B), site-f
thumbnail 200 (6,608 B).  40 rapid requests to the Anubis assets through the
terminator: 200/200, and 30 through the public address as a non-whitelisted
source: 200/200.  Angie's error log has **0** "limiting requests" entries.
No panics after the 10:54 restart.

## Remaining layer: Cloudflare

With no Cloudflare clearance cookie, **every** URL — including
`/.within.website/x/cmd/anubis/static/*` — answers CF's managed challenge:

```
HTTP/2 403
cf-mitigated: challenge
server: cloudflare
```

With the in-app browser (Electron UA `OpenCode/2.3.0 … Electron/44.9.1`),
Cloudflare never grants clearance, so:

1. the Anubis page's subresource requests are challenged/rate-limited
   (`429` on `locales/en.json`, `worker/sha256.mjs`; the workers die and the
   page shows "all proof of work workers failed"), and
2. the `pass-challenge` navigation is challenged again, which produces the
   loop (the tab URL becomes the pass-challenge URL under a "Just a moment..."
   page).

That is a two-bot-filter interaction (Cloudflare managed challenge + Anubis),
not an origin failure: the origin answers 200 to the same requests with a
non-challenged client.

## Recommended Cloudflare changes

1. **WAF → Skip** (or "Bypass" for Bot Fight/Managed Challenge) for
   `/.within.website/*` and `/.well-known/*` on this zone.  This lets the
   challenge page load its own assets and submit `pass-challenge` without a
   second challenge.
2. Keep the zone Security Level at Medium/High, not "I'm Under Attack", if
   every navigation is challenged.
3. Either layer is sufficient: if Cloudflare's bot protection is the intended
   perimeter, disabling Anubis (`--optimize anubis=no`) removes the duplicate
   challenge and the extra hop; if origin-level filtering is required for
   direct-IP clients, keep Anubis and apply rule 1.

No origin-side change can bypass the CF challenge; `429` never comes from
Angie (verified with non-whitelisted sources) and the origin returns 200 for
the exact paths Cloudflare challenges.
