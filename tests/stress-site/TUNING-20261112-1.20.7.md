# setup.sh 1.20.7 - three-application validation (2026-11-12)

Host: `audit-host` (AMD Ryzen 7 8745HS, 8 cores / 16 threads, 27 812 MiB RAM,
NVMe, Ubuntu 26.04.1, bare metal, kernel 7.0). Stack installed from the local
checkouts with `--basic --angie --php ver=8.5 --mariadb size=auto --valkey
--elastic ram=4g --others all`, then `--optimize`. Applications: WordPress
7.1.4 (100 users / 400 posts / 300 comments), XenForo 2.3.13 (60 members /
200 threads / 2 600 posts, friendly URLs, Valkey cache over the Unix socket,
server-based job trigger) and Chevereto 4.5.9 (Valkey cache), each created
with `--domain ... app=wordpress|xf|chevereto db=... user=... pass=...`.

Load generator: `oha` 1.16.0 on a macOS workstation. **Both the workstation
and the host were on Wi-Fi**, so every cached tier tops out at 3-4k req/s on
the link, not on the server. Server-side CPU per request (systemd cgroup
accounting, `sample-cpu.sh`) is the number the decisions below are based on.
The workstation subnet was in `SETUP_LIMIT_REQ_EXEMPT`.

| Profile | WordPress member home | XenForo member thread | Chevereto guest home |
|---|---|---|---|
| `opcache.jit = off` | 295 req/s, 52.1 ms PHP | 601 req/s, 24.0 ms PHP | 2 340 req/s, 3.69 ms PHP |
| **tracing, 64 MB (shipped)** | 298 req/s, 49.9 ms PHP | 588 req/s, 24.5 ms PHP | 2 274 req/s, 3.80 ms PHP |
| function, 64 MB | 249 req/s, 58.4 ms PHP | 578 req/s, 24.6 ms PHP | 2 234 req/s, 3.86 ms PHP |

Tracing is 4% cheaper than JIT-off on WordPress and 2-3% dearer on XenForo
and Chevereto in this run, all inside the run-to-run band; the 1.20.1 sweep's
+5% on XenForo did not repeat today. Function JIT is the worst on all three.
The shipped profile stays: `opcache.jit = tracing`, `jit_buffer_size = 64M`
(OPcache/8, clamped 32-128 MB), PHP's default hotness thresholds
(`jit_hot_loop 64`, `jit_hot_func 127`, `jit_hot_return 16`,
`jit_hot_side_exit 64`).

## Compression cost on cached pages

A cached WordPress page costs Angie about 1 ms of CPU per hit and a cached
XenForo page 0.14 ms. XenForo gzips its own output, so the cache stores the
compressed body; WordPress and Chevereto bodies are stored uncompressed and
Brotli-compressed on every hit. WordPress home (92 KB HTML), Angie CPU per
cached hit by level:

| Setting | Bytes on the wire | Angie CPU per hit |
|---|---:|---:|
| **Brotli 4 (shipped)** | 13 435 | 0.96 ms |
| Brotli 3 | 13 970 | 0.63 ms |
| Brotli 2 | 14 382 | 0.59 ms |
| Brotli 1 | 15 462 | 0.40 ms |
| Brotli 0 | 16 091 | 0.33 ms |
| Brotli off (gzip 4) | 13 935 | 0.85 ms |

Level 3 costs 34% less CPU than level 4 for 4% more bytes, the same shape the
comment in `angie_brotli_level` records for a XenForo page. The default stays
at 4; an origin whose cached WordPress or Chevereto pages are CPU-bound can
set `SETUP_BROTLI_LEVEL=3`.

## Open finding: cached guest pages replay `Set-Cookie`

`h5bp/php_chev.conf` and `h5bp/php_xf.conf` in server-configs-nginx cache
guest responses with `fastcgi_ignore_headers ... Set-Cookie` and do not hide
the header, so the cookie of the request that filled the cache is sent to
every guest that gets a HIT:

- Chevereto `/explore`: two fresh clients received the same `PHPSESSID`.
  A login made with that shared session id did **not** log in a second
  client that held the same id (Chevereto authenticates with `KEEP_LOGIN`),
  but all guests share one PHP session and therefore one `auth_token`.
- XenForo: the same `xf_csrf` cookie was returned on MISS and HIT. XenForo's
  own `XF.KeepAlive` refreshes the token when the cookie is absent, which is
  how its built-in guest page cache works without a cookie.

Not changed in this release: hiding `Set-Cookie` only on cacheable guest
requests needs the PHP location split into a cached and an uncached branch,
which changes every deployed vhost. It is a decision for the config repo's
owner.
