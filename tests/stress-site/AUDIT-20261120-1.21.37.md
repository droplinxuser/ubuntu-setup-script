## 2. Guest-cache throughput and Anubis

`oha -c 100`, cached home page (Chevereto `/explore`; its `/` is dynamic by
design), 100% success:

| Tier | Anubis off | Anubis on (valid cookie, browser UA) |
|---|---:|---:|
| XenForo guest | 84,472 | 27,729 |
| WordPress guest | 83,461 | — |
| Chevereto guest | 110,315 | — |

`c=400` does not raise the Anubis number (28,512), so the filter is
CPU-bound, not latency-bound: during the run Anubis holds ~5.2 cores and
Angie ~3.4 (TLS terminator + application vhost), and the host is at 94 %.
Removing Anubis gives 80,501 req/s with the same cookie: **the filter costs
about 65 % of cache-hit throughput on this CPU**.  That is the price of
validating every request, not a misconfiguration.

Tuning probes on the filter (valid cookie, check endpoint, TCP-bound to
measure it directly): `GOGC=100` 66.5k, `GOGC=400` 73.0k, `GOGC=800` 74.5k,
`GOGC=off` 74.7k (RSS 107 MB at 800 vs 2.0 GB at off + 2 GiB limit);
`GOMEMLIMIT=4096MiB` is not faster than 2048 MiB.  The shipped
`GOGC=off GOMEMLIMIT=2048MiB GOMAXPROCS=8` is at the ceiling; raising the
limit to 8 GiB only inflates RSS to 7.9 GB.  No change.

**Subrequest-auth mode was prototyped and rejected.**  Anubis 1.28.2
supports `TARGET=" "` plus `auth_request` (the official nginx recipe), which
removes the response-body copy.  Measured on the same vhost: 19.8k req/s
without upstream keepalive and 28.5k with `keepalive 64` +
`proxy_http_version 1.1` (the shipped proxy mode is 27.7-28.5k).  The saved
body copy is offset by the extra subrequest pass and the extra Anubis
connection state, so the proxy architecture stays.  The prototype also
showed that `location /.within.website/` must be `^~`, or the application's
dotfile deny regex wins and the challenge page answers 403.

## 4. Bug fixed: losing the Anubis state left every site down

`anubis=no` restores the vhosts from `$STATE_DIR/anubis/vhosts/*.orig` and
recognized "Anubis is managed" only by the marker inside that same state
directory.  If the directory was moved or removed by hand, the marker was
gone, so `--optimize anubis=no` did nothing — while a plain `--optimize`
also ignored the integration.  Once the filter was stopped (manual or by
`--purge angie`) every vhost still listened on
`unix:/run/angie/anubis-backend.sock` and answered 502.

Fix:

* `anubis_artifacts_present` recognizes this module's own terminators,
  common snippet, static shadow and integrated vhosts, so the integration is
  visible without the marker;
* `anubis_deintegrate_vhost` rebuilds the public listener from the
  integrated form (two `listen 443 ssl`, `http2 on`, the two real-IP lines
  removed, everything else untouched) when an `.orig` copy is missing;
* `anubis_restore_vhosts` runs that fallback and returns non-zero if a
  vhost still cannot be rebuilt; `anubis_disable` then keeps the filter
  running and reports the failure instead of a false success.

Verified on the host by enabling the filter, moving
`/var/lib/setup.sh/anubis` away and running `--optimize anubis=no`:
three vhosts rebuilt, `angie -t` clean, the service stopped, HTTP 200, and
the next `--optimize` is a no-op.  13 unit checks cover the transform,
the idempotence and the artifact detection (1,119 total).

## 6. Open items

* PHP 8.6.0: unchanged from 1.21.36 — `php8.6-redis`/`-imagick` still
  unpublished and PECL does not compile.
* XenForo responses carry `X-Content-Type-Options` twice: `php_xf.conf`
  and `basic_xf_headers.conf` both add it at server level.  Values are
  identical and browsers ignore the duplicate; folding the header sets is a
  cosmetic cleanup for the Angie repo.
* Anubis is the dominant cost on a cache-hit-heavy host (section 2).  A host
  that needs >30k guest hits/s should run it only in front of the dynamic
  locations or accept the trade-off; the tool keeps the filter off unless
  `anubis=yes` is asked for.

Restore: `--purge all`, then the added packages, web roots, databases and
service state removed; reboot into the 695-package baseline.
