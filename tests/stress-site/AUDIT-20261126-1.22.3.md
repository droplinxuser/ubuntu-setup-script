# Audit — 1.22.3 (migrating deb-package hosts: Sury PHP 8.1-8.6, Ubuntu 24.04)

Date: 2026-11-26
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe, Ubuntu
26.04.1, kernel 7.0); KVM guests on the same host for the other replicas.
Pair: `server-configs-nginx` 1.7.3 (branch `main`, unchanged this cycle).

## 1. Scope

Primary focus (operator request): the source-built nginx, PHP and Valkey
must be safe to run on the live hosts that still use the deb packages, and
`--optimize` must migrate hosts on Sury PHP 8.1 to 8.6.  Secondary: lean,
performance, security on the current hardware.

What was known before the cycle: 1.22.0 had migrated one host shape only
(Ubuntu 26.04, Angie package, Sury PHP 8.5, valkey-server package).  The
live hosts include Ubuntu 24.04 machines, and nothing had exercised the
other PHP series, a second running PHP version, or a small Angie-only
proxy.

## 2. Method

* Pristine baseline recorded first (701 packages: the 695 of the last
  report plus the six 7.0.0-44 kernel packages the host booted on, installed
  by the OS during the previous cycle; no leftovers of the tests).
* Two read-only code reviews (Sury 8.1-8.6 migration; Ubuntu 24.04
  compatibility) produced the hypotheses; each was then checked on a host.
* Replicas built with the 1.21.71 installer (the last 1.21 release:
  Angie package, `packages.sury.org` PHP, valkey-server package, the three
  applications), then `setup.sh --optimize` of this tree:

  | Replica | Where | Shape |
  |---|---|---|
  | M1 | bare metal, 26.04 | PHP 8.5 active + Sury 8.3 running with its own vhost, Elasticsearch, an operator `/usr/bin/php8.5` cron line |
  | noble | KVM 8 vCPU/16 GB, Ubuntu 24.04 | PHP 8.3, Valkey 7.2.14 package (the live 24.04 hosts' shape) |
  | r81, r82, r84 | KVM 4 vCPU/8 GB, 26.04 | single Sury 8.1 / 8.2 / 8.4 (8.1 without Chevereto, which needs 8.2) |
  | r86 | KVM 4 vCPU/8 GB, 26.04 | Sury 8.6 moved to by hand from 8.5 (1.21.71 cannot configure 8.6), 8.5 left installed but stopped |
  | rpx | KVM 2 vCPU/3.8 GB, 26.04 | Angie only: an operator `upstream` + `proxy_pass` vhost (the fleet proxies' shape) |
  | M2 | bare metal, 26.04 | PHP 8.5 + Elasticsearch, used for the before/after benchmark |

* After each migration: the functional walk (`exercise-apps.sh`), the
  security probe, the guest-cache cookie suite, journal and segfault checks,
  a reboot where noted, and a second `--optimize`.
* Benchmark (section 5): the same host before and after the migration, 5
  rounds of the 12 built-in loopback tiers each (`wrk -c100`, 10 s), clock
  pinned at 3.6 GHz, `mitigations=off`, a reboot before each arm.

## 3. Findings fixed

### 3.1 Cron ran Sury's PHP without its extensions (high)
At the PHP cutover the migration moves Sury's `cli/conf.d` links away and
writes our `php.ini`, but `/usr/bin/phpX.Y` (and `/usr/bin/php` through the
alternatives link) stayed Sury's binary until the purge.  On M1 the Sury
purge is deferred (8.3 still runs), so the window never closes: the diverted
Sury binary loads 2 of the 7 application extensions against the converted
tree, and setup.sh's own every-minute `wp-cron.php` and `xf:run-jobs` jobs
call `/usr/bin/php`.  Fix: the cutover diverts `/usr/bin/phpX.Y`
(`dpkg-divert --local` to `phpX.Y.sury`) and links our CLI in its place;
rollback and post-purge handle the record; the version's Sury packages are
held until the purge.  Verified on M1 (`/usr/bin/php8.5` -> source CLI with
every extension, 8.3 untouched) and on every single-version replica (no
diversion left after the purge).  `setup.sh --purge` and
`restore-baseline.sh` take a leftover diversion back (found when the
restored host reinstalled `php8.5-cli` into `/usr/bin/php8.5.sury`).

### 3.2 Valkey did not build on Ubuntu 24.04 (high for the 24.04 hosts)
glibc 2.39 defines `sprintf` as a fortify macro for clang; Valkey's Lua
module includes `fmacros.h`, which re-declares `sprintf`, after
`<stdio.h>` ("expected parameter declarator").  The 26.04 glibc fortifies
without the macro, so the bug never showed there.  The migration kept the
package serving (safe), but the host stayed half-migrated.  Fix: the
re-declaration is skipped where `sprintf` is a macro.  Verified: Valkey
9.2.0 built and replaced the 7.2.14 package on the noble replica.

### 3.3 PHP JIT sizes not a whole number of 2 MB (high for ~8 GB hosts)
RAM/16 gives a 495 MB OPcache on an 8 GB host and RAM/16/8 a 61 MB JIT
buffer.  With huge code pages that pair leaves the JIT region unaligned:

| | 495/61 | 495/60 | 496/61 | 494/60 |
|---|---|---|---|---|
| PHP 8.1 build, 40 rounds of 5 PHP pages | 10 segfaults, 200 x 502 | 0 | 0 | 0 |
| PHP 8.6 build, `php-fpm -t` x 30 | 30 x `mprotect() failed [22]` | 0 | - | 0 |

8.5 accepts either; Sury's 8.1, 8.2, 8.4 and 8.6 packages fail the same way
(the 1.21 replicas of those series served 502 until the sizes were made
even).  Fix: both sizes round down to whole 2 MB (494/60).  Hosts of 16 GB
and more were already at 512/64 and do not change; the live PHP hosts are
32-64 GB.

### 3.4 A failed PHP reload was reported as OK (high)
On r86 the tuner wrote the 61 MB buffer, its single `php-fpm -t` passed
(the per-path JIT sections it was missing came with the later refresh),
`systemctl reload` returned success, and the re-executed master exited:
"Reload: OK", PHP down.  Fixes: reloads confirm the master survived for
~3 s; a refresh that rolls back restarts the pool from the restored files;
a unit that had *failed* (not one the operator stopped) is started again
once the tuned configuration passes `php-fpm -t`, and a recovered start
with a current build does not fail the run.  Verified by forcing the bad
size on r86: the next `--optimize` ended SUCCESS with PHP serving.

### 3.5 Unbuildable PHP series and the active version (medium)
PHP 8.0 or an unreleased series (a Sury RC) was built, failed and retried on
every run, and an idle RC could become the active version.  Now refused in
the pre-flight (retried when php.net releases the series); the active
version is chosen among buildable series, by Angie's `local_php`, then by
the vhosts' `fastcgi_pass` references, then the newest.

### 3.6 PHP 8.6 and PECL (medium)
8.6 removed compatibility aliases (`zval_dtor`, `zval_is_true`,
`XtOffsetOf`, `INI_STR`/`INI_INT`, `WRONG_PARAM_COUNT`,
`php_hash_bin2hex`, ...) and made `unserialize_callback_func` a zend_string.
The build restores each alias the tree no longer defines and adapts
igbinary: igbinary 3.2.16 builds on 8.6.  phpredis 6.3.0 still fails (its
session handler uses the `PS()` fields 8.6 changed; a real port, not an
alias), so redis has a series ceiling of 8.5.  On r86 with Chevereto and a
XenForo Redis cache the migration refuses 8.6 in the pre-flight in 2 s with
that reason (Sury keeps serving); with neither, 8.6 migrated, and redis
kept only by `PHP_EXT_EXTRA` from the 8.5 era is left out with a warning.
The refusal's scan digest now includes the applications' requirements, so
removing the application retries it without `SETUP_MIGRATE_RETRY`.

### 3.7 Smaller fixes
* Operator edits to Sury's `php.ini` survive as
  `conf.d/10-migrated-php-ini.ini`.
* Report noise: the leftover-Angie scan listed every log, note, backup and
  checkout under `/root` (it buried the one real line); a host without PHP
  warned about a dead `local_php`; the migration's `nginx -t` trials wrote
  their expected `[emerg]` lines into the live error.log (now `-e stderr`);
  crontab lines are listed with the PHP each one will run.
* The PHP BOLT pass uses a working `perf` instead of always installing
  `linux-tools-$(uname -r)`.
* `restore-baseline.sh` releases holds on added packages before purging and
  re-enables the baseline's units that `--purge` disabled (sysstat).

## 5. Benchmark: what the migration buys

M2, same host and harness, before (Angie 1.12.5 package + Sury PHP 8.5.13)
and after (nginx 1.31.10 + PHP 8.5.13 + Valkey 9.2.0 from source, ThinLTO +
BOLT).  Medians of 5 rounds, req/s (spread = min-max as % of the median),
p99 and PHP-FPM CPU ms per request:

| Tier | Before | After | Δ req/s | p99 before → after | PHP ms/req |
|---|---:|---:|---:|---|---|
| WP guest home (cached) | 99,561 (0.4 %) | 113,001 (0.5 %) | +13.5 % | 1.68 → 1.61 ms | - |
| WP guest post (cached) | 95,215 (0.3 %) | 107,288 (0.3 %) | +12.7 % | 1.79 → 1.66 ms | - |
| WP member home | 141 (1.4 %) | 152 (0.7 %) | +7.8 % | 1,140 → 1,090 ms | 76.4 → 70.5 |
| WP member post | 138 (10.9 %) | 143 (0.7 %) | +3.6 % (noise) | 1,180 → 1,130 ms | 80.4 → 77.5 |
| XF guest home (cached) | 139,936 (0.2 %) | 158,028 (4.3 %) | +12.9 % | 1.11 → 0.86 ms | - |
| XF guest thread (cached) | 128,373 (0.3 %) | 153,066 (1.2 %) | +19.2 % | 1.10 → 1.01 ms | - |
| XF member home | 448 (0.9 %) | 492 (4.7 %) | +9.8 % | 269 → 235 ms | 21.0 → 18.7 |
| XF member thread | 256 (0.0 %) | 263 (0.8 %) | +2.7 % (noise) | 566 → 543 ms | 39.4 → 38.1 |
| Chev guest explore (cached) | 135,272 (0.4 %) | 154,370 (2.3 %) | +14.1 % | 1.05 → 0.95 ms | - |
| Chev guest image (cached) | 132,602 (0.4 %) | 151,190 (4.2 %) | +14.0 % | 1.15 → 0.93 ms | - |

Verdict: the migrated stack serves cached pages 13-19 % faster and the
PHP-rendered pages 8-14 % faster where the change is outside the spread
(PHP CPU per request -8 to -14 %); three tiers move within the noise.  One
regression: the Chevereto member-explore p99 rose from 150 to 207 ms while
its median throughput tied (a 1.6-core tier that is lock-bound in MariaDB;
not investigated further this cycle).  Confound: the arms are sequential
(a one-way migration cannot be interleaved), so the clock was pinned and
both arms followed a reboot; the before arm's CPU attribution has no nginx
column (the analyzer keys on the unit name).

Final PHP parameters on this host (62 GB, 12 threads): OPcache 512 MB,
tracing JIT with a 64 MB buffer, huge code pages on, hot counters
64/127/16/64; `pm = static`, 12 children, `max_requests` 12288,
`listen.backlog` 49152.  Per-app maximum PHP version: WordPress 8.6,
XenForo 8.6 (without a Redis cache, until phpredis supports 8.6), Chevereto
8.5 (needs redis).  Default stays 8.5.

## 6. Upstream and host items (listed, not ours)
* XenForo 2.3.13 core `E_DEPRECATED` on PHP 8.5 (null array offset); under
  `compat-php.sh`'s debug mode it turns the reply and search POSTs into 500.
  Lint of an unused vendor library (Braintree) reports a parse error.
* The 1.21.71 installer cannot configure Sury 8.6 (its own JIT settings hit
  3.3); no live host runs 8.6.

## 7. Open items
* Multi-version hosts: a second running PHP version stays on Sury by design
  (one active version).  Supporting several active source builds would need
  the build/start logic to stop disabling the others; ask before changing.
* phpredis on 8.6: lift the ceiling when a release builds.
* Valkey on a persisting host stays on its package's series (7.2 on
  24.04); a newer server loads an older RDB, so this could allow upgrades.
* The Chevereto member-explore p99 (section 5).
