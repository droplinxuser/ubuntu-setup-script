# Audit — 1.21.33 (Ubuntu 26.04.1, Angie 1.12.4, PHP 8.4/8.5/8.6)

Date: 2026-11-19
Host: OVH dedicated server — Intel Xeon E-2236 (Coffee Lake, 6C/12T,
3.4 GHz base, 4.2–4.5 GHz all-core under load), 62 GB RAM, two Samsung
PM983 960 GB NVMe (root on md RAID0 `md3`, swap on two partitions), BMC
virtual floppy/CD-ROM devices, public IPv4 + IPv6, bare metal, Ubuntu 26.04.1
(kernel 7.0.0-43).  Pristine baseline: **705 packages**, UFW inactive,
timezone UTC, no `/etc/angie`, `/etc/php`, `/var/www`.
Pair: `server-configs-nginx` **1.6.46**.

This was the first run on Intel and on md RAID.  Most findings are specific
to that hardware class.

## 1. Code audit

A five-dimension review (Angie security, install/`--optimize` parity,
hardware auto-tuning, robustness, Angie/cache/Anubis performance) was run by
independent reviewers.  An adversarial verifier then re-checked every
finding against the code.  Eleven findings were confirmed (one medium, ten
low).  Running on the host surfaced six more.  All of them are fixed in this
release; see `CHANGELOG.md` 1.21.33.

| Severity | Area | Finding |
|---|---|---|
| medium | Angie (1.6.43–1.6.45) | `if ($flarum_guest_cacheable$req_encoded_path)` made `angie -t` fail for every Flarum vhost |
| medium | `--upgrade-php` | one apt transaction per optional extension hit systemd's start limit; `php8.4-imagick` (Chevereto hard requirement) was rolled back with only a warning |
| medium | `--basic` | needrestart's APT hook ran while PID 1 re-executed after a systemd upgrade; 16 daemons stayed on the old libc |
| low | security | catch-all 443 server sent a certificate naming the host to no-SNI scanners |
| low | tuning | md/dm readahead stayed at the stripe-derived 2048 kB (root on md3) |
| low | tuning | `lsblk -s` tree parse classified only the last RAID member |
| low | tuning | OPcache file count rewrote the ini (and reset OPcache) on every template compile |
| low | Anubis | backend/static Unix sockets kept the 511 backlog; large responses spooled to `proxy_temp` |
| low | Angie | Flarum cache had no background update |
| low | zero-warning | udev re-trigger replayed BMC virtual devices through sg3-utils (5 warnings per `--optimize`) |
| low | zero-warning | Ubuntu 26.04 `mariadbd` AppArmor profile denied MariaDB's sysfs reads (21 `DENIED` per install) |
| low | `--purge` | `--purge others` disabled the sysstat timers Ubuntu ships enabled |
| low | robustness | Sury keyring via bare `dpkg -i` (no lock wait); fleet-update could leave an empty checkout; missing lock timeouts |
| low | tests | seeder exit 1 (`authors=` unused); cookie suite did not follow SV/StandardLib's POST log-out |

Rejected or deliberate (not changed): `--optimize` recomputes Elasticsearch,
MariaDB and Valkey sizes from live data and drops install-time `ram=`/`size=`
(1.21.32 design).  The audit host's explicit `ram=4g` became a 512 MB heap
for an empty index.

## 5. Performance — the published XenForo 2.3.13 benchmark

The tiers of the published XenForo 2.3.13 web-stack benchmark (xenforo.com
thread 241386 and its Ubuntu-vs-CentMinMod follow-up) were reproduced with
`tests/bench-php-matrix/bench-thread-tiers.sh`.  The method matches the
published one: loopback HTTPS, `wrk -t4 -c100 -d10s`, 2 s warm-up,
`Accept-Encoding: gzip`, the median 9-post thread (127.5 KB), and oha for
Anubis tiers.  Raw rows: `tests/bench-php-matrix/results/xeon-e2236/thread-bench.tsv`.

| Tier | Published best (EPYC 4245P, Zen 5) | This host (Xeon E-2236) |
|---|---:|---:|
| Guest cached (S3) | 390,232 | 128,058 first run, ~104,000 steady |
| Guest cached + Anubis (S4) | 68,725 | 27,753 |
| Guest bypass | 819 | 374 |
| Member home | 747 | 317 |
| Member thread (9 posts) | 838 | 341–368 |

The published numbers were **not** beaten on this host.  The gap is the CPU,
not the configuration:

* **Member tiers are 95% user-space PHP.**  PHP-FPM used 11.0 of 12 cores,
  10.5 of them in user space; MariaDB 1.0, Valkey 0.07, Angie 0.1.  Zen 5 at
  5.5 GHz against Coffee Lake at 4.2–4.5 GHz all-core accounts for the
  ~2.3× difference.
* **The cached tier is two-thirds kernel, TLS and the load generator.**
  Angie used 7.7 cores (2.5 of them kernel) and wrk the rest.  Coffee Lake
  runs with Meltdown PTI and kernel IBRS (Spectre v2 and Retbleed) and has no
  VAES.  Every syscall and every AES-GCM record costs several times more than
  on Zen 5, which needs none of these mitigations.  No thermal throttling was
  recorded (0 package/core throttle events).  The first run after idle
  benefits from the PL2 turbo window (128k vs ~104k steady).
* Disabling the CPU mitigations would narrow the cached-tier gap.  It was
  **not** done or measured: it is a security downgrade on an
  internet-facing host and an operator decision.

Experiments on this host (interleaved, steady state):

| Change | Result | Decision |
|---|---|---|
| kTLS (`ssl_conf_command Options KTLS`, `tls` module; TX offload confirmed by `TlsTxSw`) | 91–97k vs 102–104k cached | rejected: in-kernel AES-GCM costs more than the copy it saves on a 15.6 KB page |
| Angie workers 6/10/12 vs 8 | 6: 90–92k, 10: 89–93k (p99 ×3), 12: 85–88k | 2/3 of CPUs (8) stays best |
| regex/map cost on the cached path | PCRE2 + map lookups ≈5% of samples | not worth restructuring |
| XenForo gzip: guests level 9 (XF), members via Angie gzip level 4 (`$config['enableGzip'] = !isset($_COOKIE['xf_session'])`) | +2–4% bypass/home/thread, p99 −5…−25% | documented, not automated (edits application config) |

Where the member time goes: XenForo core compresses every response with
`gzencode($body, 9)`.  That is 15% of PHP CPU on the member thread tier: 3.3 ms
per 128 KB page at level 9, against 1.7 ms at level 6 for a 0.6% larger body.
The split above keeps level 9 for cacheable guest pages and moves member
compression to Angie at level 4.

### Optimal PHP parameters (unchanged; re-confirmed on Intel)

| Parameter | Value |
