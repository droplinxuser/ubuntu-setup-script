# Audit — 1.21.63 (XenForo logged-in throughput)

Date: 2026-11-23
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe,
Ubuntu 26.04.1, kernel 7.0.0-43), verified against its pristine manifest
(696 packages) before the install and restored afterwards.  CPU mitigations
were **off** for every number below (operator request; a test-host-only GRUB
drop-in, removed at restore; `/sys/.../vulnerabilities/*` read
"Vulnerable").  Pair: `server-configs-nginx` 1.6.56.  Applications:
WordPress 7.1.4, XenForo 2.3.13 (200 threads / 2,600 posts / 60 users),
Chevereto 4.5.9-pro on PHP 8.5, deployed with `deploy-three-apps.sh`.

Primary focus: more requests per second and lower latency for uncached /
logged-in XenForo pages, shipped in a way that reaches a new install and an
existing host (`--optimize`) alike.

## 1. Where a member page spends its time

`loopback-tiers.sh` baseline (3 passes, c=100, 10 s, unpinned clock):
XenForo member home 492 req/s (p99 229-243 ms), member thread 265-267 req/s
(p99 559-575 ms).  Per-service CPU on the member thread (cgroup delta per
request):

| Service | ms per request | share |
|---|---:|---:|
| php-fpm | 36.9 | 92 % |
| mariadbd | 2.4 | 6 % |
| angie (TLS + compression) | 0.28 | 0.7 % |
| valkey | 0.22 | 0.5 % |

`perf record -a` during the same load, by shared object: **libz 12.0 % of all
samples, all of it in php-fpm** (`crc32_z` among the symbols), the PHP binary
itself (shown as `[JIT] tid` because `opcache.huge_code_pages` remaps its text
to anonymous huge pages) ~62 %, MariaDB 4.9 %, libc 4.3 %, kernel 3.2 %.

The zlib time is XenForo's own page compression.  XenForo gzips every page at
level 9 whenever the request's `Accept-Encoding` names gzip, and the
uncached Angie handler (`h5bp/php_xf_handler.conf`) passed the client's
header straight to PHP.  Verified on the live vhost with a member cookie:

```
Accept-Encoding: gzip, br             -> content-encoding: gzip  (XenForo)
Accept-Encoding: br, gzip (Cloudflare) -> content-encoding: gzip  (XenForo)
Accept-Encoding: br                   -> content-encoding: br    (Angie)
```

1.21.36 had measured the fix (guests keep XenForo's gzip for the cache,
members get Angie compression) but shipped it as a managed block in each
forum's `src/config.php` that only `--optimize` writes.  A forum installed
after the server — the normal order, and what this cycle's deployment did —
ran XenForo's level-9 gzip for every member until the next `--optimize`.

## 2. The fix (primary focus)

`server-configs-nginx` 1.6.56, `h5bp/php_xf_handler.conf`:

```nginx
include snippets/fastcgi-php-noinfo.conf;
fastcgi_param HTTP_PROXY "";
fastcgi_param HTTP_ACCEPT_ENCODING "";
```

The uncached handler serves members, guest bypass, `admin.php` and
`job.php`.  PHP now sees no `Accept-Encoding` (a probe script printed
`NULL`), sends plain HTML, and Angie compresses it with the shipped Brotli /
gzip level 4.  The guest-cache location (`@xf_guest_cache` in
`php_xf.conf`) still passes the cache key's encoding (`$guest_cache_ae`), so
the stored body is still XenForo's gzip and a hit is never compressed again.
The tree is rsynced by both a fresh `--angie` install and `--optimize`
(`lib/web.sh`), so one file gives parity with no new code path.  The
`src/config.php` block stays as a second guard for hosts on an older tree.

Angie spends ~2 ms more per thread page on Brotli 4, but outside the PHP
pool and at a fraction of XenForo's level-9 cost: −10 % CPU for the whole
server per thread page, −17 % inside PHP.  Response sizes for the member
thread: XenForo gzip 9 17.6 KB, Angie Brotli 4 17.1 KB (Cloudflare and
browsers), Angie gzip 4 19.4 KB (gzip-only clients).  Every other tier is
inside its spread: the guest cache path did not change.

**Verdict on the primary focus:** the only large lever left on the
logged-in XenForo path that the server owns was compression in the PHP
worker; moving it to Angie gives +5 % (home) / +9 % (thread) req/s and a
lower p99, and it now applies from the first request of a new install.
What remains is XenForo's own PHP work (≈ 35 ms per thread page at 3.6 GHz,
≈ 27 ms at 4.5 GHz), which the server cannot shrink further without changing
the application (sections 3.2-3.4).

## 3. Measured and not shipped

### 3.1 The clock is the biggest source of noise on this host

Mid-cycle, a php-fpm restart appeared to add 16-27 % to the member tiers.
It was the CPU: turbo on the E-2236 is power-limited (RAPL PL2 112 W for the
turbo window, then PL1 80 W), not thermal (throttle counters 0, package
35 °C).  One XenForo member-thread run per line, identical configuration:

| Run | req/s | mean MHz | php-fpm ms/req |
|---|---:|---:|---:|
| steady 1 | 350 | 4500 | 27.4 |
| steady 2 | 347 | 4500 | 27.5 |
| after Angie reload | 356 | 4499 | 27.3 |
| next run | 326 | 4100 | 30.0 |
| after php-fpm reload | 332 | 4099 | 29.4 |
| next run | 324 | 4099 | 30.1 |

PHP CPU per request follows the clock 1:1 (4500/4100 = 1.10 =
30.0/27.4).  The hung huge-page rounds (3.2) left the host idle, which gave
the next variant a fresh turbo budget; the same effect explains the
"first slot wins" bias noted in 1.21.58.  `tests/stress-site/set-clock.sh
3600` pins `scaling_max_freq` below the sustained all-core clock (sysfs
only, a reboot restores it); at 3.6 GHz two consecutive runs gave 285 and
286 req/s.  `loopback-tiers.sh` now prints the mean clock and compact
per-service ms/request on every row.

### 3.2 Zend heap on transparent huge pages — rejected

THP is `madvise` on every setup.sh host, so `USE_ZEND_ALLOC_HUGE_PAGES=1`
(a php-fpm systemd drop-in) would put only PHP's request heap on 2 MB pages.
A single request answered 200, but under 100 connections the pool stopped
answering: 5 req/s for member home, 0 for the thread, 60 timeouts, in all
three rounds; `AnonHugePages` stayed 0.  Not shipped.

### 3.3 PHP-FPM workers — 12 stays

`set-fpm.sh` 12 / 15 / 18 workers, rotated, after the handover:
member home 580 / 577 / 580, member thread 336 / 334 / 337 req/s (unpinned,
all inside the spread).  The host runs 10.9-11.3 busy cores at 12 workers;
extra workers only queue.

### 3.4 Brotli level for dynamic HTML — default stays 4

With the handover, Brotli runs on every member page, so the level matters.
Rotated, 3 rounds, unpinned clock:

| Level | member home | member thread | Angie ms / thread page | thread size |
|---|---:|---:|---:|---:|
| 1 | 541 | 296 | 0.82 | 23.9 KB |
| 2 | 527 | 291 | 1.26 | 18.4 KB |
| 3 | 521 | 290 | 1.37 | 17.9 KB |
| 4 (shipped) | 510 | 285 | 2.05 | 17.1 KB |

Level 1 gains 4-6 % for 40 % more bytes to every direct client; 2 and 3 are
inside the noise.  The default stays; the README gives these numbers for
`SETUP_BROTLI_LEVEL` (an origin whose only client is Cloudflare can take 1).

### 3.5 Other observations

* The JIT works (a 20M-iteration loop runs at JIT speed, 0.27 s) and
  XenForo needs < 1 MB of the 64 MB buffer; `opcache_get_status()` reports
  the buffer as essentially free.  Not changed (32 and 64 MB measured equal
  in earlier cycles).
* WordPress also compresses member pages in PHP (`zlib.output_compression`
  level 6, per root); 1.21.58 measured moving that to Angie as no gain
  (WordPress spends ~98 ms of PHP per member page), so it stays.

### 4.1 Restore

`restore-baseline.sh` (run from a copy outside `/root/work`), then
`/root/audit`, `/root/work` and `/root/.debug` deleted, the audit GRUB
drop-in removed, reboot, `host-manifest.sh` against the pre-install
baseline: **696 -> 696 packages (none added, removed or version-changed),
0 `/etc` files added, removed or changed**, no non-volatile sysctl
difference, kernel back to its default mitigations, `/root`,
`/home/ubuntu`, `/etc/hosts`, hostname and timezone as recorded.  The first
pass left `/swapfile` and its fstab line: `--purge` keeps a managed swap
file on purpose (switching swap off can OOM a live host), so
`restore-baseline.sh` now removes it when the baseline had none.
