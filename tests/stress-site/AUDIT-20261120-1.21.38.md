# Audit — 1.21.38 cycle (Ubuntu 26.04.1, Angie 1.12.4, PHP 8.5)

Date: 2026-11-20
Host: OVH dedicated server, Intel Xeon E-2236 (Coffee Lake, 6C/12T), 62 GB,
md RAID0 over two PM983 NVMe, Ubuntu 26.04.1, kernel 7.0.0-43, 695-package
baseline.
Pair: `server-configs-nginx` **1.6.49**.
Applications: WordPress 7.1.4, XenForo 2.3.13 (Hampel Seeder 1.0.0b11:
20,060 users, 10,200 threads, 103,001 posts; SV RedisCache/FloodCheck/
ViewCounter/StandardLib), Chevereto 4.5.9-pro, all on PHP 8.5.13.

Method: loopback HTTPS with `wrk` (`loopback-tiers.sh`, c=100, 10 s, 2 s
warm-up, `Accept-Encoding: gzip, br`), guest tiers served from the FastCGI
guest cache.

## 1. The host was not pristine

The 1.21.37 restore left `/var/lib/mariadb` (including a `chevereto`
database), the `angie` and `mysql` accounts, `/usr/local/bin/mysqlbkup.sh`,
`/etc/mysqlbkup.*`, `/root/mysqltuner.pl`, `/root/tools` and `/root/.debug`
behind.  The package count was the baseline's 695, and the manifest did not
list data directories or `/root`, so the residue was invisible.  The first
install of this cycle ran on the old datadir and the MariaDB postinst logged
"mysql.user table already exists! Run mariadb-upgrade".

Fix (`tests/deploy-audit/`): `host-manifest.sh` lists the top level of
`/root` and of every service data/cache/log directory; `restore-baseline.sh`
also removes `/root/.debug` and the benchmark binaries.  The host was
restored, a new baseline recorded and the install repeated.

## 3. Header defects fixed (server-configs-nginx 1.6.49)

### 3.1 XenForo passkeys

Reported by the operator from production: on `/login/two-step` the "Use
passkey or security key" button did nothing.  The shared
`$permissions_policy` map in `angie.conf` sent
`publickey-credentials-get=()`, which denies WebAuthn
(`navigator.credentials.get()`) to the page itself.  XenForo did not send
the header until 1.6.35 (`48545e6`, 2026-11-16), when the PHP handlers
re-included `permissions-policy.conf` to restore the security headers that a
location-level `add_header` drops.  The token is now `(self)`.

| URL | before | after |
|---|---|---|
| xf `/login/` | `publickey-credentials-get=()` | `(self)` |
| xf `/login/two-step` | `()` | `(self)` |
| wp `/wp-login.php` | `()` | `(self)` |

A browser passkey ceremony was not run (no authenticator on the audit
host); the policy is the only thing that blocked the call.

### 3.2 Duplicate security headers

| Response | Duplicated header | Source of the second copy |
|---|---|---|
| XenForo pages, `css.php`, 404, admin | `X-Content-Type-Options` | `XF\Mvc\Renderer\AbstractRenderer` (also Proxy and Oembed controllers) |
| WordPress `wp-login.php` | `X-Frame-Options`, `Referrer-Policy` | WordPress core |
| WordPress REST API | `X-Content-Type-Options` | WordPress REST server |
| Chevereto pages | `Permissions-Policy` (`interest-cohort=()`) | Chevereto |

The PHP handlers hide the upstream copy (`fastcgi_hide_header`).  A/B on the
XenForo login page: 2 copies with the hide line commented out, 1 with it.
PHP's own two `Cache-Control` lines on `job.php` (session cache limiter) and
separate `Vary` lines are legitimate and left alone.

Probe: `security-probe.sh` checks each security header appears once on
eight URLs and that the passkey policy allows the site on three: **65/65**.

## 4. Anubis: validated-pass cache investigated, rejected

Goal: skip the Go hop for a visitor whose challenge cookie Anubis has
already validated, by caching a per-cookie "pass" in Angie in front of the
check endpoint.  Probing `/.within.website/x/cmd/anubis/api/check` on the
running proxy-mode instance (1.28.2):

| Client | Answer |
|---|---|
| Browser UA + valid cookie | 401 (the page itself is 200 through the proxy) |
| No/garbage cookie | 401 |
| `curl` (default-allowed) | 403: ALLOW proxies the check URI itself to the origin, which denies the dotfile path |
| GPTBot (DENY) | **200** with the "Oh noes!" page (Anubis's default DENY status) |

A cache over this endpoint would let denied crawlers through and pass no one
else.  Doing it correctly needs a second Anubis instance in auth mode
(`TARGET=" "`) with a DENY status override and the challenge routed via
`error_page` — the 1.21.37 prototype of that mode measured no win without a
cache.  Rejected as not lean.  The shipped proxy mode with the static-asset
shadow stays.

## 5. Load tiers and CPU mitigations

Anubis off.  Three boots: stock kernel, `mitigations=off` (the shipped
opt-in), and `mitigations=off init_on_alloc=0 randomize_kstack_offset=off
preempt=none` (audit-only drop-in).  Two rounds per boot (round ranges):

| Tier | stock | mitigations=off | + extra flags |
|---|---:|---:|---:|
| WP guest home (cached) | 79,330-79,727 | 111,538-121,570 | 114,669-116,602 |
| XF guest home (cached) | 101,066-120,717 | 107,482-114,394 | 109,658-112,526 |
| Chev explore (cached) | 123,844-123,905 | 133,368-133,832 | 135,613-136,963 |
| XF member thread | 255-258 | 294-296 | 292-294 |
| WP member home | 170 | 153-168 | 156-171 |
| Chev home (uncached) | 1,549-1,559 | 1,778-1,798 | 1,795-1,801 |

* `mitigations=off`: +8-50 % on cached tiers (XF guest is inside its own
  noise), +15 % on XF member and Chevereto uncached.
* `init_on_alloc=0` + `randomize_kstack_offset=off`: within run-to-run
  noise (Chevereto explore +1.5-2 % at best).  Not worth weakening the
  kernel's memory hardening; not offered.
* `preempt=none`: rejected by the 7.0 kernel ("Dynamic Preempt: unsupported
  mode: none"); the kernel already runs the throughput-oriented `lazy`
  model.
* Not tested, by design: `nosmt` (halves the threads), disabling
  AppArmor/audit (security, negligible per-request cost here), `tsx=on`
  (no lock-elision user in this stack).

Anubis on (stock kernel, non-browser UA, so every request takes the Go hop):
WP guest 26.3-26.8k, XF guest 30.5-30.8k, Chevereto 28.6-28.8k; member
tiers unchanged from Anubis off (166/147 WP, 246/248 XF).

Notes: WordPress member pages are CPU-bound at 43 ms per request (OPcache
99.97 % hit rate, JIT on); `Chev member explore` completes ~6 req/s because
every wrk connection shares one PHP session and session locking serializes
them — a harness artifact, not a server limit.
