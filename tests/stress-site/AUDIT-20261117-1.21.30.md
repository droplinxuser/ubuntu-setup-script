## 6. PHP compatibility matrix

Lint pass over every PHP file with `error_reporting=-1`, plus a run-time pass
with each app in its own debug/E_ALL mode.  Counts are deprecation notices in
**vendor** code, not fatals.

| PHP | WordPress | XenForo | Chevereto | Run-time |
|---|---:|---:|---:|---|
| 8.4.27 | 18 | 56 | 480 | 0 unexpected responses |
| 8.5.12 | 18 | 60 | 481 | 2 unexpected on 8.5 in XF debug mode (`xf reply POST`, `xf search POST` → 500), 0 with production `E_ALL & ~E_DEPRECATED` |
| 8.6.0RC5 | 19 | 62 | 497 | refused: `php8.6-redis`, `php8.6-imagick`, `php8.6-igbinary` are not published; the upgrade stops before purging (`SETUP_PHP_ALLOW_MISSING_EXT=1` overrides) |

Findings:

* WordPress 7.1.4 is clean at run time on 8.4–8.6; its 18 notices come from
  the bundled `sodium_compat` (implicit nullable parameters, PHP 8.4+).
* XenForo 2.3.13 is **cleanest on 8.4**: 8.5 adds four deprecations and, in
  debug mode, makes two POST routes answer 500.  Its 56+ notices are the
  bundled `league/*`, `flysystem` and `braintree` libraries; two vendor files
  do not even parse on 8.2+ (`Digest.php`, `laminas-mail/Null.php`) but are
  never autoloaded.  Recommendation: `--upgrade-php=8.4` for a forum-only host.
* Chevereto 4.5.9-pro runs clean on 8.5 with production error reporting but
  carries ~480 vendor deprecations (Azure SDK, hybridauth, nette, PHPCS).
  8.4 is the conservative match; the panel itself is functional on 8.5.
* 8.6 is a release candidate in Sury and **cannot serve** Chevereto (imagick)
  or the XF Redis cache (redis) on this host.  The upgrade correctly refuses.

Upgrade round trip: 8.5 → 8.4 → 8.6 (refused) → 8.6 (forced, extensions
missing) → 8.5, each time Angie reloaded, socket preserved, extensions and
managed pool/ini intact; final state 8.5.12 with all apps HTTP 200.

## 7. Anubis

* Policy: allow good crawlers, deny AI crawlers, allow `.well-known`,
  favicon, robots.txt and static asset extensions; challenge empty and
  `Mozilla` user agents; unmatched clients default-allow (API/cron).
* Runtime: `GOMAXPROCS=8`, `GOGC=off`, `GOMEMLIMIT=2048MiB`,
  `LimitNOFILE=65536`, `SLOG_LEVEL=WARN`, Unix socket 0660 in a 0750
  runtime dir, `www-data` in the `anubis` group only.
* Static assets never enter the Go process: a generated static shadow of each
  vhost (same root and deny rules) answers them directly (measured 35–41k
  req/s for cached pages, static assets far higher).  RSS 24 MB, 0 journal
  warnings.
* The remaining cost is body copying for dynamic pages; member traffic is
  unaffected.  This is the leanest configuration that keeps a challenge in
  front of every HTML page.

## 8. Known limitations and deferred items

* `--domain` still runs a full `--optimize` pass by default (documented, and
  what keeps new vhosts tuned); `SETUP_DOMAIN_OPTIMIZE=0` skips it.
* Guest-cache zone sizing and `fastcgi_cache_background_update` are patched
  into the live tree by the optimizer; the shipped defaults are small-host
  sizes, not the tuned ones (intentional: the optimizer owns sizing).
* `h5bp/sys_guard`, `ngx_waf_conf`, `naxsi_conf` and `ppa_eilander_conf`
  remain disabled samples that would need their modules; they are not loaded
  by any template.
* Access logging is off globally (performance default); the operator gets
  the managed error logs and `/var/www/logs`.  Enable a buffered access log
  for credential endpoints on a host that needs forensic trails.
* The `Chev member explore` bench tier is not representative: all requests
  share one PHP session and serialize on the session lock (12 req/s, 20
  aborted).  Guest tiers are the ones to compare.
