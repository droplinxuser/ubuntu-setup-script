Notes:

- Chevereto 4.5.9 bundles Intervention Image 2.x. Its implicit-nullable
  constructor is promoted to an `ErrorException` by Chevereto's shutdown
  handler on the first request after each FPM restart on 8.4+, so the
  one-line `?ImageManager $manager = null` upstream fix is still required.
  This is an application defect, not a server setting.
- The XenForo deprecations are all in `src/vendor` (League Flysystem/Event,
  JoyPixels, Laminas); none of the two fatal files (laminas-mail,
  braintree) is loaded by a stock board.
- 8.6 cannot be installed by `--upgrade-php` on this host because the purge
  would remove `redis`/`imagick`/`igbinary`; the preflight refuses before
  changing anything and names the sites that would break.

## 6. Security findings

1. **XenForo upgrader login was unthrottled (fixed in Angie 1.6.28).**  The
   board's `/login` is capped at 20 submissions a minute per address, but
   `/install/index.php?upgrade/login` (reached from `/install/` via a 303)
   was not in the `limit_req_login` map and accepted unlimited attempts at
   the generic POST rate.  Verified after the change: 11 submissions are
   answered 400 (missing CSRF token) and every later one 429.
2. **A cached 301 outlived an option change (harness).**  XenForo caches
   options at install time; the raw `UPDATE` in the deploy script did not
   invalidate them, and the vhost stores 301s for an hour.  The deploy script
   now uses the option repository and purges the guest cache.  The Angie
   repository already shortened the 301 TTL from 24 h to 1 h in an earlier
   cycle; README said 24 h and is corrected.
3. **The cookie-safety suite was silently unrunnable.**  Missing fixtures
   made a correct host look broken (MISSHITHIT from the cache, 200 instead of
   302 for the Chevereto login).  With fixtures, all 61 checks pass: no
   `Set-Cookie` is stored or replayed, a forged `xf_session` bypasses the XF
   cache, two guests get different CSRF tokens, and each WordPress visitor
   with `?gc=1` gets a unique uncached token.
4. **51-check probe suite.**  Hidden files, `wp-config.php` backup copies,
   root dumps, PHP below writable directories, PATH_INFO execution, dot
   segments, XenForo `internal_data`/`src`/`library`/`data`/`js`/`styles`,
   Chevereto `app`/`vendor`/`importing`/`content`/`sdk`, unknown `Host`
   (connection reset), `X-Forwarded-Host`, PUT and TRACE all answer the
   documented deny/4xx.  No bypass was found.

## 7. Residual risks and recommendations

- The XenForo upgrader stays reachable by design.  Enable the commented
  `auth_basic` block in the vhost, or remove `install/` between upgrades.
- XenForo's guest cache stores 301s for an hour.  After changing URL or
  routing options, purge `/home/nginx_cache` (the deploy harness does).
- Chevereto on 8.4+ needs the upstream `?ImageManager` one-liner; without it
  the first request after an FPM restart fails once.
- The cache tiers are client-bound on this workstation's Wi-Fi; use the
  wired figures in `AUDIT-20261114-1.21.6.md` as the server ceiling.
