## 1. Changes

### 1.1 Anubis pass cookie checked in Angie (njs)

The 1.21.55 edge route left every browser request on the Go hop, including
visitors who had already solved the challenge.  The Anubis 1.28.2 source
(`maybeReverseProxy`, `PassChallenge`) checks, for a CHALLENGE rule: the
HS512 signature, `exp`, the matched rule hash, and `restriction` =
SHA-256 of the `X-Real-IP` header when one is configured.  No server-side
session exists.  A real token from the audit host:

```
{"action":"CHALLENGE","challenge":"<uuid>","exp":...,"iat":...,"method":"fast",
 "nbf":...,"policyRule":"<hash>","restriction":"sha256(127.0.0.1)"}
```

The cookie is `techaro.lol-anubis-auth-<8 hex>` (a suffix derived from the
cookie settings).  `anubis_pass.js` (angie-module-njs 1.12.5) checks the
same fields.  For the rule hash it substitutes "issued after the policy
file last changed".  It also sends the post-challenge Referer-restore
request, an empty User-Agent, AI crawlers and anything malformed to Anubis.

| Request (XenForo home, browser UA) | Result |
|---|---|
| valid pass cookie | forum page |
| no cookie | Anubis challenge |
| signature tampered (one character) | Anubis challenge |
| GPTBot + valid cookie | Anubis deny page |

Throughput of the browser path (cached XenForo home, valid cookie, c=100):

| Variant | req/s |
|---|---:|
| Go hop (1.21.56) | 19,295 |
| njs, verify every request | 42,061 |
| njs + shared-dict verdict cache (shipped) | **55,192** |
| `js_set` returning a constant (njs floor) | 62,610 |
| no njs, browser UA sent straight to the backend (ceiling) | 62,206 |

WordPress with a pass cookie: 16,686 (1.21.55) -> **49,961**.  The verdict
cache is keyed by token signature, visitor address, policy epoch and a
secret fingerprint, so a policy or secret change invalidates cached verdicts
although the zone survives reloads.

A first build wrote the secret to `/etc/angie/anubis-pass-key.conf`; the
Angie tree normaliser resets every file outside `ssl/` to 0644, so it ended
world-readable on the test host.  The key now lives in
`/etc/angie/ssl/anubis/pass-key.conf` (directory 0700, file 0600; verified
after two further `--optimize` runs).

With the filter on: security 65/65, cookie suite 62/62, functional exercise
0 unexpected, no njs lines in the Angie error log; `--optimize` twice gives
0 differences in 3,049 state facts.  `SETUP_ANUBIS_PASS_EDGE=0` removes the
loader, script and key (browser route back to `anubis`), a plain
`--optimize` restores them, and `anubis=no` removes everything with all
three sites answering 200.

### 1.2 Guest-cache page gzip for sites deployed after `--domain`

The first tiers of this cycle measured cached WordPress at 6,576 req/s and
Chevereto explore at 9,346 (93k and 129k in 1.21.55), with Angie at 800 %
CPU (1.2 ms per hit).  The per-root `zlib.output_compression` section was
written only for roots that already held `wp-config.php` /
`app/env.php`.  The audit deploys the applications after `--domain`, as an
operator would, so the cache stored plain bodies and Angie compressed every
hit.  The vhost now decides.  After `--optimize` and expiry of the old
entries (Chevereto caches for 1 h):

| Tier | before | after |
|---|---:|---:|
| WP guest home (cached) | 6,576 | **93,385** |
| WP guest post (cached) | 6,419 | **90,309** |
| Chev guest explore (cached) | 9,346 | **140,016** |
| Chev guest image (cached) | 7,149 | **130,180** |

### 1.3 Stale repository index on a CDN

The first install attempt failed after 7 min 57 s: Sury's CDN served an
`InRelease` dated 09:01 next to a `Packages.xz` from 09:31 (cache age 45
minutes).  All four 1.21.56 retries failed.  The uncompressed `Packages` was
cached with the `InRelease` and matched it.  `apt_update` now refetches only
the failing repositories uncompressed before the timed retries.  The rerun
logged one info line and continued: install 2:04, 0 warnings.

unpublished.  `--upgrade-php=8.6 --dry-run` blocks on Chevereto (redis,
