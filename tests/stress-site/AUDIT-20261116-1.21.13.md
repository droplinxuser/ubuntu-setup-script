(1.21.9), the nested XenForo include migration (1.21.10), the default
WordPress guest cache (1.21.11) and the unified `X-Cache-Status` header
(1.21.12).

## 1. Findings and fixes (1.21.13)

| Area | Finding | Fix | Verification |
|---|---|---|---|
| MariaDB pool | `auto` sized `innodb_buffer_pool_size` at 4% of live data: a 935 MB table got 128 MB.  Point-query benchmark: **70 876 q/s** with 36 661 physical reads per 40 000 queries (92%); **212 041 q/s** with 0 reads at 1.7 GB. | `auto` = data+index plus 25%, capped at RAM/2 and at the shared budget; 128 MB floor and only-increase rule unchanged. | 840 -> 845 tuning checks; live report `data+index=61MB ... kept existing pool; the data+25% target is 128MB`. |
| XenForo include | A one-line `location /x/ { include h5bp/php_xf.conf; }` was not treated as nested, so `angie -t` failed (`named location @xf_guest_cache can occur on the server level only`) and the whole tree rolled back. | The migration also rewrites an include that follows `{` on the same line. | Reproduced on the live tree (`angie -t` failed), then `--optimize` rewrote it and `angie -t` passed; unit test added. |
| WordPress cache report | A vhost with `h5bp/wordpress.conf` but no `h5bp/php_wp.conf` has no insertion anchor; the report claimed `SETUP_WP_GUEST_CACHE=0` was set. | The report names the missing anchor and leaves the vhost alone; the opt-out report is reserved for a real opt-out. | Unit tests for both paths. |

No changes were needed in `server-configs-nginx`; 1.6.30's
`X-Cache-Status` rename was verified on all three applications.

## 3. Performance

`oha` over the LAN, TLS, HTTP/1.1, 10 s per tier, 200 connections for guest
tiers and 100 for member tiers.  Every response was 200.

### 3.1 Distribution defaults vs shipped tuning

Stock: `pm=dynamic`, `pm.max_children=5`, start/min/max spare 2/1/3, JIT off.
Tuned: `pm=static`, `pm.max_children=16`, tracing JIT 64 MB.

| Tier | stock req/s | tuned req/s | change |
|---|---:|---:|---:|
| XenForo member home | 407 | **880** | +116% |
| XenForo member thread | 270 | **573** | +112% |
| WordPress member home | 140 | **296** | +111% |
| WordPress member post | 133 | **283** | +113% |

### 3.3 OPcache JIT sweep (loopback, 100 connections, tuned pool)

XenForo member / member-thread req/s (8 s runs):

| Configuration | member | thread |
|---|---:|---:|
| tracing, 64 MB, 64/127/16/64 (shipped) | **962 / 923** | **619 / 595** |
| JIT off | 887 | 563 |
| tracing, 32 MB | 940 | 606 |
| tracing, 128 MB | 933 | 598 |
| function, 64 MB | 876 | 555 |
| tracing, aggressive 16/64/8/32 | 929 | 595 |
| tracing, conservative 128/255/32/128 | 913 | 604 |

The shipped configuration is the best or within noise of the best on every
tier; JIT off costs 6-9%, function JIT costs 7-9% and worsens p99.

### 3.4 MariaDB buffer-pool measurement

935 MB InnoDB table, 8 concurrent PHP clients, random primary-key lookups,
5 000 queries each:

| Pool | aggregate q/s | physical reads / 40 000 |
|---|---:|---:|
| 128 MB (the 4% rule's floor) | 70 876 | 36 661 |
| 1 738 MB (holds the table) | 212 041 | 0 |

The 128 MB pool answered the same workload at one third of the throughput,
which is why `auto` no longer uses 4% of data.
