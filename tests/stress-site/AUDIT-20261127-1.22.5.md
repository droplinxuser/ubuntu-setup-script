# Audit — 1.22.5 (XenForo uncached throughput, build defaults, release before/after)

Date: 2026-11-27
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe, Ubuntu
26.04.1, kernel 7.0), clock pinned at 3.6 GHz for every measurement.
Pair: `server-configs-nginx` 1.7.4 (branch `main`).  Operator rule for
this cycle: XenForo only; an option at least 2 % faster on a tier, with
no tier slower, becomes the default; an opt-in that is not faster is
deleted.

## 1. Method

* XenForo tiers only (`/root/xf.tiers`): guest home cached, guest home
  and guest thread uncached (`xf_session=bench-bypass`), member home and
  member thread.  `loopback-tiers.sh 100 10`, 5 rounds per arm, median,
  every row gated on HTTP status, the logged-in marker and the cache
  status.
* Build options are switched through `nginx-build.conf` /
  `php-build.conf` and applied with two `--optimize` runs under
  background load (build, then the BOLT profile), as an operator would.
* RSS under load is sampled every 15-30 s while `wrk` runs (sum of every
  `php-fpm` / `nginx` process).

C = PHP mimalloc + nginx AWS-LC, B = PHP glibc + nginx OpenSSL 4.1.0.

|---|---:|---:|---:|---:|---:|---|

RSS under load:

| Process | glibc / OpenSSL | mimalloc / AWS-LC |
|---|---:|---:|
| PHP-FPM | 1,190-1,370 MB | 416-449 MB |
| nginx | 300-320 MB | 234-237 MB |

AWS-LC feature check: `nginx -t` clean, 16 UDP 443 listeners (HTTP/3),
TLS 1.3 `TLS_AES_256_GCM_SHA384` and TLS 1.2 `ECDHE-RSA-AES256-GCM-SHA384`.
Session resumption, rechecked after the release run with
`openssl s_client -reconnect` (1 + 5 connections): TLS 1.2 resumes from
nginx's shared cache on AWS-LC (1 New, 5 Reused); TLS 1.3 does not (6
New).  AWS-LC resumes TLS 1.3 only through tickets, and `ssl_session_tickets
off` stays; OpenSSL issues stateful TLS 1.3 tickets backed by the shared
cache even with tickets off.  The cost is a full handshake for a TLS 1.3
client that reconnects directly to the origin; AWS-LC's full ECDSA
handshake needs about half of OpenSSL's CPU, and behind Cloudflare the
edge keeps its origin connections open, so no tier measured it.  The
earlier probe here (`New` on both libraries) did not reconnect.

B1's uncached rows (540/351/486/267) sit 5-10 % under B2's, so the "C vs
B" means above overstate the gain; against B2 alone C is +2-4 %.  The
release run (section 6) separates the two: mimalloc alone is +3.3-3.8 %
on every uncached tier and halves PHP-FPM RSS; AWS-LC moves the cached
tier and nginx memory only.

Decision: nginx builds only on AWS-LC and PHP only on mimalloc; the losing
values (`TLS_LIB=openssl`, `PHP_BUILD_MALLOC=glibc`) are removed with a
warning and a one-time rebuild.

## 5. Review and tests

* An adversarial review of the AWS-LC/mimalloc change (4 reviewers, every
  finding verified by a skeptic) confirmed 4 of 5 findings, all fixed:
  * the 1.22.4 PHP library cache could never be reused after the update.
    It was keyed without the allocator, so every host would have
    recompiled every library once.  The old key is now hashed without
    mimalloc, and only mimalloc is built into the renamed cache;
  * a test pattern rejected the intended `jemalloc)` warning arm;
  * two CHANGELOG wordings.
* The release before/after (section 6) found one more: the renamed 1.22.4
  PHP library cache kept its old directory in its `.pc`, `.la` and
  `*-config` files, so the PHP build failed on every `--optimize`.  Fixed
  (the rename rewrites the name; a unit test covers a `.pc` file and a
  binary) and confirmed by A3/A4 building on mimalloc from a recreated
  1.22.4 cache.
* Unit suites, `tests/test-tuning.sh` (4,177 pass, 0 fail) and the dry-run
  matrix (301 pass) on the host; ShellCheck clean.
* On the final state: security probe 78/78, guest-cache cookie test
  109/109, `nginx -t` clean with 16 UDP 443 listeners, Redis 6.0.16 starts
  on the rendered config (`save 300 1`, `port 0`, RDB written).  The PHP
  compatibility walk shows the known upstream item of AUDIT-20261126-1.22.3
  section 6 (XenForo 2.3.13 core `E_DEPRECATED` on PHP 8.5 turns member and
  admin pages into 500 in the walk's debug mode only; normal mode served
  every gated member round of section 6).

## 6. Release before/after (1.22.4 vs 1.22.5)

The whole release as an operator gets it: the 1.22.4 pair (`before`) and
the 1.22.5 pair (`after`) each applied with two `--optimize` runs under
load, then a reboot (the kernel command line is part of the release),
then 60 s idle and 5 rounds.  Arms in this order: B1 A1 B2 A2 A3 B3 A4.

**A1 and A2 do not count as 1.22.5.**  Their PHP rebuild failed: the
1.22.4 library cache renamed to the 1.22.5 key still held the old path
in its `.pc`, `.la` and `*-config` files, so `libxml/parser.h` was not
found.  The build stopped before anything changed (PHP stayed the 1.22.4
glibc build) and `--optimize` exited 1.  Every host updating from 1.22.4
would have hit it on every run.  Fixed: the rename rewrites the old
directory name in every file of the cache (both names are
`deps-<16 hex>`, so binaries keep their length) and drops the cache if a
reference survives; a unit test covers a `.pc` file and a binary.  A3
and A4 ran after the fix, from a recreated 1.22.4 cache, and built
`malloc=mimalloc`.  A1/A2 stay below as "1.22.5 without the PHP rebuild".

| State | 1.22.4 (B1 B2 B3) | 1.22.5 (A3 A4) |
|---|---|---|
| Kernel | mitigations on (PTI, IBRS) | `mitigations=off` |
| nginx 1.31.10 | OpenSSL 4.1.0, BOLT | AWS-LC 5.15.0, BOLT |
| PHP 8.5.13 | glibc malloc, BOLT | mimalloc, BOLT |
| Dynamic Brotli | level 4 | level 1 |
| OPcache | `validate_timestamps=1` | the same + `enable_file_override=1` |
