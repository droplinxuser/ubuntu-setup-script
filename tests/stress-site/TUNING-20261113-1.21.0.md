# setup.sh 1.21.0 - three-application validation (2026-11-13)

Host: `audit-host` (8 cores / 16 threads, 27 812 MiB RAM, NVMe, Ubuntu
26.04.1, bare metal, kernel 7.0).  Stack installed from the local checkouts
with `--basic --angie --php ver=8.5 --mariadb size=auto --valkey --elastic
ram=4g --others all`.  Applications created with `--domain ... app=wordpress
| xf | chevereto db=... user=... pass=...` and installed by
`deploy-three-apps.sh`: WordPress 7.1.4 (100 users / 400 posts / 300
comments), XenForo 2.3.13 (60 members / 200 threads / 2 600 posts, friendly
URLs, Valkey cache and sessions over the Unix socket, server-based job
trigger) and Chevereto 4.5.9 (Valkey cache over the Unix socket).

Two load paths were used:

- **Loopback** (`loopback-tiers.sh`, `wrk -t4 -c100`, HTTPS/1.1 keep-alive, on
  the host).  This is the server's own ceiling and the basis of every
  decision below.  The generator shares the 16 threads with the stack.
- **Workstation** (`bench-one.sh`, `oha` 1.16.0, 100 connections, HTTP/2).
  Workstation and host were both on Wi-Fi (4-100 ms ping jitter), so cached
  tiers stop at 3-4k req/s on the link.

Server CPU per request is from the systemd cgroup accounting
(`sample-cpu.sh`).

Every response was 2xx.  The WordPress and Chevereto cached tiers were
CPU-bound in Angie before (about 1 400% of one core, i.e. every thread):
the cache held the uncompressed page and Angie Brotli-compressed it on each
hit.  With PHP gzipping the page once for the cache, a hit costs what a
XenForo hit always did.  Member tiers do not move: they are bound by PHP.

A Chevereto logged-in tier is not in the table: Chevereto verifies the
`KEEP_LOGIN` cookie with bcrypt on every request and serialises the requests
of one session, so 100 connections on one login complete nothing within
wrk's 2 s timeout.  That cost is in the application.

`jit_hot_func = 127`, `jit_hot_return = 16`, `jit_hot_side_exit = 64`.

## PHP version compatibility (`compat-php.sh`)

Method: `php -l` with `E_ALL` on every PHP file, then the application walk
with WordPress in `WP_DEBUG`, XenForo in debug mode with
`error_reporting(E_ALL)` (a deprecation in XenForo's own code becomes an
exception and a 500) and Chevereto logging to a file.  A plain
`error_reporting = E_ALL` in php.ini reports nothing, because all three
applications mask `E_DEPRECATED` themselves.

Compile-time deprecations found by lint:

| | PHP 8.3.36 | PHP 8.4.27 | PHP 8.5.12 | PHP 8.6.0 RC5 |
|---|---:|---:|---:|---:|
| WordPress 7.1.4 (1 513 files) | 0 | 18 | 18 | 19 |
| XenForo 2.3.13 (9 018 files) | 13 | 56 | 60 | 62 |
| Chevereto 4.5.9 (51 628 files) | 1 | 480 | 481 | 497 |

All of them are in bundled libraries: WordPress `sodium_compat` (its 32-bit
fallback), XenForo `src/vendor` (Laminas, Braintree, Flysystem, less.php),
Chevereto `app/vendor` (the Azure storage SDK is 467 of the 481 on 8.5, then
intervention/image).  XenForo also ships two vendor files no PHP 8 can
compile (`laminas-mail/.../Transport/Null.php`, `braintree/.../Digest.php`);
they are never loaded.

Run-time result:

| | PHP 8.3 | PHP 8.4 | PHP 8.5 | PHP 8.6 RC5 |
|---|---|---|---|---|
| WordPress 7.1.4 | clean | clean | clean | clean |
| XenForo 2.3.13 | clean (vendor deprecations logged only) | clean (same) | works; XenForo's own `src/XF/App.php` raises "Using null as an array offset is deprecated" on every member and admin page (masked in production mode, a 500 in strict debug mode) | same as 8.5, and only with the Valkey cache switched off: Sury publishes no `php8.6-redis`, `-igbinary` or `-imagick` yet |
| Chevereto 4.5.9 | clean, including the first request after an FPM restart | works, but the first request that compiles a deprecated vendor file after every FPM restart or OPcache reset fails once (login answered 403): Chevereto's shutdown handler turns the compile-time deprecation into an exception | same as 8.4 | same as 8.4, and only with the Valkey cache switched off |

Newest PHP version each application runs on without any diagnostic from its
own code path:

- **WordPress 7.1.4: PHP 8.6** (RC5 tested; nothing at run time on 8.3-8.6).
- **XenForo 2.3.13: PHP 8.4.**  It runs on 8.5 in production mode.
- **Chevereto 4.5.9: PHP 8.3.**  It runs on 8.4 and 8.5 apart from the
  one-off failures after a restart.

The Chevereto logins in `exercise-apps.sh` can also answer 500 when the same
user logs in twice within one second (`Duplicate entry ... for key
'login_cookie_unique'`); that is the test, not the PHP version.

## Not changed

- Brotli stays at level 4.  It no longer matters for cached WordPress and
  Chevereto pages (they are stored gzipped); it still applies to uncached
  responses and to clients that accept Brotli but not gzip.
- No tuning default for sysctl, MariaDB, Valkey, Elasticsearch or the Angie
  event loop changed: no tier was bound by any of them.  MariaDB used at
  most 2 of the 16 threads in every tier.
