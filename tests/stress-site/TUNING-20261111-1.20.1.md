## OPcache JIT sweep (authenticated XenForo thread, no FastCGI cache)

100 connections, 8 s per profile after 3 s warm-up, PHP-FPM reloaded between
profiles, `zzz-audit.ini` drop-in. `php ms/req` is PHP-FPM cgroup CPU divided
by successful requests. Medians of three runs (the first sweep's tracing64
row was a single 397 req/s thermal outlier; the repeat below is stable).

| JIT profile | `opcache.jit` | buffer | hot loop/func/return/side | req/s (median) | p50 ms | PHP ms/req |
|---|---|---|---:|---:|---:|---:|
| off | off | 0 | 64/127/16/64 | 578 | 171.0 | 24.9 |
| function | function | 64M | 64/127/16/64 | 566 | 176.4 | 24.8 |
| **tracing, 32 MB** | tracing | 32M | 64/127/16/64 | **610** | 162.4 | 22.9 |
| **tracing, 64 MB (shipped)** | tracing | 64M | 64/127/16/64 | **606** | 162.7 | 23.2 |
| tracing, 128 MB | tracing | 128M | 64/127/16/64 | 612 | 163.2 | 23.2 |
| aggressive | tracing | 64M | 16/64/8/32 | 611 | 161.8 | 23.1 |
| conservative | tracing | 64M | 128/255/32/128 | 609 | 162.9 | 23.0 |
| root traces 256 | tracing | 64M | 64/127/16/64 | 605 | 161.9 | 23.2 |
| root traces 1024 | tracing | 64M | 64/127/16/64 | 608 | 163.3 | 23.2 |
| polymorphic calls 4 | tracing | 64M | 64/127/16/64 | 607 | 162.5 | 23.1 |
| side traces 128 | tracing | 64M | 64/127/16/64 | 576 | 176.3 | 23.3 |
| combined (1024/128/4) | tracing | 64M | 64/127/16/64 | 555 | 180.3 | 23.7 |

The tracing JIT is worth **+4.8%** over JIT off (606 vs 578 req/s, 23.2 vs
24.9 ms PHP CPU/request) and +7% over function JIT. 32 MB, 64 MB and 128 MB
are within noise; the buffer only reserves address space, so the shipped
64 MB stays. Lowering/raising the hotness thresholds, adding root/side
traces or allowing more polymorphic calls are all within run-to-run noise on
this CPU count; PHP's defaults stay. `SETUP_PHP_JIT_HOT_*` remain available
for a host that measures a difference.

100 connections, 8 s per count after 3 s warm-up, `pm = static`.

| Workers | req/s | p50 ms | p99 ms | PHP ms/req |
|---:|---:|---:|---:|---:|
| 8 | 419 | 243.7 | 285.8 | 18.3 |

| 20 | 600 | 166.4 | 198.9 | 23.9 |
| 24 | 582 | 172.0 | 251.4 | 24.6 |

The shipped 1.0 worker per logical CPU (16) is the throughput peak; beyond it
the same cores are shared by more processes and per-request CPU rises. This
repeats the 1.19.2 sweep (16-20 plateau) and keeps
`php_workers_per_cpu_tenths=10` for a local-DB flash host.

## Static assets: edge cache, immutable headers and precompression

`SETUP_PRECOMPRESS_ASSETS=1` wrote `.br` and `.gz` siblings for 3 820 static
files under the XenForo and WordPress roots (7 616 siblings, 3m28s first
pass; the 5-minute cron pass compresses 0 files in 0.45s when nothing
changed).

| Asset | identity | gzip | brotli | Saving |
|---|---:|---:|---:|---:|
| XenForo `/js/xf/filter.js` | 14 076 B | 3 938 B | 3 430 B | -75.6% br |
| WordPress editor CSS | - | - | - | served br, `max-age=31536000` |

XenForo assets carry `Cache-Control: public, immutable` + `expires` 30 days
(the tuner's regex location), WordPress core assets 1 year. Guest pages are
served from the Angie FastCGI cache: XF home `X-5m-Cache: MISS -> HIT`,
WordPress `X-Cache-Status: MISS -> HIT`, XenForo thread canonicals cached
(301).

### Valkey backends for authenticated traffic (measured, then reverted)

| Config | XenForo home | XenForo thread | WordPress member |
|---|---:|---:|---:|
| MariaDB cache/sessions (shipped) | 898 | 607 | 300 |
| XF cache/sessions in Valkey (socket) | 803 (-10.6%) | 563 (-7.3%) | - |
| WP Redis object cache (Valkey, phpredis) | - | - | 278-283 (-7%) |

On a single host with a local MariaDB, both backends add a socket round trip
and serialisation without removing a bottleneck: the pages are PHP/render
CPU-bound (MariaDB is 3-4 ms/request). They are the right choice for a
multi-node or remote-database deployment; the optimize report keeps saying so
and neither is enabled by default.
