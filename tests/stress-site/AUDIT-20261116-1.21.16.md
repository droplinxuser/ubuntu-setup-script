Date: 2026-11-16
Host: `16c-32g-1T` (SER8), Ubuntu 26.04.1 LTS, 16 logical CPUs, 27 812 MiB
RAM, 931 GB NVMe (CT1000P3PSSD8), bare metal, kernel 7.0.0-43.
Baseline: 526 packages, no managed services, `/tmp` empty apart from
systemd-private directories.  Stack installed by `setup.sh`: Angie 1.12.4,
PHP 8.5.12-FPM (8.4.27 round trip, 8.6.0RC5 CLI for the deprecation scan),
MariaDB 11.8.6, Valkey 9.0.4, Elasticsearch 9.5.6, Node.js 26.13.1,
Anubis 1.28.2.  Applications: WordPress 7.1.4, XenForo 2.3.13,
Chevereto 4.5.9, deployed from the local archives through `--domain`.
Angie configuration came from the local `server-configs-nginx` checkout
(`CONFIG_SOURCE_DIR`), not from GitHub, so the run exercised the audited tree.
Load generators: `oha` 1.17.0 on the host (loopback, TLS/HTTP1.1) and
`oha` 1.16.0 on the Mac over the LAN.

## 1. Findings and fixes

### 1.1 ubuntu-setup-script 1.21.16

| Area | Finding | Fix | Verification |
|---|---|---|---|
| `--upgrade-php` noise | `angie_vhost_root` piped `grep -m1` into `sed`; a conf.d file with no `root` directive (every Anubis TLS terminator) returned 1 through `inherit_errexit`, so the upgrade preflight's vhost walk printed four false `[ERR] command failed ... sed`/`sort -u` lines while the run finished successfully (exit 0). | The lookup is an awk that always succeeds and prints nothing for a rootless or missing file. | `--upgrade-php=8.4` then `=8.5`: 0 `[ERR]`/`[WARN]`; two new unit checks (878 total). |
| Duplicated app detection | The `--upgrade-php` preflight carried two inline copies of the WordPress/XenForo/Chevereto marker check; the tuners and the report carried more. | `app_type_at_root` in `lib/util.sh` is the single owner; both preflight walks call it. | WordPress/XenForo/Chevereto/empty/missing cases unit-tested; upgrade preflight still blocks 8.6 for both app types. |
| Anubis runtime | The Go proxy ran the default `GOGC=100`; mark/sweep long before the ~120 MB working set needed it. | Managed unit sets `GOGC=400` and `GOMEMLIMIT=1GiB` (OOM backstop). | Cached WordPress tier 7 100 req/s vs 6 750 (p99 35 vs 39 ms), RSS 114 MB; applied by install and `--optimize`. |

### 1.2 server-configs-nginx 1.6.33

| Area | Finding | Fix | Verification |
|---|---|---|---|
| Credential limiter | `$req_login_key` used `$limit_req_key`, the map that the `geo` whitelist empties. `setup.sh` writes `SETUP_LIMIT_REQ_EXEMPT` into that whitelist so a load generator or reverse proxy escapes the 100 r/s GET zone — which also removed the 20 attempts/minute login limit for that address. A CDN range added there would have removed it for every visitor behind the proxy. | The credential zone has its own key (`$limit_req_login_key`) and its own whitelist (loopback only). A trusted proxy must configure real_ip so `$binary_remote_addr` is the visitor. | Before: 16/16 `POST /wp-login.php` from the exempt LAN address answered 200. After: 10 then 429 from that address, 16/16 from loopback, generic GET from the same address still unthrottled (10 353/10 353 200s). Login limiter also verified end-to-end through Anubis (11 allowed, then 429). |

### 1.3 Reviewed and confirmed (no change needed)

* Anubis's TLS terminator, `real_ip` migration, X-Forwarded-For replacement,
  upload cap, failed-start rollback and purge restore were re-exercised:
  pages 200, no bypass from an unknown `Host` (connection reset on the
  catch-all), 400 on an empty `Host`.
* TLS: TLS 1.2/1.3 only, balanced cipher list, `server_tokens off`,
  HSTS preload; no autoindex, DAV, `stub_status` or variable `proxy_pass`.
* Guest caches: WordPress and XenForo stay at `HIT` on the second request,
  Chevereto home is `BYPASS` by design, explore/image are cached.
* The WordPress `zlib.output_compression` page-gzip profile causes two
  `ob_end_flush(): Failed to send buffer of zlib output compression` notices
  per request **only when `WP_DEBUG` is on** (WordPress hides E_NOTICE in
  production).  Measured: 10 notices/5 requests with zlib on, 0 with it off.
  The 7.6x cached-page gain is kept; the notice is documented here rather than
  suppressed with a global `error_reporting` downgrade.

The Chevereto rows are the post-flush measurement: a cache entry written

`--optimize` wrote the `[PATH]` section and the entry was dropped, the same
tier measured 87 112.  Operators who copy application files in after
`--domain` should run `--optimize` and flush `/home/nginx_cache*`.

16 = one static worker per logical CPU is the plateau; deeper pools only

local database).

### 4.4 OPcache JIT, paired A/B (XenForo member thread)

Interleaved pairs (shipped tracing/64 MB, then JIT off), 8 s each, 100
connections:

| Pair | tracing 64 MB | JIT off |
|---|---:|---:|
| 1 | 386 | 372 |
| 2 | 384 | 372 |
| 3 | 384 | 367 |
| 4 | 380 | 368 |
| 5 | 377 | 367 |
| **median** | **384** | **368** |

The shipped profile is +4.3% and wins every pair.  A single unpaired sweep
run suggested the opposite (380 vs 425) because the first run after a reload
pays cold-cache/CPU-frequency cost; the paired design removes that.  The 8.4
audit's wider sweep found tracing 64 MB with PHP's default hotness thresholds
(64/127/16/64) best on this hardware, `function` JIT worst (p99 4x), and
32/128 MB equivalent; nothing changed.
