# setup.sh 1.21.17 — Anubis static-asset fast path

Date: 2026-11-16
Host: `16c-32g-1T` (SER8), Ubuntu 26.04.1 LTS, 16 logical CPUs, 27 812 MiB
RAM, 931 GB NVMe, kernel 7.0.0-43.  Stack: Angie 1.12.4, PHP 8.5.12-FPM,
MariaDB 11.8.6, Valkey 9.0.4, Elasticsearch 9.5.6, Node.js 26.13.1,
Anubis 1.28.2.  Applications: WordPress 7.1.4, XenForo 2.3.13,
Chevereto 4.5.9.  Angie tree from the local `server-configs-nginx` checkout.

## 1. Why

The 1.21.16 audit prototyped a terminator-level static-asset bypass that
reached 300 000+ req/s, then rejected it: the simplest implementation proxied
straight to `/run/angie/anubis-backend.sock`, which is `0750 root:anubis` on
purpose.  Granting `www-data` traverse would have let any PHP process (or a
local account in the web group) connect to the real backend with
`X-Real-IP: 127.0.0.1` and skip both the bot filter and every IP ACL.

The performance case is real, though: static assets are most of a site's
request volume, the managed policy ALLOWs them, and every one of them paid a
Go proxy hop.

## 2. Design

Every protected vhost gets a **static-only shadow** server block, generated
from the application block itself, on its own socket
`/run/angie-static/static.sock` (directory `0750 root:www-data`).

The shadow is a mechanical copy: `server_name`, `root`, every `include` and
every `location` of the application block, with the public `listen` lines and
TLS directives removed, and two server-level guards added:

```
if ($uri !~* "^/(?:.*/)?[^/]+[.](?:css|js|mjs|map|png|jpe?g|gif|webp|avif|svg|ico|bmp|woff2?|ttf|otf|eot|mp4|webm|mp3|ogg|wav|wasm|html?)$") { return 404; }
if (!-f $request_filename) { return 404; }
```

and one `default_server` block that answers 404 for an unknown `Host` so a
request can never fall through to the first site's root.

The terminator proxies the asset extensions to it and intercepts 404:

```
location ~* ^/(?:.*/)?[^/]+[.](?:css|...|wasm)$ {
    proxy_pass http://anubis_static;
    ...
    proxy_intercept_errors on;
    error_page 404 = @anubis_static_miss;
}
location @anubis_static_miss { include snippets/anubis-location.conf; }
```

Copying the block is the security argument:

* XenForo's `location ^~ /internal_data { internal; }`, the dotfile,
  backup, database-dump and root-archive denies, exact-match locations and
  `expires`/header rules all apply exactly as on the backend socket;
* a URI that is not an existing static file — including every `.php`, every
  dynamic route and every miss — is a 404, so the terminator retries through
  Anubis.  A local `www-data` process that reaches the shadow can read public
  files and nothing else;
* the real backend socket keeps its `0750 root:anubis` and `nobody` cannot
  reach either directory.

A server block with a server-level `return`/`rewrite` is skipped (its assets
are redirected; pushing that redirect through the terminator would loop).
`SETUP_ANUBIS_STATIC_BYPASS=0` disables the fast path and is persisted as
`ANUBIS_STATIC_BYPASS`; `--optimize anubis=no` and `--purge angie` remove the
generated file with the rest of the Anubis files.

## 3. Measurements

Loopback, `oha`, TLS/HTTP1.1, 100 connections, 8 s, one CSS file from
WordPress (`/wp-includes/css/...`), all responses 200:

| Path | req/s | p50 ms | p99 ms | Anubis cores |
|---|---:|---:|---:|---:|
| Through Anubis (bypass off) | 41 603 | 1 | 8 | 0.42 |
| Static shadow (on) | **137 090** | **0** | **1** | **0.00** |

**3.3x** the throughput and **zero** proxy CPU for the asset tier.  Over the
LAN the link is the limit (12 871 -> 13 171 req/s); the gain there is server
headroom, not client-visible bandwidth.

Page tiers are unchanged because they still pass through Anubis:

| Tier | 1.21.16 | 1.21.17 |
|---|---:|---:|
| WP guest home (cached) | 7 442 | 7 630 |
| XF guest home (cached) | 10 704 | 10 701 |

HTTP semantics on the fast path: `HEAD` 200, `Range` 206, conditional
(`If-Modified-Since`) 304, HTTP/2 200 with `content-type: text/css` and the
application's 1-year `expires`/`Cache-Control`; a missing `.css` falls back
through Anubis and returns the application's 404.

dynamic backend socket: refused.  `www-data` on the dynamic backend socket:
refused (directory `0750 root:anubis` unchanged).

**61/61**, functional suite **0 unexpected responses / 0 PHP diagnostics /
0 XenForo error rows**.

## 6. Restore

`--purge all` + `restore-baseline.sh` returned the host to the recorded
baseline: 526 packages (0 added/removed/changed), 0 enabled-unit changes,
crontab empty, all managed trees and units absent, `tcp_bbr` unloaded.
The only `/etc` delta is the four shadow-utils backup files (`passwd-`,
`group-`, `shadow-`, `gshadow-`), which are regenerated snapshots written by
`useradd`/`userdel` while the Anubis service account was created and removed;
the live user/group databases themselves match the baseline byte-for-byte.
`/run/angie`, `/run/angie-static` and `/root/audit` were removed and `/tmp`
was cleared.

Artifacts from the run (install/optimize/disable logs, security and functional
suite output, final manifest and delta) were collected on the workstation; the
seed data and session cookies used by the audit are not committed.
