# Audit — 1.21.60 (web-server shootout, install/security fixes)

Date: 2026-11-23
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe,
Ubuntu 26.04.1, kernel 7.0.0-43).  This cycle ran with `mitigations=off`
(`--basic mitigations=off`, applied at boot) because that is the recorded
configuration of this host; the previous cycle's numbers were taken with
PTI/IBRS on and are not directly comparable.  Pair:
`server-configs-nginx` 1.6.53.  Applications: WordPress 7.1.4, XenForo
2.3.13, Chevereto 4.5.9-pro, deployed with `deploy-three-apps.sh`
(400 posts / 300 comments, 200 threads / 2,600 posts, one uploaded image).

Primary focus: which web server performs best for these three
applications.  Candidates: Angie 1.12.5, nginx 1.28.3, FreeNginx 1.31.5,
OpenResty 1.31.8.1, Tengine 3.1.0 (nginx 1.24 core), Caddy 2.11.9 and
OpenLiteSpeed 1.9.4.

## 1. Findings fixed

Ranked by impact.  Every fix has a test or a live reproduction below.

### 1.1 Fresh installs failed at the swap step (high)

`lib/os.sh:create_swap_file` created `/swapfile.new`, ran `mkswap`, then
`swapon /swapfile.new`, and only afterwards `mv /swapfile.new /swapfile`.
Linux refuses `rename(2)` on a file that is active swap (`EPERM`), so every
fresh `--basic swap=SIZE` died:

```
mv: cannot move '/swapfile.new' to '/swapfile': Operation not permitted
[FAIL] Could not move the new swap file into place
[WARN] basic FAILED after 00:00:06
```

The failing `--basic` skipped sysctl, PAM limits, udev, cron and the UFW
pass; the rest of the install continued, so the run ended `FAILURE` with a
half-tuned host.  This was reproduced on the first install of this cycle
(1.21.59, pristine 696-package host).

Fix: `mkswap` validates the file while it is still inactive; `swapoff`
releases the old file; the old file is renamed to `/swapfile.old` (not
deleted); the new file is renamed into place and only then `swapon`ned.  A
failed `swapon` removes the new file and puts the old one back.  The 64 MiB
floor now lives in `validate_all` (`lib/validate.sh:634`) so a dry run
rejects `swap=1M` before hostname/timezone/DNS are touched.  Six new
source-order checks in `tests/test-tuning.sh` and two dry-run rows.
Verified live: `basic OK`, `/swapfile` 8 GiB active.

### 1.2 A direct client could choose PHP's forwarded identity (high, security)

`http.d/https_map.conf` rebuilt the `HTTPS` flag from `X-Forwarded-Proto`
only for a trusted peer, but every other forwarded header still reached PHP
as the client sent it: `X-Forwarded-Host`, `X-Forwarded-Proto`,
`X-Forwarded-For`, `X-Real-IP`, `Forwarded`.  A cache MISS could render
absolute URLs for an attacker's host (then be stored), and app-level IP
allowlists or audit logs could be spoofed.

Fix: `http.d/https_map.conf` defines `$trusted_forwarder` (Unix socket,
loopback, or `custom.d/trusted_proxies.map`); `snippets/fastcgi-php-common.conf`
overrides the headers with the normalised host, public port/scheme and the
trusted header or the direct peer, and blanks `Forwarded` and
`X-HTTP-Method-Override`.  Live probe from the public address with spoofed
headers:

| header sent | PHP saw |
|---|---|
| `X-Real-IP: 203.0.113.9` | `192.0.2.10` (the real peer) |
| `X-Forwarded-For: 203.0.113.9` | `192.0.2.10` |
| `X-Forwarded-Host: evil.example` | `wp.test.local` |
| `X-Forwarded-Proto: http` | `https` |
| `Forwarded: for=203.0.113.9` | unset |

From the loopback peer (Anubis, a local terminator) the header is still
passed, which is what the integration needs.

### 1.3 `--optimize` rebound a hand-managed Elasticsearch node to localhost (high)

`elasticsearch_write_performance_block` always commented `http.host` and
`transport.host`.  An adopted node that binds with `http.host: 0.0.0.0` and
has no `network.host` was left with no bind directive, so it fell back to
localhost after the restart; the health probe then queried the new local
endpoint and reported success.  Now those two keys are commented only when
`network.host` is present (the managed base block or an adopted node that
already sets it).  Unit tests cover both shapes.

### 1.4 `SETUP_CF_SELF_SIGNED=0` was not persisted (medium)

The README promises `CF_SELF_SIGNED=0` in `/etc/default/setup-tuning`, but
no writer existed: the next plain `--optimize` re-enabled the certificate
migration and certbot retirement.  `CF_SELF_SIGNED_PERSIST` now mirrors the
other feature-choice flags and persists on an apply (never on a dry run).

### 1.5 `LIMIT_REQ_EXEMPT` was written into a root-sourced file unquoted (medium, security)

`persist_tuning_var` wrote `KEY="value"`.  A value containing a quote or
`$(...)` became shell code when the host file was sourced as root on the
next run.  Values are now written with `%q`, which keeps them data.  A test
persists an injection-shaped value and sources the file.

### 1.6 Missing security headers and a needless `sendfile off` (medium, config pair)

* Flarum's two PHP locations replaced the server-level header set and
  dropped `X-Frame-Options`; both now include it.
* XenForo's `/js/`, `/styles/` and `/data/` locations replaced the header
  set and lost CORS, Referrer-Policy, Permissions-Policy and XFO; all are
  included again.
* Chevereto's `/images/` location had `sendfile off` (read/write copies on
  the media hot path) and added a second `Cache-Control` on top of the
  inherited `expires`.  It now uses the global sendfile path, sets
  `expires off`, and carries the same security/CORS set.
* XenForo's `/proxy.php`, `/css.php`, `/webmanifest.php`, `/sitemap.php`
  cache stored every unique query on its first request for an hour
  (`fastcgi_cache_min_uses` was missing).  Now `min_uses 2` with background
  update, like the page cache.

### 1.7 Open issues (not fixed this cycle)

* The WordPress/XenForo/Chevereto/Flarum guest caches are default-allow for
  unknown cookies and routes.  A plugin session cookie outside the list
  (WPML/Polylang/WooCommerce Multilingual, a custom SSO route) can render a
  personalised page that is then stored for a guest.  Making the decision
  default-deny needs an allowlist per application and a compatibility pass;
  it is the next security cycle's first item.
* The README says `SETUP_WP_DB_SPLIT`, `SETUP_WP_ALLOW_FILE_MODS`,
  `SETUP_UFW_SSH_LIMIT`, `SETUP_PURGE_MALWARE`, `SETUP_CHEV_GUEST_CACHE`
  and `SETUP_ANUBIS_LANGUAGE` are persisted; they are not, and the code
  reads only the environment names.  Documented as drift; the opt-outs are
  re-applied on every `--optimize`.
* `install_mariadb` writes the tuning drop-in before validating it and does
  not restore the old tree if MariaDB rejects it (the `--optimize` path
  does).  A future MariaDB can leave a host that cannot restart.
* Cache zones are rewritten from the memory plan by setup.sh, but the
  canonical tree still ships 1 GiB (`fastcgicache_chev`) and 256 MiB zones
  with no `min_free`; a direct (non-setup) deployment on a small VPS can
  reserve ~1.8 GB of shared memory.
* `opt_backup` ignores a failed `cp`, so a later rollback can be a no-op.

## 2. Web-server shootout

### 2.1 Method

* One server on `:443` at a time, started as a transient systemd unit so
  its CPU is the unit's cgroup `usage_usec` delta divided by the requests
  `wrk` completed.  The production stack was stopped; PHP-FPM 8.5,
  MariaDB, Valkey and the application files stayed the same.
* Identical minimal vhosts for every candidate: same document roots,
  `try_files` semantics, TLS certificates, gzip level, keepalive, open file
  cache, FastCGI parameters.  nginx-family servers also got the same
  `fastcgi_cache` (key `host|method|uri|encoding`, any cookie bypasses,
  `min_uses 1`, 60 s TTL, `ignore_headers Vary Set-Cookie`), which is the
  production policy in one file.
* 9 tiers: two static files, a 16 KB PHP endpoint, cached guest pages for
  the three apps, an uncached Chevereto page, and WordPress/XenForo member
  pages.  Static and the PHP endpoint were measured with
  `Accept-Encoding: identity` so per-request compression did not hide the
  server path; app tiers used `gzip`.
* `wrk -t4 -c100 -d8s`, 2 s warm-up, 3 rounds; servers rotate within each
  round so the first slot does not keep the CPU-boost head start.  Median
  and min-max spread are reported.  Run-to-run spread on this desktop-class
  CPU is 10-45 % for static/PHP micro tiers and 3-10 % for cached tiers;
  differences inside the spread are called noise.
* Caddy has no generic FastCGI/proxy cache in its standard build, so its
  guest rows are uncached by design.  OpenLiteSpeed is discussed in 2.3.

What the table says:

* **The nginx family is one server with several logos.**  On the three
  cached tiers the medians are 108.9-138.9k (WP), 116.8-140.8k (Chev) and
  117.2-138.9k (XF); the per-tier spread is 4-49 %, and no build wins all
  three applications.  Angie, nginx and FreeNginx are within 1-12 % of each
  other on every tier; OpenResty and Tengine move around inside the spread.
  There is no consistent winner to justify a migration.
* **Member pages are the application, not the server.**  154-157 req/s for
  WordPress and 270-276 for XenForo on every candidate, with 0.4-1.9 %
  spread.  Caddy does the same work with 78 MB of RSS instead of ~490 MB.
* **The generic cache is a 100-800x factor.**  A cached WordPress post is
  126k req/s; the same page through Caddy (no cache) is 158.  XenForo
  124.8k vs 370 (337x); Chevereto 133.6k vs 1,203 (111x).  The uncached
  Chevereto page is 1,203-1,275 on every server, so the gap is the cache,
  not the engine.
* **Caddy's static path is competitive** (26.1-28.5k vs 20.8-30.7k), and
  its real-application uncached page is only 5 % behind (1,203 vs 1,274).
  Its PHP-micro path is 22.0k against 30.5-36.9k for the FastCGI servers
  (34 % slower), and it has nowhere to put a rendered page.
* **RSS:** Caddy 78 MB; nginx-family 470-500 MB with 12 workers and a
  256 MB cache zone.  On a 62 GB host that is noise; on a 1 GB VPS the
  worker count, not the RSS, is the limit.

The production Angie configuration (maps, security headers, rate limits,
Brotli) answered a single loopback pass at 116-122k WordPress, 145-158k
XenForo and 150k Chevereto cached, so the minimal benchmark vhosts are not
flattering Angie.

### 2.3 OpenLiteSpeed

OpenLiteSpeed 1.9.4 was installed from the vendor repository and started,
but it is not in the measured table.  Two reasons, both architectural:

1. Its generic page cache does not exist: the LSCache module only stores
   responses that an application plugin (the WordPress LSCache plugin)
   marks, and Chevereto/XenForo have no such plugin.  A guest request is a
   PHP render, exactly as in Caddy's row.
2. Its fast path is LSAPI (`lsphp`), a different PHP SAPI from the
   PHP-FPM pool every other candidate shares.  Measuring it against
   PHP-FPM would compare two PHP builds, not two web servers; measuring it
   with FastCGI would remove the only advantage OLS has.

A static-only OLS number would not answer the application question, so it
is excluded rather than reported as if it were comparable.

### 3a. Focused before/after

**Chevereto media, `sendfile` on/off** (4 MB image, 20 connections, 5 s, three
rotated rounds): off 812 / 905 / 838 (median 838), on 857 / 854 / 837
(median 854).  +1.9 %, inside the 11 % spread: the zero-copy path is the
correct default, but on this host and file size it is not a throughput win.
The change ships for correctness and CPU, not for a claimed gain.

**XenForo one-shot query pollution:** not measurable on the generated
`--domain app=xf` vhost, because that vhost uses `h5bp/php_xf.conf`
(uncached `/css.php`) and not `h5bp/xf2.conf` with
`h5bp/php_xf_proxy.conf`.  The fix is verified by the tree check and applies
to vhosts built from `xf2.conf`; on this host `/css.php` is intentionally a
normal PHP request.

**Forwarded headers:** probe from the public address with spoofed
`X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto` and
`Forwarded`; PHP saw the real peer, the normalised host, `https`, and an
empty `Forwarded`.  From the loopback peer (the Anubis path) the header is
still passed.  The table in 1.2 uses documentation addresses for the host's
real address.
