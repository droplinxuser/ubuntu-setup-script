# Audit — 1.21.70 (Angie from source, hardening, libsystemd, compression, PGO/AutoFDO, glibc)

Date: 2026-11-25
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe, Ubuntu
26.04.1, kernel 7.0.0-44), restored to its baseline, then freshly installed
with WordPress 7.1.4, XenForo 2.3.13 and Chevereto 4.5.9-pro
(`deploy-three-apps.sh`, standard data set).  CPU mitigations off (operator
request).  Pair: `server-configs-nginx` 1.6.60.

## 1. Requests

1. Compile glibc, libm and libsystemd from source too.
2. A smaller, leaner compiled php-fpm: nothing the three applications do not use.
3. Drop the `lean`/`source` aliases of `SETUP_PHP_BUILD=clang`.
4. Measure Brotli and gzip built from their latest sources.
5. Fix `server-configs-nginx`'s CI.
6. Compile Angie from source too, with only the modules the configuration
   uses, if it is faster (guest caching especially).
7. (Mid-cycle) Do the builds use x86-64-v3/v4/znver4, PGO, LTO and BOLT, as
   CachyOS does?

## 2. Method

PHP 8.5.13, the managed `php.ini` (OPcache 512 MB, tracing JIT 64 MB,
`opcache.huge_code_pages = On`), 12 static workers; loopback `wrk` at 100
connections, 12 s per tier, 5 rounds with the arm order rotated, clock pinned
at 3.6 GHz (`bench-php-sources.sh`; `SWITCH=switch-angie-arm.sh` for the
Angie arms).  Compression: `compression-bench.sh`, Angie and PHP CPU per
request from their cgroups, 5 rotated rounds.  Every candidate was a build
of `tools/php-fpm-build.sh` or `tools/angie-build.sh` (or the Angie prototype
it grew from), copied to `/opt/php-TAG`/`/opt/angie-TAG` for the A/B.

## 3. Findings

### 3.1 The compiled php-fpm had no hardening (security, fixed)

Ubuntu's gcc enables a stack protector, stack-clash probes,
`_FORTIFY_SOURCE`, CET and full RELRO by default; upstream clang enables
none.  The 1.21.68/1.21.69 builds ran without all five while the package has
them.  1.21.70 builds every library and PHP with
`-fstack-protector-strong -fstack-clash-protection -D_FORTIFY_SOURCE=3
-fcf-protection=full` and links `-z relro -z now`, unconditionally.  Cost,
LTO builds before BOLT: XenForo thread -2.2 %, home -2.1 %, WordPress -0.7 %,
Chevereto uncached -0.5 % (table in 3.5).

### 3.2 glibc, libm, libsystemd

* **libsystemd:** PHP-FPM calls only `sd_notify()`/`sd_notifyf()`.  A static
  implementation of the protocol replaces the library; a unit test checks the
  datagram systemd would read.  The build now links only libc and libm.
* **glibc 2.44 from source, static:** builds with gcc (glibc does not build
  with clang) once Ubuntu's multiarch kernel headers are gathered into one
  tree, and links with `-static-pie`.  Two failures followed:
  * PHP's configure test programs segfaulted: PHP adds `-Wl,-rpath` for every
    `--with-x=DIR`, and a static-pie binary with a RUNPATH crashes at
    startup.  Fixed with `--disable-rpath` (kept for every build).
  * php-fpm crashed at startup with `opcache.huge_code_pages`: the remap stub
    lives in its own section but calls `mmap`/`memcpy`, which in a static
    binary are inside the `.text` being remapped.  Patched (inline syscalls,
    an inline copy, and no `errno`, whose accessor is in `.text` too and is
    already unmapped when the hugetlb mmap fails); the build then started
    with huge code pages and passed every check, linking nothing at all.
  * It still served nothing: the workers aborted with "Fatal glibc error:
    rtld_static_init.c:90 (__rtld_static_init): assertion failed: guard_sym !=
    NULL" and the master respawned them in a loop (zombies, hung requests;
    the same symptom as the first static arm with huge pages off).  Switching
    to www-data makes glibc read `/etc/nsswitch.conf` (`files systemd`) and
    `dlopen` Ubuntu's `libnss_systemd`, which loads Ubuntu's glibc 2.43 into a
    binary linked with 2.44.
  Verdict: a source-built glibc needs its own NSS modules and runtime beside
  the binary.  Not shipped; the experiment code (glibc build, static modes,
  stub patch) is not kept.  glibc stays Ubuntu's, as for every package.

### 3.5 PHP build variants (CachyOS question)

`-march=native` is already more specific than x86-64-v3/v4/znver4: each
server compiles for its own CPU (a v4/znver4 binary cannot run on this
AVX2-only Xeon at all).  ThinLTO and BOLT were already in.  The missing piece
was compiler feedback before BOLT:

| vs package (req/s) | XF thread | XF home | WP home | Chev uncached |
|---|---:|---:|---:|---:|
| package | 218 | 409 | 139 | 1,474 |
| 1.21.69 flags, LTO | +6.4 % | +4.4 % | +2.9 % | +2.8 % |
| hardened, LTO | +4.1 % | +2.2 % | +2.2 % | +2.3 % |
| hardened, LTO, zlib-ng | +3.7 % | +2.4 % | +2.9 % | +9.8 % |
| hardened, LTO + BOLT | **+10.6 %** | **+6.8 %** | **+6.5 %** | **+3.8 %** |
| instrumented PGO + BOLT | +8.3 % | +6.6 % | +7.2 % | +4.9 % |
| AutoFDO + BOLT | +6.4 % | +3.7 % | +3.6 % | +0.6 % |

Instrumented PGO: `-fprofile-generate`, trained with `exercise-apps.sh` and
30 s per member tier, merged with `llvm-profdata`, then BOLT (2,504 functions
profiled).  Mixed against LTO + BOLT (-2 % to +1 %): not shipped.  AutoFDO:
LBR samples of a line-table build with huge code pages off, `llvm-profgen`
(the binary path must be the running one), `-fprofile-sample-use`, BOLT:
slower everywhere: not shipped.

### 3.6 Size

* Stripped, the LTO php-fpm is 42.2 MB (59.7 MB with symbols and BOLT's
  relocations, which `php-fpm.lto` keeps); the BOLTed binary php-fpm runs is
  48.4 MB (1.21.69 shipped 60.4 MB unstripped).  Code is 18.2 MB, read-only
  data 15.8 MB, of which 10.4 MB is fileinfo's built-in magic database
  (which `finfo` needs), 0.4 MB timezone data and lexbor's Unicode tables;
  the rest is mostly the JIT, OpenSSL and libxml2.
* Trimmed: `xmlreader`; OpenSSL ciphers and protocols nobody here uses
  (IDEA, Camellia, SEED, ARIA, SM2/3/4, Whirlpool, MD4, RC2, RC4, MDC2, CAST,
  Blowfish, GOST, SRP, DTLS, SSL 3, binary curves, compression); GNU
  libiconv's extra CJK tables; unused sections (`--gc-sections`) and
  identical functions (`--icf=safe`).  The candidate must now show no module
  outside the app set and PHP's fixed core.
* The compiled Angie is 13.5 MB stripped with OpenSSL, PCRE2 and zlib-ng
  inside; both link only libc and libm.

### 3.7 server-configs-nginx CI

The h5bp workflows (an nginx container testing upstream's `nginx.conf`)
were deleted on 4 November and nothing replaced them.  1.6.60 adds a
workflow that installs Angie and its Brotli module from Angie's repository,
installs the tree as setup.sh does and runs `angie -t` on the base tree and
with all 14 vhost templates; a lint job runs ShellCheck and the
public-address check.  First run green.

### 3.8 Other

* zlib.net stalled after 200 KB during a test build; `--max-time 1800`
  would have waited 30 minutes before the GitHub fallback.  Downloads now fail
  over below 1 KB/s for 30 s.
* `-march=native` ties a build to its CPU: `build.info` records the model,
  and a build started on another one goes back to the package and rebuilds
  (php-fpm and Angie).

## 4. Validation

Through `setup.sh` on the fresh install (`a1`):

* unit 1,681 checks (1 environment skip), dry runs 227, all passing;
* `SETUP_PHP_BUILD=clang SETUP_ANGIE_BUILD=clang --optimize` under mixed
  load: both built and BOLTed from live traffic in 18 minutes (libraries
  included); both binaries link only libc and libm; Angie and php-fpm ran the
  builds;
* on the two builds: security 78/78, cookie 105/105, functional suite 0
  failures;
* a plain `--optimize`: both builds reported current;
* `=package` for both: drop-ins and both builds removed.

Found and fixed during validation:

* `install_stripped` (new) ran `ls` on a glob that matched nothing when the
  GitHub LLVM fallback was absent; under `set -e`/`pipefail` that ended both
  tools silently just before installing the binary.  The first `--optimize`
  reported both builds FAILED and left the packages serving (the fallback
  worked; suites passed on the packages).  Fixed, with a unit test.
* The shared LLVM toolchain survived `=package`: the PHP removal kept its
  logs (so its directory) and deferred to Angie, Angie's removal saw that
  directory and deferred to PHP.  Each now checks the other's build and the
  PHP removal deletes its logs; a unit test removes them in both orders.
