# setup.sh 1.21.3 / server-configs-nginx 1.6.26 audit

Date: 2026-11-13
Host: `16c-32g-1T` (SER8), Ubuntu 26.04.1 LTS, 16 logical CPUs, 27 812 MiB
RAM, NVMe, bare metal, kernel 7.0.0-43.
Stack: `--basic time=Asia/Manila --angie --php ver=8.5 --mariadb user=admin
pass=temp size=auto --valkey --elastic host=localhost ram=4g --others all`.
Applications: WordPress 7.1.4, XenForo 2.3.13, Chevereto 4.5.9 (PHP 8.5, and
PHP 8.4 through `--upgrade-php`).

Method: the 1.21.2 code was installed on the pristine host and measured
("before").  Two reviewers that had not seen earlier audits read the shell
libraries and the Angie tree; every finding acted on was first reproduced on
the host, fixed, and re-probed after `setup.sh --optimize`.

## 4. PHP compatibility

| Version | WordPress 7.1.4 | XenForo 2.3.13 | Chevereto 4.5.9 |
|---|---|---|---|
| 8.4.27 | clean at run time | works; 7 vendor deprecations at run time with E_ALL (implicit nullable parameters in league/flysystem, league/event, joypixels) | **first request after every opcache reset fails**: the vendored intervention/image deprecation is turned into an exception at shutdown and the session is not saved, so a login right after a PHP-FPM reload answers 403 (reproduced twice: cold 403, warm 302) |
| 8.5.12 | clean at run time | works; with XenForo's debug mode and E_ALL its own `src/XF/App.php` raises "Using null as an array offset is deprecated" (new in 8.5) and member pages answer 500 in that mode only; production mode logs nothing | clean; cold and warm logins both succeed |
| 8.6.0 RC5 | not testable | not testable | not testable |

Lint (`php -l`, E_ALL) finds deprecations in vendored libraries on both
versions (WordPress 18 in sodium_compat's 32-bit classes, XenForo 56-60,
Chevereto 480) and two files in XenForo's vendor tree that do not parse on
8.x and are never loaded.  PHP 8.6 cannot run the stack yet:
`php8.6-redis`, `php8.6-imagick` and `php8.6-igbinary` are not published
(`--upgrade-php=8.6 --dry-run` reports all three).

Newest fully working version today: PHP 8.5 for all three applications.
Chevereto 4.5.9 was requested on 8.4; on this stack it is more reliable on
8.5, and 8.4 and 8.5 receive byte-identical managed settings, so the
difference is PHP's.

Operational note: Chevereto keeps PHP sessions as files in `/tmp` and starts
one for every uncached guest request.  The load runs left 503 102 `sess_*`
files there; nothing collects them (`phpsessionclean` only covers
`/var/lib/php/sessions`).  Set `CHEVERETO_SESSION_SAVE_HANDLER=redis` (or a
`CHEVERETO_SESSION_SAVE_PATH` under `/var/lib/php/sessions`) on a busy site.

## 6. Reviewed and left as is

- The Angie tree is downloaded from the `main` branch at every install and
  `--optimize` without a checksum; pin `CONFIG_REPO_REF` to a tag where
  change control matters.
- `/etc/sysctl.conf` is replaced as a whole; operator keys outside the
  profile are lost.
- `--purge basic` removes the whole managed cron block (backups, wp-cron).
- The memory plan counts only the `www` pool and an explicit `children=` is
  not re-budgeted.
- Storage class inside an LXC container follows the host's disk inventory.
- No `limit_conn`; a cache-busting GET flood is bounded only by 100 GET/s
  per address.
- A Redis protected by `requirepass` is probed without the password.
