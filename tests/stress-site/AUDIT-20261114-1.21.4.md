## 3. Performance

### 3.1 Distribution defaults vs shipped tuning (loopback wrk, 64 connections, 8 s)

Distribution-like profile: `pm=dynamic`, `pm.max_children=5`, OPcache 128 MB,
JIT off, default realpath cache.  Shipped profile: `pm=static`,
`pm.max_children=16`, OPcache 512 MB, tracing JIT 64 MB, realpath cache tuned.

| Tier | defaults | shipped | change |
|---|---:|---:|---:|
| WordPress member home | 131 | **278** | +112% |
| WordPress member post | 108 | **223** | +106% |
| XenForo member thread | 231 | **458** | +98% |
| Chevereto guest home (uncached) | 1 528 | **2 677** | +75% |
| WordPress guest home (cached) | 67 252 | 63 477 | link/Angie-bound |
| XenForo guest home (cached) | 81 185 | 82 189 | link/Angie-bound |

Member pages are CPU-bound in PHP; the pool depth is the dominant lever.
Cached guest pages never enter PHP and are unchanged.

### 3.2 OPcache JIT sweep (static 16, 64 connections, 8 s)

| JIT profile | XenForo member thread | WordPress member home | Chevereto guest home |
|---|---:|---:|---:|
| off | 470 | 258 | 2 609 |

### 3.4 From the workstation (oha 1.16, Wi-Fi LAN, 100/50 connections, 10 s)

The workstation was exempted from the per-IP limiter only for the run
(`SETUP_LIMIT_REQ_EXEMPT=192.168.1.200`).  Every response was 2xx; the
`aborted due to deadline` counts are oha's in-flight requests at `-z`.

| Tier | req/s | p50 | p99 |
|---|---:|---:|---:|
| XenForo guest home (cached) | 6 502 | 13.7 ms | 30.2 ms |
| XenForo guest home (uncached) | 1 072 | 45.5 ms | 60.7 ms |
| XenForo member home | 862 | 54.9 ms | 225.8 ms |
| XenForo member thread | 500 | 98.5 ms | 127.2 ms |
| WordPress guest home (cached) | 5 082 | 18.2 ms | 30.1 ms |
| WordPress guest home (uncached) | 270 | 182.9 ms | 274.3 ms |
| WordPress member home | 260 | 193.6 ms | 222.7 ms |
| WordPress member post | 212 | 232.5 ms | 294.9 ms |
| Chevereto guest explore (cached) | 5 345 | — | — |
| Chevereto guest home (uncached) | 2 310 | — | — |
| Chevereto member explore | 17 | — | — |

The Chevereto member result is per-session PHP file-locking: all 100
connections share one `PHPSESSID`, and PHP serialises requests that hold the
same session file.  It is not a server limit; per-user traffic is serialised
by design, and different users run in parallel.  Use a Redis session handler
(or one FPM pool per tenant) if a single account must issue concurrent
requests.
