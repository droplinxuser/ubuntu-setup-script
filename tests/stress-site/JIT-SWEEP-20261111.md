# OPcache JIT sweep - 2026-11-11

Host: `audit-host` (16 logical CPUs, 27 812 MiB RAM, NVMe, bare metal,
Ubuntu 26.04.1, PHP 8.5.12-FPM).  Load: `oha` 1.16.0 from the macOS
workstation over the LAN, 100 connections, 8 s per profile after a 3 s
warm-up, authenticated XenForo thread page
(`/index.php?threads/benchmark-thread-1-1b9c65.1/`, 60 members / 200 threads /
2 600 posts).  Each profile was written as a `zzz-audit.ini` drop-in (it sorts
after the managed `zz-setup-optimize.ini`) and PHP-FPM was reloaded.
`php-ms/req` is PHP-FPM cgroup CPU divided by successful requests.

`opcache.jit_max_root_traces`, `jit_max_side_traces` and
`jit_max_polymorphic_calls` were tested one at a time and then together
(`combined`); none beat the defaults.  Run-to-run noise on this Wi-Fi link is
about ±2% (the same tracing64 profile measured 613-625 req/s in three
standalone runs), so the 607-619 rows are ties, not wins.

## Conclusion

Tracing at 64 MB with PHP's default hotness thresholds (64/127/16/64) is the
right default and stays in `lib/web.sh`.  The JIT is worth **+5.9%** over JIT
off (614 vs 580 req/s, 22.73 vs 24.53 ms PHP CPU per request) and **+7.9%**
over function JIT.  A 32 MB or 128 MB buffer is within noise of 64 MB; the
64 MB buffer costs no measurable CPU, so there is no reason to shrink it
(the used trace buffer is ~850 KB).  Lowering the hotness thresholds
("aggressive") or raising them ("conservative") only trades compilation CPU
for interpreted execution at this CPU count; the 1-2 CPU conservative profile
in `php_jit_threshold_lines` is unchanged.
