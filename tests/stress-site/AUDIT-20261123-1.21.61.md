# Audit — 1.21.61 (which PHP server, and a guest-cache leak)

Date: 2026-11-23
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe,
Ubuntu 26.04.1, kernel 7.0.0-43), returned to its pristine 696-package
manifest before the install and restored to it afterwards.  This cycle ran
with `mitigations=off` (the recorded configuration of this host).  Pair:
`server-configs-nginx` 1.6.54.  Applications: WordPress 7.1.4, XenForo 2.3.13,
Chevereto 4.5.9-pro, deployed with `deploy-three-apps.sh` (400 posts / 300
comments, 200 threads / 2,600 posts, one uploaded image).

Primary focus: which PHP execution model performs best for XenForo,
WordPress and Chevereto.  Candidates: PHP-FPM 8.5, PHP-CGI 8.5, FrankenPHP
1.14.0 (classic and worker, embedded PHP 8.6.0), RoadRunner 3.0.1, Swoole
6.2, OpenSwoole (Sury build), Workerman 5.2, ReactPHP 1.12, AMPHP 3.4 and
PHP's built-in server.

## 1. Findings fixed

Ranked by impact.  Every fix has a test or a live reproduction below.

### 1.1 A guest cache could store one visitor's page for everyone (high, security)

The four guest caches bypassed on a fixed list of session cookie names and
treated every other cookie as page-neutral.  A plugin session, an SSO token
or a language selector outside that list reached the application while the
response was stored under the clean URL: a cross-user page leak, and a cache
that fills with per-visitor entries.  This was the first item in the previous
report's open list.

Fix (`server-configs-nginx` 1.6.54): `http.d/fastcgi_cache.conf` defines
`$guest_cookie_unlisted`, one PCRE pass per request (no regex for the common
no-Cookie request) that accepts only page-neutral names — analytics and
consent cookies, CDN/bot-management cookies, the Anubis pass cookie, and the
first-party guest cookies of the supported apps (WordPress
`wordpress_test_cookie`/`comment_author`, XenForo `xf_csrf` and the style and
language cookies that are already in the cache key).  Every application
decision (`$skip_cache`, `$xf_guest_cacheable`, `$chev_guest_cacheable`,
`$flarum_guest_cacheable`) and every `*_no_cache`/`*_cache_bypass` line now
includes it; `setup.sh --optimize` adds the variable to XenForo lines written
by older releases.

Verified live (86/86 cookie suite): an unknown cookie is `BYPASS`, an
analytics-only cookie still reaches `HIT`; a language selector still bypasses
because it changes the page.

The end-to-end Anubis run caught a regression the source tests could not:
Anubis sets `techaro.lol-anubis-auth-*` on every visitor, and the first
default-deny version treated it as unknown — every request on an
Anubis-fronted host became a cache `BYPASS` (measured 1.5 ms of Angie CPU per
sequential request and a PHP render).  The pass cookie is now in the
allowlist; the same request is a `HIT` and Anubis costs 0.0008 ms of CPU per
request (500 sequential requests, cgroup delta).

### 1.2 A rejected MariaDB tuning file could leave a host that cannot restart (high)

`install_mariadb` wrote `50-server.cnf` and the tuning drop-in, then validated
them with `mariadbd --help --verbose` and returned 1 on rejection — but left
the rejected files in place.  MariaDB kept running with the old in-memory
configuration, so the failure only appeared at the next restart or reboot.
The install path now snapshots `/etc/mysql/mariadb.conf.d` before the rewrite
and moves the rejected tree to `/tmp` with the old one back, the same
rollback `--optimize` already had.  (The generated files were valid on this
host; the rollback path is covered by the source-order test.)

### 1.3 A failed backup made a later rollback a no-op (medium)

`opt_backup` ignored `cp -a`'s status.  A full disk or a permission error left
a partial snapshot (or none) and the rollback then restored nothing.  It now
removes the partial copy and stops before any change.

### 1.4 Cache paths had no filesystem headroom (medium)

A host that deploys the Angie tree without `setup.sh` could let a 16 GB cache
fill its filesystem, and the Chevereto zone defaulted to 1 GiB (large for a
small VPS).  Every shipped `fastcgi_cache_path`/`proxy_cache_path` now sets
`min_free=512m`, and the Chevereto default drops to 512 MiB.  `setup.sh` still
sizes every zone from the host's RAM (512 MiB / 3.9 GiB on this host) and the
`min_free` survives the rewrite.

### 1.5 README claimed persistence that the code did not have (low, docs)

`SETUP_ANUBIS_LANGUAGE`, `SETUP_UFW_SSH_LIMIT`, `SETUP_WP_DB_SPLIT`,
`SETUP_WP_ALLOW_FILE_MODS`, `SETUP_WP_GUEST_CACHE`, `SETUP_CHEV_GUEST_CACHE`
and `SETUP_PURGE_MALWARE` are environment inputs, not values written to
`/etc/default/setup-tuning`.  The table now says which choices are persisted
and which are one-run inputs.  Making the rest persistent is an open item.

### 1.6 Chevereto's guest cache only serves cookie-less clients (finding, not fixed)

Chevereto sets `PHPSESSID` on every guest response, and the cache correctly
bypasses a PHP session because pages embed its CSRF token.  A returning guest
therefore never reads the cache; only first visits and bots do.  The
production tier measured 141k req/s with no cookie and 1,519 req/s for the
same page once a session exists.  Fixing it needs a per-route decision (cache
read-only pages, bypass forms) or an application change; both are
application-level work, not a server choice.

### 1.7 Open issues (not fixed this cycle)

* The persistence drift in 1.5 (implement, rather than document).
* MariaDB `--optimize` still validates a host's live config but only the
  install path now rolls back (verified equal on this host).
* Anubis' static-asset shadow and its CPU cost were measured only on the
  cached WordPress home this cycle; a full `exercise-apps.sh` through Anubis
  needs a cookie-aware runner.
* `SETUP_UPGRADE_PHP` 8.5 → 8.6 → 8.5 was not repeated: no PHP code changed
  this cycle, and the last report's 0:44 / 1:09 clean runs still apply.
  `--upgrade-php=8.6 --dry-run` was exercised by the matrix.

## 2. PHP application-server shootout

### 2.1 Method

Two layers, because they answer different questions.

* **Layer 2 (runtime ceiling).**  One application-shaped workload
  (`tests/stress-site/php-appsim/`): 60-file framework bootstrap, two
  MariaDB statements, one Valkey `GET`, a 13 KB template with 160 rows, a
  SHA-256 of the page and a JSON round-trip.  Every runtime gets the same
  Angie in front (FastCGI for FPM/CGI, `proxy_pass` for the HTTP runtimes),
  the same 12 workers/threads (ReactPHP and AMPHP: 12 event-loop processes
  with `SO_REUSEPORT`), the same OPcache and tracing JIT (`opcache.jit=tracing`,
  64 MB), gzip off, 64 connections, 8 s, 2 s warm-up, 3 rounds with the order
  reversed on even rounds.  CPU is the backend's cgroup `usage_usec` delta
  divided by the requests `wrk` completed; Angie's CPU is reported separately.
* **Layer 1 (the real applications).**  PHP-FPM, PHP-CGI and FrankenPHP serve
  the actual WordPress/XenForo/Chevereto document roots over TLS on :443, with
  no page cache (a cache would hide the PHP path), `Accept-Encoding: gzip`,
  100 connections, 8 s, 3 rounds.  PHP-CGI and FPM share the same minimal
  Angie vhost; FrankenPHP terminates TLS itself.  OpenLiteSpeed is excluded:
  its LSCache stores only plugin-marked responses (Chevereto and XenForo have
  no such plugin) and its fast path is LSAPI, a different PHP SAPI, so it
  would compare two PHP builds rather than two servers — the same reason as
  the previous report.

Run-to-run spread on this desktop-class CPU is 13-16 % for the FPM/CGI
group in layer 2 and 0.3-10 % for the application tiers.  Differences inside
the spread are called noise.  The first candidate of a round can keep a
frequency boost; the reversed order spreads that across candidates.

| ReactPHP 1.12 | 2165 | 11.1% | 27.85ms | 33.82ms | 0.279 | 0.091 | 72 |

What the table says:

* **The bootstrap is not where the time goes.**  The 60-file bootstrap costs
  ~0.05 ms with OPcache; the DB statements and the render dominate.  That is
  why FPM (which pays the bootstrap per request) and FrankenPHP worker (which
  does not) land within the same throughput band, and why the worker's win is
  visible only inside FrankenPHP: 7.6k → 9.6k req/s, p99 13.3 → 8.3 ms
  (+26 % throughput, -38 % p99) against classic mode.
* **The database/cache work dominates CPU, not the SAPI.**  FPM, CGI, the
  built-in server and FrankenPHP worker all sit at 0.60-0.65 ms of PHP CPU
  per request.  FrankenPHP classic (0.92) pays Caddy's per-request hop and
  the embedded runtime; RoadRunner (0.90) pays PSR-7 + Goridge; AMPHP (0.97)
  pays its request objects and the 12-process event loop.
* **Workerman/OpenSwoole are the only clear win, and they are a rewrite.**
  1.4-1.6x the throughput of FPM with 0.37-0.43 ms of CPU per request, and
  the lowest p99 in the group (5.7-7.8 ms).  They are persistent workers:
  every PHP file they touch must be safe to keep in memory (static state,
  leaked sessions, request data in `$_ENV`).  WordPress, XenForo and
  Chevereto are not written for that; using them means an application adapter
  (and an add-on for XenForo) with a compatibility pass, not a server swap.
* **ReactPHP is not a server ceiling.**  With 12 processes it still delivers
  only 2.2k req/s at 100 connections because each event loop is
  single-threaded and its p50 is 27.9 ms (queueing).  Its 0.28 ms CPU per
  request is the lowest of all, so it is efficient per request and wrong for
  this concurrency profile.
* **CGI is not slower than FPM here.**  It is within the spread and uses
  2-2.5x the memory (1.3 GB vs 537 MB in layer 1).  OPcache is shared through
  the file cache, but CGI has no process manager, no slow log and no graceful
  reload, so there is no reason to move a production host to it.

What the table says:

* **WordPress and XenForo are application-bound, not server-bound.**  143-157
  req/s for a WordPress post and 324-348 for a XenForo thread across three
  different execution models.  The spread between servers is smaller than the
  spread between the same server's rounds in several rows.
* **FrankenPHP is competitive on WordPress and XenForo, and 44 % slower on
  Chevereto.**  Chevereto's home page costs 11.15 ms of PHP CPU per request
  under FrankenPHP against 5.38 under FPM (830 vs 1,482 req/s), with no
  redirects or errors.  The other two applications show no win to justify the
  embedded PHP 8.6 runtime and its separate server.
* **CGI is 6-13 % faster than FPM on this workload and costs 2-2.5x the
  memory.**  It is inside or just outside the spread on the WordPress and
  XenForo tiers.  No production case: no pool manager, no slow log, no
  graceful reload, and 1.3 GB instead of 0.5 GB for 12 workers.

### 2.4 Verdict

**Keep PHP-FPM.**  No candidate beats it on the three applications by more
than the run-to-run spread: the app time is MariaDB and template work, not
the SAPI.  FrankenPHP worker mode is a real improvement over FrankenPHP
classic (+26 % throughput, -38 % p99 on the synthetic workload) but it still
does not beat FPM on this workload and cannot serve these three applications
without a worker-safe front controller; its classic mode is slower than FPM
and its Chevereto page is 44 % slower.  RoadRunner and AMPHP add per-request
abstraction and lose to FPM.  Swoole/OpenSwoole and Workerman are the only
1.4-1.6x CPU/throughput win, and they require the application to be ported to
a persistent worker — an application project with a state-safety audit, not a
server change.

For a WordPress/XenForo/Chevereto host the highest-leverage PHP change is
still what the guest cache does (100-800x on cached pages) and, for members,
fewer and faster database statements; a different PHP server moves the needle
by <10 % and can regress Chevereto by 44 %.
