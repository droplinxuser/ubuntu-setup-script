## 1. Defects fixed

### 1.1 certbot never retired on fleet hosts (1.21.48 regression)

`certbot_letsencrypt_users` greps `/root`, `/opt`, `/srv`, `/usr/local` and
`/home` for references to `/etc/letsencrypt`.  `tools/fleet-update.sh` keeps
the checkout (and a dated previous one) and its run logs in `/root`, and
`lib/web.sh`, `CHANGELOG.md` and every "certbot: kept ..." report line quote
that path.  So the scan always found the project itself, and the 1.21.48
certbot retirement could never run on a fleet host.  The unit tests set
`CERTBOT_EXTRA_ROOTS=""`, which hid it.

The scan now prunes copies of this project (a directory with `setup.sh`
next to `lib/web.sh`) and Angie configuration trees outside `/etc/angie`
(`angie.conf` next to `conf.d/templates`, i.e. a `server-configs-nginx`
checkout whose samples name certbot paths; the loaded configuration is still
read through `angie -T`), and skips `*.log` files.

Live check: certbot installed with both checkouts and a fake report log under
`/root`.  Before: "kept; /etc/letsencrypt is still used by
/root/work/server-configs-nginx/conf.d/templates/sample_sfs.conf".  After:
"purged (certbot python3-certbot) ... the old tree is kept in
/var/backups/setup-letsencrypt-...".

### 1.2 A full volatile-* Valkey cache ratcheted up 20% per run (1.21.49)

1.21.49 made `volatile-*` caches follow their data both ways.  A TTL-heavy
`volatile-lru` cache fills its maxmemory and evicts like an LRU cache, so
each `--optimize` read used == maxmemory and wrote +20%: 512 -> 614 -> 736 ...
up to the whole service budget.  A `volatile-*` cache that has evicted keys
since it started (`INFO stats evicted_keys > 0`) now counts as evicting and
keeps its size; one that has evicted nothing still follows its data.

### 1.3 Wildcard server names were glob-expanded (1.21.48)

`for name in $names` in the Cloudflare TLS move ran pathname expansion: a
`*.example.com` name could match a file in the current directory and be
checked as an exact name.  Now `read -ra`.

### 1.4 PHP-FPM restarts logged MariaDB warnings

Every PHP-FPM restart logged 12-13 `[Warning] Aborted connection ... (Got an
error reading communication packets)` lines: systemd stops php-fpm with
SIGTERM, which kills the workers while they hold XenForo's persistent
connection (`p:localhost`).  A/B under XenForo member load:

| Stop | Aborted connections | stop+start |
|---|---:|---:|
| `systemctl restart`, SIGTERM (before) | 12 | 244 ms |
| `systemctl reload` (USR2) | 0 | — |
| `systemctl restart`, `KillSignal=SIGQUIT` | 0 | 244 ms |

The PHP-FPM unit drop-in now sets `KillSignal=SIGQUIT` (graceful: workers
finish the request and close their connections; `TimeoutStopSec=15` still
bounds a stuck worker).  Applied by the install and `--optimize` through the
same writer; verified live: `KillSignal=3`, 0 warnings during `--optimize`
and on a restart under load.
