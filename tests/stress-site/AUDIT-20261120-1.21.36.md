# Audit — 1.21.36 performance cycle (Ubuntu 26.04.1, Angie 1.12.4, PHP 8.5/8.6)

Date: 2026-11-20
Host: OVH dedicated server, Intel Xeon E-2236 (Coffee Lake, 6C/12T), 62 GB,
md RAID0 over two PM983 NVMe, Ubuntu 26.04.1, 705-package baseline.
Pair: `server-configs-nginx` **1.6.48**.  Operator context: one SSH-key-only
administrator, no FTP or other users, every site behind Cloudflare.

Scope (operator request): CPU mitigations off, XenForo gzip handover to
Angie, lean regex/map cost on the cached path, tracking parameters out of
the guest-cache key, the security location chain made lean (low-value rules
removed), and PHP 8.6.0 against the three applications.

Method: every benchmark is loopback HTTPS (`wrk -t4 -c100 -d10s`, 2 s
warm-up, `Accept-Encoding: gzip`) and interleaved old/new in the same boot
unless stated.  Applications: WordPress 7.1.4, XenForo 2.3.13 (Hampel
Seeder: 20,060 users, 10,200 threads, 103,000 posts; SV RedisCache,
RedisFloodCheck, RedisViewCounter, StandardLib), Chevereto 4.5.9-pro, on
PHP 8.5.13.

## 1. CPU mitigations

Each state measured right after a fresh boot (Anubis off, XenForo gzip
split).  `mitigations=off` turns PTI, IBRS, MDS buffer clearing and
Retbleed mitigation off (`/sys/devices/system/cpu/vulnerabilities/*` read
"Vulnerable").

| Tier (req/s) | on | off | change |
|---|---:|---:|---:|
| XenForo guest cached | 104,880 / 97,608 | 125,795 / 115,647 | +19 % |
| WordPress guest cached | 84,522 / 84,646 | 105,953 / 105,993 | +25 % |
| Chevereto guest cached | 120,004 / 120,160 | 137,319 / 137,785 | +14 % |
| XenForo bypass | 360 / 345 | 393 / 363 | +7 % |
| member home | 315 / 292 | 331 / 307 | +5 % |
| member thread | 330 / 330 | 348 / 349 | +6 % |

The cached tiers are syscall- and TLS-bound (the PTI/IBRS cost); the PHP
tiers are user-space bound.  Implemented as `--basic mitigations=off`,
`--optimize mitigations=off` or `SETUP_CPU_MITIGATIONS=off`: a managed GRUB
drop-in that keeps the provider's own kernel options, persisted as
`CPU_MITIGATIONS`, removed by `mitigations=on` or `--purge basic`.  Verified
on the host: the kernel booted with `... console=ttyS1,115200n8
mitigations=off`; after `--purge basic` and a reboot the default returned.

## 2. XenForo compression

The request said to set `$config['enableGzip'] = true;` so that Angie
compresses pages.  `true` is XenForo's default (it compresses every page at
level 9), so the measured goal was implemented instead:

| Mode (req/s, two rounds) | guest cached | bypass | home | thread |
|---|---:|---:|---:|---:|
| XenForo for everyone (`true`) | 104,834 / 104,317 | 369 / 361 | 321 / 299 | 344 / 348 |
| **split: guests XenForo, members Angie** | 104,967 / 104,397 | 362 / 362 | 316 / 314 | **360 / 360** |
| Angie for everyone (`false`) | **6,741 / 6,843** | 367 / 366 | 314 / 314 | 362 / 364 |

`false` stores uncompressed pages in the guest cache and Angie compresses
every hit (a 127 KB thread page): the cached tier collapses.  The split keeps
the guest cache at full speed and gives members +4 %.  Member pages grow
from ~16-20 KB (level 9) to ~21 KB (Angie level 4).  Shipped as a managed
block at the end of every XenForo `src/config.php` (`XF_MEMBER_GZIP=angie`).

## 3. Regex and map cost on the cached path

`perf record -a -g` during the XenForo cached tier, Angie samples only:

| Change | regex+map share of Angie CPU | XenForo cached | WordPress cached | Chevereto cached |
|---|---:|---:|---:|---:|
| before | 6.35 % | | | |
| lean http maps | 5.02 % | +3.2 % | +2.6 % | ~+2 % |
| + lean location chain | 2.89 % (from 3.71 % in that session) | +3.0 % | ~+1.5 % | ~+1.5-3.5 % |

Lean maps: ~26 regex calls per XenForo hit (~34 for WordPress) down to ~3
(alternations, exact fast paths for the common inputs, the credential
limiter gated on POST).  A 167-probe corpus over URIs, cookies, headers and
methods gave identical values for every decision variable.

Lean location chain: one deny regex per application, exact
`= /index.php`, `[^/]\.php$`, no PATH_INFO split for those locations, the
dot-segment test as a map; 25-39 location regexes per guest hit down to 2-4.
A 164-probe status corpus (with fixture files: `.env`, `.git/config`,
backups, dumps, PHP in upload/data trees, ...) differed only where intended:

* closed: `/css.php/x` (executed with PATH_INFO) 200 -> 404,
  `/proxy.php.bak` (served as text) 200 -> 403, `/data/.x.png` 200 -> 403;
* removed (fingerprinting only): WordPress `readme.html`, `license.txt`,
  plugin `composer.json`/`package.json`, `.psd`/`.fla`; `composer.json`
  in the XenForo root;
* refused with another code: `/login/x.log`, `/install/x.log`,
  `/attachments/x.log` 403 -> 404, `/a.php/b.sql` 404 -> 403, WordPress
  names on XenForo/Chevereto 403 -> 404, `/x/.aac,.webp` on WordPress
  404 -> 403.

Existing vhosts are migrated by `--optimize` (`tune_vhost_lean_locations`):
all four test vhosts converted, `angie -t` passed, security probe 54/54,
cookie suite 62/62, functional exercise 0 unexpected responses.

## 4. Tracking parameters

`$cache_request_uri` drops `utm_*`, `fbclid`, `gclid`, `gclsrc`, `gbraid`,
`wbraid`, `dclid`, `msclkid`, `mc_cid`, `mc_eid`, `_ga`, `_gl`, `igshid`,
`yclid`, `ttclid`, `twclid`, `li_fat_id`, `srsltid` from the guest-cache key
(up to six per URL; other parameters keep their order; PHP still gets the
original URI).  On the host `/threads/<x>/?utm_source=facebook&
utm_medium=social&fbclid=...` and `?fbclid=other` were answered from the
entry of the clean thread URL; `?page=2&utm_campaign=x` got the `?page=2`
entry.  A request without a query string runs no regex for this.

## 5. PHP 8.6.0

| Check | Result |
|---|---|
| Sury packages | `php8.6-*` core 8.6.0-2 published; **`php8.6-redis`, `-igbinary`, `-imagick`, `-apcu`, `-msgpack` not published** |
| PECL builds against 8.6.0 | igbinary 3.2.17RC1, redis 6.3.0 (with and without igbinary) and imagick 3.8.1 **fail to compile** (removed `XtOffsetOf`, `INI_INT`/`INI_STR`, `zval_dtor`; changed `php_error_docref` argument types) |
| `--upgrade-php=8.6` | refuses before purging: Chevereto needs redis and imagick, XenForo needs redis |
| with `SETUP_PHP_ALLOW_MISSING_EXT=1` | 8.6.0 installed and tuned (JIT tracing 64 MB) |
| WordPress 7.1.4 on 8.6 | production exercise clean; debug: 19 compile-time deprecations, 0 at run time |
| XenForo 2.3.13 on 8.6 | fatal while its Redis cache is configured (no php-redis); with the cache off, production exercise clean; debug: the same two POST 500s as on 8.5, 59 deprecation log rows |
| Chevereto 4.5.9 on 8.6 | cannot run (Imagick is a hard requirement; login 500) |
| back to 8.5 | blocked once by the collateral-removal guard (test-only `php8.6-dev` pulled `pkg-php-tools`); after removing the test packages: 40 s, 0 warnings, all extensions back, exercise clean |

Verdict: not ready for live production on this stack.  Re-test when Sury
publishes `php8.6-redis` and `php8.6-imagick` (they need upstream PECL
releases first).  Most recent fully compatible versions stay: WordPress
8.5, XenForo 8.4 (8.5 clean in production mode), Chevereto 8.4.

| Live suites on the migrated test host | security **54/54**, cookie **62/62**, functional **0 unexpected** |

An adversarial review (5 lenses, 3 skeptics per finding) confirmed 16
findings, all fixed before commit, among them: the vhost migration could
drop the line after a one-line block and remove a one-line `auth_basic`
admin block; the `/images/` fold was not scoped to that block; a nested
`php_wp.conf` would fail `angie -t` (now rewritten to `php.conf`); a
failing `update-grub` aborted the run (now a retried warning); a trailing
`?>` on a code line would have printed the XenForo block as text; and a
request with tracking parameters could have stored a redirect or page that
echoes them under the clean URL (such requests now read the shared entry
but never write it).

Restore: `restore-baseline.sh` (`--purge all` removes the GRUB drop-in and
runs `update-grub`), session files removed, reboot.
