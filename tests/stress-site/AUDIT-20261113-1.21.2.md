## 1. Refactoring and architecture

The audit fixes keep the install and `--optimize` paths on the same helpers
instead of adding a second implementation:

- `valkey_guard_maxmemory_mb` is the single maxmemory decision for the
  install plan, `--optimize` and the dry run.  `valkey_live_cli`,
  `valkey_active_conf`, `valkey_size_to_mb`, `valkey_current_maxmemory_mb`
  and `valkey_policy_evicts` isolate the live probes.
- `sysctl_dirty_thresholds_mb`, `io_rotational_read_ahead_kb` and
  `network_tuning_unit_text` replace inline arithmetic and a duplicated
  systemd unit writer.
- `php_purge_preflight`, `php_fpm_candidate`, `php_installed_version` and
  `php_upgrade_unversioned_only` are shared by `--php`, `--upgrade-php` and
  validation.  `--php` is now a first installation; an existing host keeps
  its packages, extensions and extra pools and only re-applies the managed
  configuration.
- `mariadb_reserved_user` / `mariadb_reserved_db` are used by `--domain`
  validation, by the provisioning function just before the SQL and by the
  MariaDB user helper.
- The state snapshot (`tests/deploy-audit/state-snapshot.sh`) compares
  digests, modes, unit enablement/activity, sysctl, limits, crontab and the
  effective values of every service.  An install followed by `--optimize`
  and a second `--optimize` is now a 0-line diff once application files are
  stable.
- The precompress helper has one runner definition (`www-data` via
  `runuser`) shared by cron and the first pass.  The root guard in the
  helper drops privileges before touching a web root.

## 2. Defects reproduced and closed

All four were reproduced on the host, fixed in the two repositories, then
re-probed after a GitHub deploy (`setup.sh --optimize` without
`CONFIG_SOURCE_DIR`).

| Defect | Probe before | Result after |
|---|---|---|
| Host-header cache poisoning | `Host: wp.test.local:8443` on 443 shared the cache entry and served a cached 301; XenForo rendered the wrong base URL | poison request 200, normal request 200 `HIT`; PHP sees `HTTP_HOST=wp.test.local` for `:8443`, uppercase and `:443` spellings; `Host: evil.test` is not routed |
| XenForo API in guest cache | `//api/`, `/Api/`, `/?api/` with `XF-Api-Key` were stored | all four are `BYPASS` with and without a key, before and after `--optimize` |
| Backup files served | `/wp-config.php.save`, `/wp-config.txt`, `/backup.zip`, `/src/config.php.save`, `/app/env.php.save` returned 200 | all 403; `/wp-content/uploads/2026/release.zip` and a normal image stay 200 |
| MariaDB resize clamp | MariaDB 11.8 accepted `SET GLOBAL` above the startup maximum, returned success and kept 1024 MB | detection reports the clamp and restarts; pool is 1738 MB afterwards, `innodb_buffer_pool_size_max=1744` |

The host-header fix lives in `http.d/fastcgi_host.conf` plus
`snippets/fastcgi-php.conf`; the API fix in `http.d/fastcgi_cache*.conf`,
`php_xf*.conf`, `xf_proxy_pass.conf` and `php_flarum.conf`; the file fix in
`h5bp/location/security_backup_files.conf` and
`security_root_archives.conf`.  The MariaDB fix is
`mariadb_pool_resize_short` in `lib/service-optimizers.sh`.

## 4. Performance

### 4.1 Guest/member tiers, loopback, 100 connections, 10 s

"1.21.0 before/after" is the tuning comparison from
`TUNING-20261113-1.21.0.md`; "1.21.2" is this build after the security
fixes.  Every response was 2xx (non-2xx column 0).

| Tier | 1.21.0 before | 1.21.0 after | 1.21.2 |
|---|---:|---:|---:|
| WordPress guest home (cached) | 14 769 | 67 240 | 65 576 |
| XenForo guest home (cached) | 81 655 | 82 256 | 82 751 |
| Chevereto guest /explore (cached) | 17 718 | 70 283 | 70 382 |
| Chevereto guest image (cached) | 16 168 | 69 525 | 72 033 |
| WordPress member home | 285 | 289 | 286 |
| XenForo member home | 862 | 864 | 887 |
| XenForo member thread | 517 | 508 | 553 |
| Chevereto guest home (uncached) | 2 621 | 2 671 | 2 739 |

The cached tiers cost 0.10-0.13 ms of Angie CPU per request.  The security
rules add a few regex locations but no measurable regression (run-to-run
variance is about 3%).  Member tiers are PHP/DB-bound and unchanged.  A
Chevereto logged-in tier remains unmeasurable at 100 connections: the
application verifies `KEEP_LOGIN` with bcrypt and serialises one session's
requests.

### 4.2 PHP-FPM

`pm = static`, 16 workers on 16 logical CPUs (one per CPU), `pm.max_requests`
16384, `request_terminate_timeout 300s`, slow log at 10s, backlog 65535,
`rlimit_files 524288`.  Static 16 remains the peak on all three apps; the
distribution default (dynamic, 5 workers, no JIT) previously measured
133 req/s WordPress member, 246 XenForo member thread and 1 541 Chevereto
guest home against 282/497/2 712 for this profile.

### 4.3 OPcache JIT

Shipped: `opcache.jit=tracing`, `opcache.jit_buffer_size=64M`,
`opcache.memory_consumption=512M`, thresholds 64/127/16/64, and
`opcache.max_accelerated_files` 93 240 after the application files exist
(128 256 ceiling on an empty root, then stable on every later run).

| Profile | WordPress member home | XenForo member thread | Chevereto guest home |
|---|---:|---:|---:|
| JIT off | 270 req/s | 520 req/s | 2 754 req/s |
| tracing, 64 MB (shipped) | 281 req/s | 501 req/s | 2 706 req/s |
| tracing, 128 MB | 281 req/s | 496 req/s | 2 711 req/s |

The 64 MB tracing buffer is kept: +5% on WordPress, -5% on XenForo and flat
on Chevereto against JIT off, and 128 MB buys nothing.  The harness now also
measures PHP 8.4+'s built-in thresholds (61/127/8/8) for the next sweep.

### 4.4 MariaDB and Valkey

- MariaDB: 1738 MB buffer pool, 200 max connections, back_log 65535.  The
  clamp test started at 1024 MB; `--optimize` wrote 1738 MB, detected the
  online clamp at 1024 MB and restarted into 1738 MB.
- Valkey: 434 MB maxmemory, allkeys-lru.  A full cache keeps its current
  size instead of growing by 20% per run; an explicit `--valkey ram=` is
  never changed by the guard.

## 7. Not done / residual

- **HTTP/3 snippet unchanged.**  The proposed centralisation of `reuseport`
  in `h5bp/tls/http3.conf` was rejected: with the operator QUIC include in
  place, `angie -t` failed with `a duplicate listen 0.0.0.0:443`.  The
  snippet is left as it was in 1.6.24 rather than shipping an untested
  change.  A vhost that enables HTTP/3 still owns its own `listen` lines.
- **PHP 8.6** is blocked by extension publication, not by application code;
  rerun the compatibility walk when `php8.6-redis` and `php8.6-imagick`
  appear.
- The MariaDB clamp test used a deliberately lowered pool; it validates the
  detection and restart path, not a production resize of a multi-TB pool.
