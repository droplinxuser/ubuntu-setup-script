# Audit — 1.22.0 (source-only nginx, PHP and Valkey; the 1.21 → 1.22 migration)

Date: 2026-11-25
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe, Ubuntu
26.04.1).  Two runs: a fresh install from the baseline, and a host
provisioned by 1.21.71 then migrated.  Pair: `server-configs-nginx` 1.7.0
(branch `nginx`).

## 1. Requests (operator decisions)

1. nginx (latest mainline, compiled, branding stripped) replaces Angie.
2. PHP (FPM and CLI) and Valkey built entirely from source; no deb
   packages.  Any PHP version php.net releases.
3. Existing hosts migrated once by `--optimize`.
4. Angie ACME configurations move to the self-signed origin certificate
   automatically.
5. Sury and Angie packages purged only after the compiled services serve.
6. CPU change: services stay down until the native rebuild finishes.
7. Hosts under 4 GB RAM: nginx only.
8. One combined release.
9. Kept from 1.21.71: the login limiter (`limit_req` compiled in),
   `auth_basic` compiled in, `limit_conn` not built.  MariaDB and
   Elasticsearch stay apt packages.

## 2. Method

* Design reviewed adversarially before implementation; the code follows
  its third revision.
* Fresh install through `setup.sh --basic --nginx --php ver=8.5 --mariadb
  --valkey --elastic --others all`, the three apps deployed
  (`deploy-three-apps.sh`), then `--optimize` under load, then a second
  `--optimize`.
* Migration: the host was provisioned by 1.21.71 with the Angie package,
  Sury PHP 8.5, the valkey-server package, the three apps, an Angie ACME
  vhost and a vhost with `auth_basic` and `sub_filter`.  The 1.21 suites
  passed before (76/76, cookie 105/105).  Then `setup.sh --optimize` with
  1.22.0, repeated after each fix, then a reboot and a second `--optimize`.
* Suites after each run: security, guest-cache cookie, functional walk.

## 3. Findings

### 3.1 Why nginx (measured in 1.21.71)
Compiled nginx 1.31.10 against compiled Angie 1.12.5, same flags,
libraries and modules, identical files, 5 rotated rounds: cached pages
+0.5 to +1.5 % (XenForo home 123,007 against 121,482 req/s), PHP pages tie.

### 3.2 Fresh install
10 min 15 s for the whole install, including building nginx 1.31.10, PHP
8.5.13 and Valkey 9.2.0 with LLVM 23.  No `Server` or `X-Powered-By`
header; the 404 page has no "nginx".  `--optimize` under load BOLTed nginx
(in-place upgrade, no restart), PHP and Valkey.  A second `--optimize`:
all builds current.

### 3.3 Bug: BOLT on an idle server
Right after the install, with no traffic yet, the PHP BOLT step reported an
error.  php-fpm had taken no samples: that is too little traffic, not a
failure.  It now reports "too little traffic, BOLT skipped" and the next
`--optimize` under load retries.

### 3.4 Migration: PHP and Valkey
Both moved in the first run.  Sury packages purged; the valkey-server
package removed (left in dpkg's `rc` state on purpose: its postrm can
delete `/var/lib/valkey`); this script's units enabled.  The PHP build kept
every extension the Sury PHP had loaded (calendar, ftp, gettext, gmp,
sockets, xmlreader and others) on top of the apps' sets.

### 3.5 Migration: three bugs in the nginx part
Each one blocked the part or rolled it back.  Each time Angie kept serving
without intervention.

1. **Package file scanned as an operator file.**  The Angie package's own
   `http.d/default.conf` (the `api` status location) was treated as the
   operator's and blocked the part as Angie-only.  Package files are no
   longer scanned or copied.
2. **Catch-all compared strictly.**  The cutover check compares each
   vhost's answer before and after.  `Host: localhost` had been answered by
   Angie's package welcome page, so the nginx answer differed and the
   cutover rolled back.  Under nginx the catch-all closes the connection
   (444).  It is now compared leniently: it may close or answer 4xx, but
   never 5xx.
3. **A rolled-back part was never retried.**  The migration skips a part
   whose scanned tree has not changed since it was refused, so even a fixed
   release did not try again.  The state now records a digest of the
   migration code with each result; a new release retries, and
   `SETUP_MIGRATE_RETRY=1` forces it.

### 3.6 Migration: after the fixes
* nginx cutover done; Angie, its repository and the `angie` user purged.
* `/etc/angie` moved to `/var/backups/setup-1.22`; `angie.service` is now an
  alias of `nginx.service`.
* Cron lines rewritten to `/etc/nginx/scripts/cloudflare.sh`.
* The ACME vhost serves the host's self-signed certificate (200).
* `auth_basic`: 401 without and 200 with the password, on nginx.
* `sub_filter` commented out with the marker.
* No Angie, PHP or Valkey packages left (valkey `rc` state only).
* Reboot: nginx, php8.5-fpm and valkey-server active and enabled, 0 failed
  units, every site 200.
* A second `--optimize`: nothing to migrate, all builds current.

### 3.7 `--upgrade-php`: up to 8.6, down to 8.1, refusals

Measured on the migrated host with all three apps (WordPress, XenForo,
Chevereto).  The suites ran after every step.

| Step | Result | Time |
|---|---|---|
| 8.5 → 8.6 | Build failed safely: the igbinary release (3.2.16) does not compile on PHP 8.6. Nothing changed; 8.5 kept serving. Build log 427 KB, disk flat (the first attempt, before the fix, grew the log to 1.7 TB). | 51 s |
| 8.5 → 8.0 | Refused before anything changed (8.1 is the oldest supported series). | 0 s |
| 8.5 → 8.4 | First attempt failed safely (the shared `opcache.so` linked with GNU ld). After the lld-driver fix: 8.4.28 serving. | 216 s |
| 8.4 → 8.3 | 8.3.37 serving. | 207 s |
| 8.3 → 8.2 | First attempt failed safely (the `php` program linked with GNU ld). After the fix: 8.2.36 serving. | 162 s |
| 8.2 → 8.1 | First attempt failed safely (PHP 8.1 does not compile against OpenSSL 4). With OpenSSL 3.6.5: 8.1.34 serving. | 316 s |
| 8.1 → 8.5 | Back to the kept build, no rebuild. | 38 s |

* Security 78/78, cookie 105/105 and functional 0 failures on 8.2, 8.3, 8.4
  and 8.5, and after every refused or failed step.
* On 8.1, Chevereto 4.5 answered 500 on every page: its Composer platform
  check needs PHP 8.2.  The after-switch check still reported "3 OK"
  because it requested `/index.php`, which nginx answers with a 301
  without running PHP.  Both are fixed.  The switch to 8.1 is now refused
  before building, naming Chevereto's PHP 8.2 requirement.  The check now
  requests the home page, and an 8.4 round trip after the fix reported
  "PHP pages probed 3 OK" from real pages.
* Exactly one previous version is kept, disabled, for rollback; the others
  are retired with their `/etc/php` tree moved to the run's manifest.
* Disk use stayed at about 22 GB through every build.

### 3.8 Supply chain and hardening
* nginx tarballs verified against nginx.org's PGP keys (fail closed);
  Valkey against valkey-hashes; PHP against php.net's SHA-256; the
  setup-build-sources mirror last, under the same hash rules.
* Hardening flags kept; every BOLT output keeps a non-executable stack
  (`bolt_stack_check`).  Units hardened; Valkey keeps `NoExecPaths=/` with
  `ExecPaths=` for the build, `/usr/lib` and `/lib`, and
  `MemoryDenyWriteExecute=yes`.

* fresh install: functional walk 0 failures, security 78/78, cookie

* migrated host: security 78/78, cookie 105/105, functional 0 failures,

* `--upgrade-php=8.6` round trip: see 3.7.
