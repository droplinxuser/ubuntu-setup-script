# Audit — 1.21.62 (Anubis removed, and what a lean Angie path costs)

Date: 2026-11-23
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe,
Ubuntu 26.04.1, kernel 7.0.0-43), returned to its pristine manifest before
the install and restored afterwards.  Mitigations were **on** for every
number below (`/proc/cmdline` without `mitigations=off`; `spectre_v2:
Mitigation: IBRS`).  Pair: `server-configs-nginx` 1.6.55.  Applications:
WordPress 7.1.4, XenForo 2.3.13 (200 threads / 2,600 posts / 60 users),
Chevereto 4.5.9-pro (one uploaded image), deployed with
`deploy-three-apps.sh` and exercised with `exercise-apps.sh keep`.

Primary focus: remove the Anubis bot filter completely, and make the Angie
map/regex layer leaner (convert every `if` that a `map` can replace).

## 1. Findings fixed

### 1.1 The bot filter is gone (primary focus)

Anubis was an optional Go proxy in front of every vhost: Angie terminated TLS
on `:443`, proxied to a Unix socket, Anubis applied a proof-of-work policy
and proxied to a second socket served by the real vhosts.  On top of that sat
a static-asset "shadow" server block per vhost, an njs pass-cookie verifier
with its own shared dictionary, a systemd unit, a policy file and a
generated `default_server`.  `lib/anubis.sh` was 1,690 lines; the
integration reached `cli`, `overrides`, `validate`, `web`, `services`,
`service-optimizers`, `restart`, `purge`, `diagnostics` and `os`.

It is deleted, not disabled: 2,4xx lines with its tests and documentation
(see `git show --stat 6734aad..HEAD`).  `--angie anubis=…`,
`--optimize anubis=…` and a leftover `SETUP_ANUBIS` now stop the run with an
explanation instead of silently deploying without a filter the operator
asked for, and `setup.sh` refuses to run at all on a host that still carries
the generated terminators (a half-migrated host would have every vhost on a
socket nothing serves).  `tools/remove-anubis.sh` performs the migration in
the only safe order: restore the vhosts from their pre-integration copies,
remove the generated Angie files, `angie -t` and a graceful reload while the
filter is still running, then stop and disable it.

Why remove rather than fix: production traffic terminates at Cloudflare, so
the origin-side filter was a second, weaker bot filter that paid a full
request hop.  Earlier cycles measured that hop on this host: a cached page
answered 27.7k req/s through the filter against 95-103k unfiltered (1.21.57),
and the worst case used ~5.2 cores of the 12-thread box at 94 % host CPU.
Those reports were removed from the tree with the feature; the numbers are
in git history.

### 1.2 Cloudflare TLS had been silently disabled (high, follow-on)

`cloudflare_tls_migrate` returned early whenever the filter was managed
(`lib/web.sh:997`), so the Cloudflare path — self-signed origin certificate,
`real_ip` from `CF-Connecting-IP`, certbot retirement — never ran on a
filtered host.  With the filter gone the guard is gone too, so the
Cloudflare profile now applies to every vhost with a certbot certificate.
That is the intended production model: the origin accepts only Cloudflare.

### 1.3 The last regex `if` in the shipped tree is gone (primary focus 2)

The shipped tree had 16 `if` statements.  Fourteen of them test a 0/1
variable (`if ($xf_guest_cacheable) { return 418; }` and the security
no-cache flags); a `map` cannot express "return only when true" — `return`
takes no condition — so those stay, and they are the cheapest possible test:
no PCRE, no string build.  The two that did run a regular expression were
Chevereto's front-controller redirect:

```nginx
if ($request_uri ~ "^/index\.php(?:[?]|$)") { return 301 /$is_args$args; }
```

A direct `/index.php` is not a route (Chevereto answers 500 for it), so both
Chevereto PHP files redirected it.  A request Angie did **not** rewrite has
`$request_uri == "$uri$is_args$args"`; a `try_files` internal redirect keeps
the original `$request_uri` and rebuilds `$uri` to `/index.php`, so the two
differ.  The identical rule is now one string comparison
(`h5bp/php_chev_cache.conf`, `h5bp/php_chev.conf`) and one PCRE is removed
from every Chevereto request.  Verified live and by the app suite:

```
/index.php        301 -> /
/index.php?a=1    301 -> /?a=1
/explore          200 (untouched)
exercise-apps.sh: "chev canonical /index.php 301"
```

`h5bp/location/security_dot_segments.conf` keeps its `if ($bad_dot_segment)`:
the map behind it (`http.d/dot_segments.conf`) is a single PCRE, evaluated
once per request and reused after the `try_files` redirect, and it must run
before the backend sees the raw request line.

### 1.4 Dead configuration removed

`http.d/referer_map.conf` defined `$302_referer` and `$302_method` (with
`~site.com` / `~site.net` patterns) and nothing in either repository
references either variable: two maps, four regexes that were never evaluated
(maps are lazy) and a misleading file.  Deleted; `--optimize` retires a copy
on an existing host.

### 1.5 Anubis remnants in the Angie tree (low)

`$guest_cookie_unlisted` (the default-deny cookie allowlist) carried the
`techaro.lol-anubis-auth*` alternatives, and the `$app_https` /
`$trusted_forwarder` maps trusted a `unix:` peer.  Both existed only for the
filter.  Removed: the allowlist alternation is shorter and a Unix-socket peer
can no longer make PHP believe a request is HTTPS.

## 2. Measurements

### 2.1 Method

Same host, same applications, same tool, same concurrency.  Two Angie trees,
deployed by the **same** `setup.sh --optimize` (`CONFIG_SOURCE_DIR`):
`scn-old` is the committed 1.6.54 tree, `scn-new` this cycle's 1.6.55.
`loopback-tiers.sh 100 10` (wrk `-t4 -c100 -d10s`, HTTPS/1.1 keep-alive,
`Accept-Encoding: gzip, br`, `User-Agent: setup-bench/1.0`) run three times
per tree, back to back, nothing else on the box.  Every number is the median
of three passes; the spread is the min-max of those passes.  Per-request CPU
is each service's cgroup delta divided by the requests completed.

Two measurement notes, both learned the hard way on this host:

* **Do not empty a 16 GB FastCGI cache with `find -delete` under a running
  Angie.**  The cache manager then reconciles a million deleted keys and
  blocks the zone: one whole 10 s tier answered zero requests, the next one
  recovered mid-run.  The passes below run against a warm cache, which is
  what a production host sees.
* A second `wrk` left running from an earlier shell halves the numbers
  (93k → 48k).  Every pass below started from an idle host (`load 0.4`).

### 2.3 Chevereto, alternating A/B

The only tier whose request path actually changed (one PCRE → one string
compare) was measured again with the two trees applied alternately, four
rounds each way, so any drift hits both sides equally:

|---|---:|---:|---:|---:|
| 1 | 142,389 | 0.96 ms | 142,795 | 1.17 ms |

**−0.2 %, inside a ±0.6 % spread: no measurable change.**  The change is a
simplification (one fewer regex in the tree, one less PCRE per Chevereto
request), not a speed-up, and it is not claimed as one.

### 2.4 Verdict on focus 2

The Angie maps were already lean before this cycle: the previous cycles
collapsed the bypass rules into one alternation per decision, added exact
(hash) matches for the common values, and made the cookie rule a single
negative lookahead that runs no PCRE without a Cookie header.  What was left
to do was small and is done:

* 0 regex `if` statements in the shipped tree (16 `if`s, 14 are 0/1 variable
  tests a map cannot replace, 2 were the Chevereto redirect, 1 is the
  dot-segment map's boolean, 1 is a sample template);
* 1 dead map file deleted;
* the Anubis alternatives and `unix:` peers removed from three maps.

The remaining per-request PCRE count on a cached guest page is three: the
dot-segment map, the URI no-cache map and the tracking-parameter map (only
when a query string is present, for the last one).  Each is one anchored
alternation; the cookie rule, the encoding rule and every cache decision are
exact matches in the common case.  Squeezing those three would buy less than
the noise floor measured in 2.2, so they stay.
