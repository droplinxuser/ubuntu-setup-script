# Audit — 1.21.59 follow-up (guest-cache encoding, zstd removal)

Date: 2026-11-23
Host: the Xeon E-2236 test host (6C/12T, 62 GB, md RAID0 NVMe, Ubuntu
26.04.1, stock mitigations), restored to its 696-package baseline after the
1.21.58 cycle.  Pair: `server-configs-nginx` 1.6.52.  Applications:
WordPress 7.1.4, XenForo 2.3.13, Chevereto 4.5.9-pro, deployed with
`deploy-three-apps.sh` (no large seed this time).

## 1. Questions and findings

**Is there a packaged PHP Brotli extension?**  No.  Sury's index for Ubuntu
26.04 (1,925 packages) has no Brotli package; its compression extensions for
PHP 8.5/8.6 are `zstd` and `lz4`.  Ubuntu's `main`/`universe` have
`php-zstd` only.  The upstream extension exists as a PECL build, which the
native-APT rule excludes.

**Can XenForo produce anything but gzip?**  No.  `src/XF/Http/Response.php`
compresses when `HTTP_ACCEPT_ENCODING` contains the substring `gzip`
(`strpos`), always with `gzencode($body, 9)`, and sends
`Content-Encoding: gzip`.  `$config['enableGzip']` only switches that on or
off.  There is no Brotli or zstd code in `src/XF`.

**Can `deflate` / `gzip;q=0` poison the plain guest entry?**  Suspected from
the code (the key treats both as plain; XenForo and PHP's
`zlib.output_compression` compress for them), reproduced on 1.21.58:

| App | header | what that client got | next `Accept-Encoding: identity` client |
|---|---|---|---|
| WordPress | `deflate` | deflate body, HIT | MISS, plain page |
| WordPress | `gzip;q=0` | gzip body, HIT | MISS, plain page |
| XenForo | `gzip;q=0` | gzip body, HIT | MISS, plain page |
| Chevereto | `deflate` / `gzip;q=0` | deflate / gzip body, HIT | MISS, plain page |

Not a leak: the responses carry `Vary: Accept-Encoding` and Angie stores a
separate variant per exact request header, so a compressed body only went to
clients that sent the same header.  The same mechanism split the cache:

| XenForo thread, 1.21.58 | result |
|---|---|
| Chrome x2, Safari x2, Chrome, Safari, Cloudflare x2, ... | Chrome MISS/HIT, Safari **MISS**/HIT, Cloudflare **MISS**/HIT |
| entries on disk for one page | **3** |

Every browser family filled its own copy of every page (two PHP renders each
with `min_uses 2`).  Behind Cloudflare the origin sees one header (`br,
gzip`), so the fleet barely paid for it; direct traffic did.

## 2. Fix

- Guest caches ignore `Vary` for storage (`fastcgi_ignore_headers ...
  Vary`, `proxy_ignore_headers ... Vary`); `Vary` is still sent.
- The application is given exactly the key's encoding: `$guest_cache_ae`
  (`gzip` or nothing) as `HTTP_ACCEPT_ENCODING` in every cached location
  (WordPress: in `php_wp_handler.conf`, since the PHP locations drop a
  server-level `fastcgi_param`).  XenForo proxy cache: `$xf_proxy_ae`, for
  cacheable guests only, so proxied members still get Brotli from the
  origin.  setup.sh's legacy XenForo map gains `$setup_cache_ae`.
- Two storage-time guards, in every guest cache's `*_no_cache` line,
  because `Vary` no longer protects anything: `$guest_cache_enc_mismatch`
  (the body's `Content-Encoding` must match the key, whichever location
  rendered it) and `$guest_cache_vary_other` (a response that varies on
  more than `Accept-Encoding` is not stored).  The three applications send
  `Vary: Accept-Encoding` only; a WordPress fixture page sending
  `Vary: User-Agent` is never stored (MISS x3).  With the WordPress handler's
  header line removed (what a `php.conf` subdirectory location does), three
  `deflate` requests were never stored (MISS x3, deflate) and the next
  plain client got a clean page.  (`angie -t` rejected a first version of
  the Vary map: map strings match case-insensitively, so `Accept-Encoding`
  and `accept-encoding` were duplicates; the run left the live tree
  untouched.)

After the fix (same host):

| check | result |
|---|---|
| Chrome, Safari, Cloudflare, `gzip` after Chrome filled the entry | all HIT, gzip |
| `deflate`, `gzip;q=0` | plain page (MISS, then HIT on the plain entry) |
| `identity` after them | HIT, plain |
| entries on disk for one XenForo thread | **2** (gzip, plain) |
| cached tiers, browser / `br, gzip` | WordPress 90.3k / 85.4k, XenForo 125.9k / 125.3k, Chevereto 131.0k / 131.4k req/s; Angie 0.06-0.09 ms per hit (smaller pages than the 1.21.58 cycle: no large seed) |

## 3. zstd removed

On request: every site is behind Cloudflare, which asks origins for `br,
gzip` only, so the 1.21.58 zstd module never answered a production request.
`--optimize` on the 1.21.58 host (module installed, `60-zstd.conf` and
`http.d/zstd.conf` live):

| step | result |
|---|---|
| `--optimize --dry-run` | announces the retirement |
| `--optimize` | 0 warnings; both managed stanzas moved to `/tmp`; `angie -t` clean; `angie-module-zstd` purged after the reload |
| compression summary | Brotli level 4, gzip |
| second `--optimize` | 0 differences in 3,032 facts |

Nothing is retired while an operator's own file uses zstd directives (they
rely on the managed `load_module`), and the purge is skipped when apt would
remove another package with it (unit-tested with stubs).  The purge runs
after the Angie pass commits (`optimize_angie` after its reload,
`install_angie` after its restart), so a rollback never restores a tree
that loads a purged module.

## 3a. Adversarial review

Three reviewers (cache correctness, live-host safety, test quality), each
finding checked by two reviewers told to refute it.  Four upheld by both,
none split or rejected; all fixed and re-verified:

| finding | fix |
|---|---|

| no test covered a 1.21.58-shaped managed map gaining `$setup_cache_ae` | fixture and check added |  `http.d/zstd_conf` left by an older tree sync is never included and
does not count as use.
